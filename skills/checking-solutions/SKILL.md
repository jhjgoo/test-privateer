# 质检解决方案

读取已经形成的方案及其问题、需求和证据，查找会让实现只对当前案例有效、却无法支持目标行为的断点。用户让 AI 输出方案时，在最终交付前对方案草稿执行本质检；只报告或修正有证据的问题，不替负责人审批，不用质检流程取代原方案生成。

## 固定质检范围

记录原问题或目标、方案声称解决的范围，以及实际读取的需求、代码、测试和运行证据。材料缺失时保留未验证连接，不补写原因或规则。已有方案直接质检；本轮同时负责产出方案时，先形成草稿，再检查并修正发现，最终只交付修正后的方案和仍未闭合的风险，不编造一次独立审查已经发生。

## 检查对症链

沿以下链路逐段检查：

```text
问题或目标 → 已知依据 → 方案作用点 → 预期行为变化 → 验证证据
```

1. **样例耦合：** 常量、字符串、错误码、用户、地区、测试数据、调用路径或措辞是否只来自当前案例，缺少业务规则、系统约束或失败机制依据。
2. **作用点错位：** 方案是否修改真正控制目标行为的 seam；局部入口补丁是否遗漏共享路径，文案或 Prompt 修改是否掩盖状态、工具、数据或编排问题。
3. **闭环断点：** 依据能否支持该方案，方案能否推出声称的行为变化，验证能否观察该变化。原因仍未知时可以止损，但必须保留未知和后续取证。
4. **范围夸大：** 防护、单点修复或单次通过是否被描述成根因修复、全局覆盖或稳定提升。
5. **区分性验证：** 选择能区分“修到共同依据”和“记住当前案例”的最小探查；按可疑耦合点选择同类、邻近正常或变形场景，不固定凑类型和数量。

硬编码按依据判断，不按代码外形判断。已确认规则支持的常量和局部分支不是 finding；明确标注范围的止损可以成立，只检查其效果、保持边界与声明是否一致。改动最小指修复共同原因所需的最小改变，不是让当前样例通过的最小 diff。

## SDD 加深分支

先依据框架或产物关系确认属于 SDD：材料明确使用 SDD／Spec-Driven，或 proposal、spec、design、tasks、verify、archive 等产物形成需要跨角色追溯的变更链。确认后再按实施前、实施中、实施后或归档前选择检查阶段，并读取 `references/sdd-contract-chain.md`。仅出现“实施前质检”等时点、但没有 SDD 框架或产物链的普通方案，仍停在核心检查，不得要求补齐 SDD 产物。

## 交付

已有方案的每条发现写明位置、直接证据、断开的连接、影响和最小补证或修正方向；另列未验证部分和证据边界。本轮同时负责产出方案时，不展开一份自我评审报告，用修正后的方案体现已处理发现，并明确剩余未知、止损性质和待验证声明。

普通方案不输出批准、驳回或实施准入结论。没有发现时只说明当前范围内未发现可证明的问题，不把它写成方案已经正确。

原因尚未查清且会改变方案时，交给 `investigating-findings`；Prompt 或完整 Agent 的专属行为质量分别交给 `prompt-eval`、`agent-eval`，本 Skill 只质检它们已经形成的改进方案是否对症。

**完成条件：** 方案每项关键主张都已连接到可定位依据、作用点、行为变化和验证，或被明确标记为断点／未验证；发现不把合法业务规则误报为硬编码，不把质检结论扩大为实施批准；AI 产出的方案在交付前已完成同一检查。
