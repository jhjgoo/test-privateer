# SDD 契约链加深检查

仅在 `SKILL.md` 的 SDD 条件成立后读取。核心方案质检已经完成；本文件只增加 SDD 阶段、产物角色、任务、实现证据和归档事实检查，不重复普通方案规则。

```text
意图与边界 → 行为与 oracle → 技术决策 → 工作切分 → 实现证据 → 归档后的当前事实
```

规格是测试依据之一，不是测试对象；有可运行版本时，还要核对规格主张、代码与测试证据的关系。

## 证据边界

1. 确认质检阶段：**实施前**看是否足以开工，**实施中**看漂移与剩余工作，**实施后**看是否收敛，**归档前**看当前事实是否会正确更新。阶段不能确定且会改变结论时，分别给出两种阶段的结果，不猜。
2. 识别框架和产物角色；无法识别时按通用角色映射，不要求项目改用特定文件名。非通用形态或来源不明时读取 `references/framework-map.md`。缺失角色只有在当前阶段需要它承担决策或证据时才形成 finding。
3. 读取项目规则、变更产物、相关代码、既有测试和执行证据。用户限定只看文档时明确“文档质检”；不把文档一致性当作实现正确或测试通过。
4. 记录实际读取范围、commit 或版本标识。引用必须能定位到具体文件和段落；无法定位的意见不是 finding。

## 产物角色

| 角色 | 常见形态 | 关口问题 |
| --- | --- | --- |
| 意图与边界 | proposal、requirement、user story、Why/Non-goals | 是否解决同一问题，什么必须变、不变、不做 |
| 当前事实与 delta | source specs、ADDED/MODIFIED/REMOVED、bugfix baseline | 变化类型和基线是否真实 |
| 行为与 oracle | acceptance、scenario、example、property、success signal | 第三方能否判定通过 |
| 技术决策 | design、architecture、ADR、constraints | seam、数据、兼容、迁移和回滚是否可落地 |
| 工作切分 | tasks、stories、tickets | 是否可独立执行、有依赖、可验证 |
| 执行证据 | implementation record、verify、review、test logs | 主张是否有命令、环境和结果支持 |
| 归档事实 | archived spec、living documentation | 已验证事实是否替代旧事实 |

## 契约链检查

### 1. 意图与边界

核对变更名、需求、设计、任务和验证是否指向同一意图；确认完成时什么必须为真、什么不能变、什么明确不做。多个可独立交付的价值应拆分。业务规则、系统边界或责任归属不明时，用 `clarifying-test-basis` 提问；未知不得写成规则。

完成条件：意图、非目标和变更类型可以从产物链一致推出。

### 2. 行为与判定依据

为每条规范性主张找到可观察结果和 oracle：

- 一个主张一个可判定行为；“快、稳健、友好、正确”等词有阈值、范围或判定方式。
- 关键规则有具体例子、场景、性质或人工检查方法，并真正行使该规则。
- 错误、权限、数据边界、并发、幂等、兼容、安全和回滚按风险有去向；高后果路径不能只有 happy path。
- 需求陈述行为，设计承载实现；实现方式进入需求时必须有已确认约束来源。
- delta 标记与当前基线相符，MODIFIED／REMOVED 不凭空替换旧事实。

完成条件：每个关键验收主张都能回答“在哪里观察、拿什么判定、失败长什么样”。

### 3. 技术与代码库贴合

能读代码时核对受影响调用点、接口契约、数据形态、状态迁移和既有测试。检查架构 seam 是否让行为可测试、可替换、可回归；外部依赖、认证、配置、迁移、回滚、发布顺序、观测和安全边界有决策或明确开放问题。与项目规则、constitution、ADR 或既有架构冲突时，设计说明处理方式。

完成条件：实施者不需要发明关键业务规则、系统边界或迁移策略。

### 4. 任务与交付切分

把任务、故事和验证动作映射回意图与验收主张。每个关键结果有任务或验证动作；每个任务能追溯到结果、共享基础设施或明确调研。任务应能审查、能失败、能验证，测试先行或回归保护符合项目要求；新增行为有验证不能代替受影响既有行为的保护。依赖、并行边界、文件边界、人工步骤和外部等待显式存在。任务状态与实际产物相符，延期工作有去处。

完成条件：任务序列可由新会话执行，不需要读取已丢失的聊天上下文。

### 5. 证据与收敛

实施后区分设计预期、实际检查和执行结果：

- 通过声明有命令、环境、目标版本、退出状态或可定位日志；预期命令清单不是执行证据。
- 验证覆盖每条关键主张；跳过项有理由、影响和替代证据。
- 测试失败、重跑、环境差异和修复范围没有抹除原始证据。
- review、tasks、verify、commit 和状态字段指向同一版本。
- 归档前 delta 已被证据支持，旧规格被替换或移除后不留下双真相。

完成条件：结论强度不超过证据，当前规格、任务状态和实现记录处于同一事实版本。

## 深度

核心契约链每次都查。标准深度补齐需求—任务—证据矩阵和回归保护；外部接口、数据迁移、破坏性签名、权限、并发、跨系统、安全、合规、不可恢复操作或发布顺序存在时，加深检查失败模式和替代证据；低风险小改可合并检查意图、验收、任务和证据，但不降低证据真实性要求。

不为格式补格式，不用覆盖率数字代替风险判断，不把所有风格差异升为 finding。

## SDD 交付补充

在核心质检输出之外补充：

```markdown
## SDD 变更关口
阶段：实施前／实施中／实施后／归档前
结果：可实施／有条件可实施／暂不可实施／实现未收敛／证据不足

## 契约链
| 环节 | 产物 | 当前结论 | 断点 |

## 验收证据矩阵
| 主张 | oracle / 检查 | 任务 | 实际证据 | 缺口 |
```

P1 只用于会让实施走偏、验收不可判定、关键结果无任务、实现未收敛仍宣称通过、归档会制造错误事实，或高风险失败模式无处置证据的问题。P2 用于会降低确定性但可后续修正的问题。P3 只改善表达，不改变执行。

测试证据强度判断交给 `assessing-test-confidence`，异常调查交给 `investigating-findings`。本 Skill 不代替负责人批准发布。

**完成条件：** 产物角色和阶段明确；意图、oracle、任务和证据形成或明确缺失一条可追溯链；每个 finding 有直接证据和最小修正；结果没有超过实际证据。
