# 集成与契约：保留目标边界

用于组件协作、真实依赖或消费者／提供者兼容性问题。先明确要发现哪种协作错误，再决定保留什么真实依赖。

## 1. 选择要保留的协作

读取目标规则、现有调用链、依赖配置与测试。先描述要发现的协作错误，再选最小真实边界；给出刺激入口、独立结果观察和必要版本。没有条件运行真实依赖时，保留缺口，不把替身通过升级为集成通过。

- 数据库约束、事务或查询语义是目标时，使用真实目标数据库及相关配置。内存替身通过不能证明这些行为。
- 序列化、路由、配置或启动接线是目标时，保留实际连接。不要只测手工调用内部函数。
- 外部服务不可控时，可用受控替身检查本方错误处理；另记真实服务兼容性缺口。替身需有契约依据，不自行补造响应。
- 固定依赖版本，独立准备和恢复数据。时钟、队列及并发条件按目标控制，不靠测试顺序。

**完成条件：** 每个保留或替换的依赖都有目标依据，版本及观察入口明确。

## 2. 准备并验证集成

按现有工具独立准备数据和依赖配置，从实际入口发起目标操作，再通过独立查询或承诺的外部效果观察结果。

例如，目标是唯一约束时，在真实数据库中准备同键记录，再经实际写入入口尝试冲突写入。依据产品合同检查拒绝及原记录；仅让 stub 返回“重复”不能证明数据库约束生效。

按授权运行最小检查。连接、建表或数据准备失败先归为基础条件缺口；断言到达后再判断目标规则。保存失败证据后恢复本轮数据，清理问题独立报告。

单元覆盖规则组合，集成覆盖真实协作，高层保留重要旅程。只去掉作用相同的重复，不连同高层独有的装配证据一起删除。

## 3. 验证消费者与提供者

消费者测试检查本方请求与响应处理；提供者验证检查真实提供者是否满足相应交互。记录双方版本和契约版本，缺一侧就保留缺口。

先运行消费者生成本轮契约，再让匹配版本的真实提供者准备约定状态并验证该契约。只改写手工 JSON 或仅对模拟提供者运行，不补齐缺失的提供者证据。

例如，消费者能解析模拟响应而提供者尚未运行时，只交付消费者结果及待验证的契约版本；不能发布“双方兼容”的结论。

契约只表达消费者真正依赖的消息，不锁死无关字段或提供者全部内部规则。双方兼容也不能替代写入、通知等业务副作用检查。

适合有明确消费者及提供者协作机制的边界。公共 API 规范校验也有价值，但不能直接称为消费者驱动契约测试；无法运行提供者验证时不宣称双方已兼容。

## 4. 交付

给出测试／契约文件、实际命令、双方或依赖版本、真实边界、状态准备、结果与未验证项。缺陷保护或受控失败变体可安全运行时，确认目标错误会被检出，再恢复。

**完成条件：** 兼容性、业务副作用和环境可用性分别有证据或明确缺口；只生成设计或契约不称验证完成。

## 来源与取舍

- [Pact 官方职责划分](https://docs.pact.io/consumer/contract_tests_not_functional_tests)：兼容性不等于功能效果。
- [Google 测试替身](https://abseil.io/resources/swe-book/html/ch13.html)：平衡速度、隔离与保真，不禁止全部 mock。
- [Ham Vocke 的测试组合](https://martinfowler.com/articles/practical-test-pyramid.html)：按粒度保留互补检查。
- [Kent C. Dodds 的集成实践](https://kentcdodds.com/blog/write-tests)：集成可提高信心；收益依架构与成本而变，不固定数量占比。
