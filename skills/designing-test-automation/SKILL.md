# 设计测试自动化

自动化提供持续反馈。选择能发现目标错误、保留真实边界的最小测试组合，不以覆盖率或固定比例代替价值。

## 1. 接收任务

沿用业务目标、选中行为和有效规则。项目任务读取相关测试资产；独立任务不要求 TCO 或 Spec。

先核对预期依据、数据与环境控制、失败定位和维护成本。规则未定只暂停相关精确断言；已选合理范围时直接进入专项，不另写策略报告。

**完成条件：** 能说明要保护什么、怎样判断正确，以及哪些缺口会影响选择。

## 2. 按所需证据选择方法

| 要证明的行为或边界 | 入口 |
| --- | --- |
| 稳定规则、计算、转换或局部状态 | writing-unit-tests；保留单元符号和 TDD 职责 |
| 接口请求、身份与业务效果 | [writing-api-tests](../writing-api-tests/SKILL.md) |
| 真实依赖、消息兼容或组件协作 | 按需读[集成与契约](references/integration-contract-testing.md) |
| 局部交互、反馈与恢复 | 按需读[组件测试](references/component-testing.md) |
| 贯穿真实系统的业务旅程 | [writing-e2e-tests](../writing-e2e-tests/SKILL.md) |

API／页面是操作入口，单元／集成／系统是测试范围，TDD 是开发节奏。分别说明选择；HTTP 不自动等于集成，浏览器不自动等于 E2E。以接口合同为主用接口专项，以跨层旅程为主用 E2E 专项，必要时读取另一方法，不重复执行同一检查。

同一行为按不同错误安排互补检查。规则的广泛输入可在较小范围覆盖；真实接线仍需集成证据。替换目标依赖后，结论仅覆盖替身行为。

按风险选择分区、边界、状态迁移和失败路径。普通确定性用例已足够时，不升级方法。风险超出其判定能力时再考虑：

| 风险 | 优先方法 |
| --- | --- |
| 并发、重试或操作顺序影响状态 | 模型检查，或可复现调度的并发探针 |
| 有限状态转换错误 | 状态机遍历／性质测试 |
| 输入域受约束但范围广 | 属性测试 |
| 有独立业务规则或参考实现 | 参考模型对比 |
| 内存、边界或解析安全 | 语言适用的 verifier、sanitizer 或静态检查 |

所选性质或模型必须映射到真实代码结构或已确认规则，说明输入域、状态边界、工具版本和覆盖范围。没有映射依据时不引入形式化方法；先补规则或用确定性检查覆盖可判定部分。交付前用历史反例、受控故障或失败变体证明检查能够失败；无法安全验证时声明探错能力未验证。随机次数不是判定依据；通过只证明当前模型和边界，不证明整个系统。

**完成条件：** 每种检查有独特反馈价值，真实与替换边界、未覆盖项可说明。

## 3. 接到当前交付

**只要求设计：** 交付选中行为、方法理由、准备、动作、预期来源、观察位置和未决项，不安装或运行。

**要求编写或验证：** 将已确认目标、合同、环境和执行许可交给专项。已有合适框架优先复用；选型未定时读取[框架与入口选型](references/harness-readiness.md#框架与入口选型)，按已有约定、明确委托或需确认的实质选择处理，纯接口不强制浏览器。官方 e2e 的获取与版本操作由 E2E 专项按需承接。

集成／组件任务按所选参考继续，不为进入实现再绕回方法入口。执行结果沿用 running-test-sessions 的记录约定；已运行的证据直接交回，不因交接再跑一次。

### 建立或修复轻量 Harness

当任务需要判断、建立或补齐一个测试表面的运行支撑时，读取[轻量六段式 Harness](references/harness-readiness.md)。Harness 是 `Prepare`、`Start`、`Drive`、`Observe`、`Preserve`、`Restore` 六段能力，不是六个脚本或新的通用框架；同一项目 Runner 可以覆盖多段，纯函数或当前目标不涉及的段可以明确不适用。

先复用项目已有测试框架、Runner、驱动、验证器和证据位置。只有当前测试目标需要且既有入口不能满足时，才在授权范围内补最小测试资产；不为统一形式新增服务、目录、注册中心或平行框架。框架或文件存在、健康检查通过、页面打开、零退出码或模型自述不能单独证明 Harness 可用。

构造或修复后的交接结果使用：

- `verified`：至少实际驱动一条目标路径，独立观察成立，原始证据在清理后仍可回读；
- `draft`：资产已形成，但存在未实际验证的段、环境或证据边界，列出恢复动作；
- `blocked`：授权、隔离、权威来源或安全前置使当前不能继续，列出具体原因和恢复入口。

上述结果只描述本次交接；临时驱动获准实测不要求先长期采纳，试验 `verified` 也不自动成为项目长期入口。`draft` 只是本次交接结果，不是项目长期状态。项目配置只使用共享参考中的六个 Harness 状态。产品行为违反已确认规则时，保留失败证据并交给 Finding／缺陷流程；只要 Harness 能真实驱动、观察、留证和恢复，产品失败本身不使 Harness 变成草案。不得为获得 `verified` 修改被测产品代码、放宽独立预期或把失败值改成通过值。

来自 Setup 的交接沿用已查清的目标路径、预期来源、表面、现有入口、环境、证据位置、隔离恢复边界、写入／执行／采纳授权和预算，不重新启动初始化问卷。按实际对象进入下述生成或维护分支；现有入口和适用证据足够时直接交回，不为交接重复生成或运行。

只补足当前缺口，用一条最小路径验证。沿用项目时间／尝试预算；没有时在执行前声明有界范围。就绪检查发现无法安全恢复的环境、权限或隔离故障时，保留原始输出并返回；无新事实不重复同一失败命令，不扩展为完整用例或全量流水线。只获准写代码时交付可检查的草案及未验证项，不借验证要求启动产品。

返回实际资产及变化、六段入口／缺口、目标版本、已执行／未执行动作、原始观察与证据、清理／残留和恢复条件，分别说明 Harness 能力、产品结果及采纳依据。维护仍使用 `clean / changed / blocked`，不与生成标签混写。只交回证据，由 Setup 回读并更新配置；本专项不并发改写 project.md 或 TCO。构造自测不得声称已经完成完整 Loop 的独立盲测。

### 生成项目产品验证器

当项目需要可持续验证真实产品行为且用户授权生成验证资产时，先访谈仓库而不是用户：从 README、启动脚本、配置、现有测试和运行代码确认用户可触达表面、启动与就绪方式、可编程驱动方式、可观察证据、实例隔离和清理方式。只有无法从材料查清的事实才询问用户。

优先复用既有 Playwright、API、CLI、组件或集成 harness；确实没有时按上述选型规则选择最小驱动方式，不默认引入框架。生成物可以是项目本地验证说明、脚本或 Skill，至少包含：

- 启动命令、就绪判定和 teardown；
- 判断实例是否值得继续的只读 doctor；
- 真实用户路径及稳定操作句柄；
- 需要捕获的动作、结果状态、日志和副作用证据；
- 共享数据、端口、凭据和会话的隔离边界；
- 失败证据保留位置和只清理本次实例的清理规则。

交付前至少实际驱动一条已映射用户路径，确认原始证据在清理后仍存在。未实测的生成物只能标注为草案，并列出启动、驱动、采证和清理的未验证项；不得称为可用验证器。无法安全隔离共享环境时拒绝双实例驱动，不破坏用户会话。

用户要求“生成验证器／验证资产”时，本节是直达路径：先读取本 Skill，再按实际表面读取接口或 E2E 专项；不要改走用例设计、终稿自校或项目完整建图。用户说“真实产品”时，接口服务也属于真实产品表面；只有跨页面／多服务旅程才必须读取 E2E 专项。只读或禁止启动时，当前交付物就是带未验证清单的草案，不停留在路由声明。

### 维护既有项目产品验证器

用户要求维护、修复或复核项目验证器时，本节是直达路径：先读取本 Skill，再确认权威验证资产和目标功能范围确实存在。用户提到实际异常、失败响应或 500 时，先按本节完成验证器维护分类；确需进一步定位原因才读取 `investigating-findings`。找不到对象时结果为 `blocked`，说明需要先确认或生成验证器；不得创建替身后冒充维护既有资产。

维护轮只修改验证说明、脚本、夹具或测试资产，不改被测产品代码。每个受影响功能先做两次对账：源码／文档说明的预期行为，与实际驱动观察到的行为。首次驱动、冷启动会话和异常后先运行只读 doctor；doctor 未通过时不进入用户路径驱动，先报告环境阻塞证据。

驱动产生的原始证据先保存到清理后仍存在的位置，再只清理本次实例拥有的数据、端口和会话；清理失败保留失败证据并说明残留和安全处理方式。结果只报告为 `clean`（核对后无需修改）、`changed`（验证资产已修改并复验）或 `blocked`（无法安全继续）。

源理解与实际行为不一致时，先分类再行动：

- **文档漂移：** 源行为有效，验证说明或映射过期，修正验证资产；
- **验证器缺口：** 验证脚本、夹具或检查漏掉真实行为，补验证资产并复验；
- **产品缺陷：** 真实产品行为违反已确认规则，记录复现证据、影响和交接目标，不顺手修产品。

## 4. 交付与来源

沿用[共享表达](../test-privateer/references/artifact-routing.md#面向读者的测试表达)。说明本轮选择、准备缺口、已有产物、未覆盖边界和下一动作；设计、编写、接入与实际运行分别报告，结论以本轮证据为限。

项目局部产物写回对应测试文档，仅长期反馈保护摘要升级到 TCO。需要汇总信心时交给 assessing-test-confidence。

**完成条件：** 方法与目标错误匹配，接手者可进入专项；没有将设计清楚或脚本存在写成已经运行成功。

- [Google 测试总览](https://abseil.io/resources/swe-book/html/ch11.html)：按反馈价值和成本取舍。
- [Ham Vocke 的测试组合](https://martinfowler.com/articles/practical-test-pyramid.html)：保留不同范围的互补证据，不设数量比例。
- [Hypothesis 状态测试](https://hypothesis.readthedocs.io/en/latest/stateful.html)：性质及模型需有依据，失败序列保留复现条件。
