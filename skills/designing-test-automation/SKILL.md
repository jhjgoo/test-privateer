# 设计测试自动化

自动化提供持续反馈。选择能发现目标错误、保留真实边界的最小测试组合，不以覆盖率或固定比例代替价值。

## 1. 接收任务

沿用业务目标、选中行为和有效规则。项目任务读取相关测试资产；独立任务不要求 TCO 或 Spec。

先核对预期依据、数据与环境控制、失败定位和维护成本。规则未定只暂停相关精确断言；已选合理范围时直接进入专项，不另写策略报告。

**完成条件：** 能说明要保护什么、怎样判断正确，以及哪些缺口会影响选择。

## 2. 按所需证据选择方法

| 要证明的行为或边界 | 入口 |
| --- | --- |
| 稳定规则、计算、转换或局部状态 | writing-unit-tests；保留单元符号和 TDD 职责 |
| 接口请求、身份与业务效果 | [writing-api-tests](../writing-api-tests/SKILL.md) |
| 真实依赖、消息兼容或组件协作 | 按需读[集成与契约](references/integration-contract-testing.md) |
| 局部交互、反馈与恢复 | 按需读[组件测试](references/component-testing.md) |
| 贯穿真实系统的业务旅程 | [writing-e2e-tests](../writing-e2e-tests/SKILL.md) |

API／页面是操作入口，单元／集成／系统是测试范围，TDD 是开发节奏。分别说明选择；HTTP 不自动等于集成，浏览器不自动等于 E2E。以接口合同为主用接口专项，以跨层旅程为主用 E2E 专项，必要时读取另一方法，不重复执行同一检查。

同一行为按不同错误安排互补检查。规则的广泛输入可在较小范围覆盖；真实接线仍需集成证据。替换目标依赖后，结论仅覆盖替身行为。

按风险选择分区、边界、状态迁移和失败路径。有可靠不变量或独立参考模型时再补属性／状态序列测试，保留可复现反例。随机次数不是判定依据。

**完成条件：** 每种检查有独特反馈价值，真实与替换边界、未覆盖项可说明。

## 3. 接到当前交付

**只要求设计：** 交付选中行为、方法理由、准备、动作、预期来源、观察位置和未决项，不安装或运行。

**要求编写或验证：** 将已确认目标、合同、环境和执行许可交给专项。已有合适框架优先复用；无框架按项目技术栈选择最小实现，纯接口不强制浏览器。官方 e2e 的获取与版本操作由 E2E 专项按需承接。

集成／组件任务按所选参考继续，不为进入实现再绕回方法入口。执行结果沿用 running-test-sessions 的记录约定；已运行的证据直接交回，不因交接再跑一次。

## 4. 交付与来源

沿用[共享表达](../test-privateer/references/artifact-routing.md#面向读者的测试表达)。说明本轮选择、准备缺口、已有产物、未覆盖边界和下一动作；设计、编写、接入与实际运行分别报告，结论以本轮证据为限。

项目局部产物写回对应测试文档，仅长期反馈保护摘要升级到 TCO。需要汇总信心时交给 assessing-test-confidence。

**完成条件：** 方法与目标错误匹配，接手者可进入专项；没有将设计清楚或脚本存在写成已经运行成功。

- [Google 测试总览](https://abseil.io/resources/swe-book/html/ch11.html)：按反馈价值和成本取舍。
- [Ham Vocke 的测试组合](https://martinfowler.com/articles/practical-test-pyramid.html)：保留不同范围的互补证据，不设数量比例。
- [Hypothesis 状态测试](https://hypothesis.readthedocs.io/en/latest/stateful.html)：性质及模型需有依据，失败序列保留复现条件。
