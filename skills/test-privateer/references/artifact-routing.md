# 测试产物的归属与维护

读取项目证据与维护项目文档分别判断。独立任务在对话或指定位置交付；相关 Spec、代码和测试仍可作依据。只维护当前请求涉及的内容。

## 测试术语

面向用户的正文和标题使用中文主词；英文保留为首次解释的别名、Skill 路由名、文件路径、标准缩写或代码标识。以下译名是本包唯一约定：

| 中文主词 | 英文别名或说明 |
| --- | --- |
| 阶段交接 | `handoff` |
| 判定依据 | `oracle` |
| 测试条件 | `TCON` |
| 测试发现 | `Finding`；观察或审查中值得记录、核实的问题，注明对象和证据 |
| 测试用例 | `Case` |
| 探索章程 | `charter` |
| 探查 | `probe` |
| 测试夹具 | `fixture` |
| 当前基线 | `baseline` |
| 可替换边界 | `seam` |
| 规格说明 | `Spec` |

`PRD`、`TCO`、`SFDIPOT`、`MFQ`、`PPDCS` 和 `Given/When/Then` 保留原名；首次出现时补充中文含义。Skill 名称、编号、命令、接口字段和文件名保持原样，不做机械翻译。

观察记录实际见到什么，审查发现指出材料的问题；缺陷判断说明违背了什么适用要求及其证据，原因判断说明机制、支持与反证及解释范围。发现不自动等于缺陷，缺陷不自动说明原因已查明。计划内尚未实现的目标是实施状态；需求矛盾和已有功能异常仍可调查。推断不能写成运行观察。

## 项目地图与需求资产

已选择项目任务时，先收集业务、系统、有效 Spec 和已有测试资料，使用 mapping-project-test-space 建立或补齐唯一 TCO，再开展变化分析。地图可以是有依据的草案，但须足以支持当前影响判断；无关未知留作项目待办，不要求先写完项目百科。独立任务可参考项目证据而不新建地图。仅文件存在不能证明上下文充分。

每个项目维护唯一 `testing/TCO.md`，按 mapping-project-test-space 的模板汇总项目概览、业务与系统地图、资料与证据、覆盖、长期风险、资源、需求索引和项目待办。它不收录某次需求的完整过程。

每个需求默认分开维护测试分析与用例，开始设计才创建用例文件。详细上下文、证据或模型妨碍主文档阅读时按需拆依据；短小且有助判断的模型留在分析。原始资料直接链接，不整篇复制。

## 跨 Skill 阶段交接（handoff）

主入口或上层 Skill 调用专项 Skill 时，专项 Skill 交回以下最小阶段交接；直接用户调用则交付自身产物后停止，不擅自扩展下一专题：

| 字段 | 内容 |
| --- | --- |
| 当前阶段 | 路径准备／项目地图／变化分析／风险聚焦／建模／用例设计／自校／执行／调查／信心 |
| 已完成 | 本轮实际完成的对象、范围、编号和产物 |
| 未完成 | 待设计、待调查、阻塞、排除及其影响 |
| 证据与产物 | 来源、版本、文件路径、链接和执行限制 |
| 下一动作 | 一个具体对象、动作和预期产物 |
| 执行许可 | 未授权／已授权未开始／执行中／已完成 |

上层收到阶段交接后更新路线状态并决定下一阶段；没有交接证据不能把局部内容包装成整条链路完成。

| 用途 | 文件名 | 模板位置 |
| --- | --- | --- |
| 测试分析 | `<前缀>-test-analysis.md` | analyzing-change-for-testing/references/test-analysis-template.md |
| 测试用例与执行记录 | `<前缀>-test-cases.md` | designing-test-experiments/references/test-cases-template.md |
| 详细依据与模型（按需） | `<前缀>-test-basis.md` | analyzing-change-for-testing/references/test-basis-template.md |

前缀使用已有需求标识＋短名；无稳定标识时使用首次建立日期＋短名。允许中文，同一需求共用稳定前缀，不随更新改日期或追加“最新版”。已有明确 Spec／需求目录时沿用；否则放 `testing/requirements/<前缀>/`，不创建开发 Spec。创建前查找旧文档并核对需求来源，不能仅凭同名覆盖。

迁移旧资产按下述编号规则保留身份映射、来源与原始执行证据并修正链接。旧入口可留简短跳转说明；迁移档案明确为历史，不能继续指导当前执行。

## 统一编号与追溯

编号识别对象，业务分类、分析方法、成熟度和执行状态另列。只为需要持续追溯的对象编号；临时问题、分组标题、规则说明和模型内节点使用名称或来源位置，不另造编号体系。已有需求、缺陷或测试平台的权威编号继续引用。

| 对象 | 新编号 | 定义位置 |
| --- | --- | --- |
| 项目覆盖节点 | `N-001` | 项目 TCO 的覆盖地图 |
| 风险 | `R-001` | 需求风险清单；长期或共享风险在 TCO |
| 测试项 | `T-001` | 主分析的测试项清单；独立分析在指定产物或当前交付中 |
| 具体用例／测试任务／探索章程 | `C-001` | 用例文件或当前独立交付；已有工具编号沿用 |

项目 TCO 与每个需求各有编号范围；同一需求的分析、依据和用例文件共享一个范围。同类型从001递增，不按章节、模块或Skill重开序列。跨范围引用带所属文件及完整编号、短名称，不能仅凭同号认作同一对象。

先读取权威清单并复用已有编号，新增编号由负责合成产物的Agent统一分配；子Agent复用给定编号，新内容交回组装者定号。只排序、改名、改分类或补细节不改号；撤回编号不复用。编号空缺本身不是内容遗漏，拆分时新增未占用编号，不顺延其他对象。同一对象只有一个定义位置，其他文档与图表引用；编号正确还需核对所指内容是否相符。

测试项从候选细化为TCON时，行为与边界未变就沿用T编号，并写明当前是候选还是已具备模型来源的测试条件；编号不代表成熟度。拆分时为独立行为分配新T编号，旧条目标明“已拆分至……”；合并时保留一个存续编号并记录其他旧号去向；被替代项退出当前待设计或待执行集合。用例使用独立C编号并明确关联T，不要求数字对应或一对一。

引用写完整编号并附可识别的短名；逐项追溯列明确列出实际目标，区间只用于概览，不能替代定义或逐项映射。已有稿的前缀省略先依上下文核实，不能机械判缺号。模型与脑图复用测试项编号；局部模型元素以名称或具体行定位，不再生成另一套测试条件编号。

生成或更新用例后，同步主分析中对应T的用例关联与安排，保留未设计、待确认和排除项的理由；不能一边声称已转换，一边保留旧的“未设计”。依据文件引用权威清单，不复制维护第二份测试项或风险状态。

旧资产优先保留已有权威ID。确需统一当前可维护资产时，Agent先确认同一对象的映射，再在有权修改的文件集合中同步引用、记录旧号去向；范围外引用、历史执行记录和外部系统编号保持原样，通过映射连接。换号不改变内容、覆盖、规则和证据结论，不做无关项目的批量迁移。

## 更新纪律

- 按相关性读取需求、有效历史 Spec、代码与已有测试；核对版本和适用范围。文件名或测试名称不证明覆盖。
- 分析维护当前规则、风险、全部已识别测试点、有效未知和行动；用例文件维护设计与执行；依据文件保留必要模型、详细事实及来源。
- 新证据原地修正对应结论；已解决问题和完成动作退出当前待办，撤回规则退出有效预期。不追加整轮问答和重复分析。
- 新规则与 PRD／Spec 冲突时注明确认来源与差异；回写超出授权则列行动。原始执行记录保留，必要时追加解释修正。
- 仅长期或跨需求认知升级到 TCO。局部用例和调查过程留在需求资产，交付可点击路径及当前下一步。

## 风险单一归属

生命周期由 analyzing-product-risks 定义。局部风险在需求分析维护；共享机制或跨需求风险在 TCO 维护，需求引用并记录本次贡献，不复制独立状态。升级跨编号范围时在项目清单分配未占用的风险编号，保留原范围＋旧编号到新定义的映射并同步当前引用；原始证据仍保留旧号。

单项用例通过只支持实际覆盖的版本与场景，不自动关闭项目风险。风险行记录最新判断和证据链接；原始证据留在用例记录或来源处。

**完成条件：** 编号范围与权威定义明确，引用和用例关联已随修改同步；TCO 唯一；需求分析与用例分工清楚、依据按需拆分；已识别测试点完整可见且有安排；规则、风险与行动反映当前有效认知，证据和编号可追溯。
