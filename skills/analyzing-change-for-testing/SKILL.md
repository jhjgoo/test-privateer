# 分析变化以支持测试

测试分析把变化转成可检查的产品行为、测试重点和证据需求，不替开发发明规则。

## 前置条件

读取 `heuristic-testing/references/artifact-routing.md`、项目 TCO、当前变化依据和已有 Spec 测试文档。

项目 TCO 不存在、失真或不足以判断影响时，先使用 `mapping-project-test-space`。不要用当前变化临时拼一份项目地图。

先确定变化处于研发前、开发中、可运行还是已执行。阶段无法从证据确定，且会改变测试对象、oracle 或产物性质时，先询问用户。

- 研发前或开发中：分析目标行为、设计风险、待实现的可验证结果和测试条件。
- 可运行：分析变化影响和测试准备，不把目标行为与当前实现的差异直接写成 Finding。
- 已执行：只有实际观察与 oracle 不一致时才形成 Finding。

## 分析变化

### 1. 明确变化目的

用 `clarifying-test-basis` 确认用户任务、现状问题、产品承诺、成功信号及真实业务链。只问会改变范围、模型、oracle 或测试重点的问题。

### 2. 扫描增量影响

用 `scanning-product-with-sfdipot` 比较变化前后。追到上游触发、下游消费者、共享数据、状态、失败与恢复，不停在 PRD 页面。只带走会改变测试范围、重点或设计的增量影响。

### 3. 组织测试空间

用 `analyzing-test-space-with-mfq` 组织本次变化的能力、交互、质量特性和具体候选测试点。每项追溯到项目 TCO 覆盖节点或明确标为新节点。

### 4. 选择测试重点

用 `analyzing-product-risks` 比较产品价值落空与负面伤害，选择本轮高价值测试点。风险只负责选择范围、顺序和深度，不代替模型或测试条件。

### 5. 对复杂行为建模

流程、规则、数据、组合或状态复杂时，使用 `modeling-tests-with-ppdcs` 形成实际模型和 TCON；简单行为直接形成 TCON。变化包含多个独立业务结果时分别建模，不把整份 PRD 或 Change 当成一个模型边界。

以下任一项不同就拆分 TCON：前置状态、角色或权限、数据分区或边界、动作或刺激、观察位置、oracle、关联风险、测试层级或环境。每个 TCON 必须追溯到路径、规则、分区、组合或迁移。

### 6. 停在请求边界

测试分析交付排好优先级的 TCON 和下一轮建议后停止。只有用户要求测试设计、测试用例或执行准备时，才将本轮高价值 TCON 交给 `designing-test-experiments`。其余 TCON 保留为候选，不批量展开。

## 分类结论

区分以下内容：

- **需求问题：** 目标行为、规则或成功标准不清、冲突或不可验证；
- **设计风险：** 即使按当前设计实现，仍可能无法兑现价值或造成伤害；
- **待实现的可验证结果：** 实现完成后必须观察到的行为、约束或证据。说明什么必须成立，不指定开发怎样实现；只有已确认约束规定了实现方式时才保留该方式；
- **测试条件：** 后续需要覆盖的场景、模型元素或 TCON；
- **Finding：** 对可运行目标取得的观察与 oracle 不一致。

可验证结果写清触发条件、动作和可观察结果。示例：已确认同一企业只能绑定一个租户时，写“两个租户同时保存同一产品和企业编码，只能一个成功，失败方原配置不变”，而非指定数据库约束或事务方案。实现方式本身属于已确认约束时，保留来源并验证该约束。

没有对可运行目标取得观察，不得形成产品 Finding。

## 阶段判定

研发前或开发中，只有同时满足以下条件，才写“测试分析足以支持实施”：

- 变化目的和业务结果明确；
- 业务链、系统、接口、数据、状态和时间影响明确；
- 高价值行为有实际模型，或有不建模的明确理由；
- 高价值 TCON 可追溯，且足以指导后续测试设计；尚无可运行实现不影响完成测试分析；
- 实施计划无需发明产品行为、业务规则、边界或 oracle。

可运行阶段改为判断测试对象、环境、oracle 和高价值测试是否足以进入执行，不再使用实施前措辞。已执行阶段使用 `assessing-test-confidence` 判断证据和残余风险。

条件不足时列出阻塞未知、证据来源、应答角色及其影响。不要创建开发计划、ticket、分支或提交，也不要调用开发 Skill。

## 写入与交付

测试文档先让测试人员看懂下一步：

1. 变化理解和证据边界；
2. 按优先级排列的测试重点、理由、测试方法和状态；
3. 会改变测试方向的未知；
4. 当前阶段判定和下一步。

面向测试人员交付。先写业务角色、产品页面、业务对象、测试动作和可观察结果。正文用“预期结果”或“判断依据”表达 oracle；必要术语首次出现说明具体含义，例如“系统被诱导访问内网地址（SSRF）”。代码标识、内部字段和技术钩子放在补充取证中。

SFDIPOT、MFQ 和 PPDCS 是分析工具，不是报告目录。主报告按“测试重点、为什么重要、怎么测、预期看到什么、当前还缺什么”组织。方法缩写、模型编号、测试条件编号和完整追溯关系只放附录；正文不得要求读者沿多层 ID 才能理解测试。同一关注只在首次出现时完整说明，后续只补充新增信息。

只有跨 Spec 或长期有效的认知才升级到 TCO。

**完成条件：** 当前变化已从项目地图追到具体测试重点和 TCON；产物停在用户要求的阶段；判定符合变化生命周期；局部内容没有污染 TCO；测试人员能直接看出先测什么、为什么、还缺什么和下一步。
