# 维护错题本与项目规则

把已发生的错误整理成下一次能改变行动的教训，再判断哪些应成为项目规则。每条教训连接失败证据、适用范围、纠正动作与验证；规则晋升和问题修复分别记录。

只调查当前异常时使用 `investigating-findings`，只质检修复方案时使用 `checking-solutions`。本 Skill 在用户要求复盘、维护或提炼规则时进入，不给每次修复附加一套项目文档。

## 确定维护范围

读取项目规则、已有错题本、规范与相关记录，沿用权威位置、编号、统计口径和审查范围。明确本轮是记录一个错误、整理一段历史还是提炼长期规则，以及允许修改的文件。已授权维护时直接完成可确定的编辑；只审查时交付可定位的建议。

没有特殊约定或既有权威位置时，在项目根目录用 `LESSONS.md` 保存教训，将提炼出的长期规则直接写入根目录 `AGENTS.md`，保留其中其他内容。规则写明适用条件、动作与检查方法，原始事故和长证据仍留在错题本。已有独立规范时继续沿用，AGENTS.md 或等价入口用有触发条件的短指针连接它；规则已在 AGENTS.md 时无需另建规则文件或自指链接。无需采用特定宿主或 OpenSpec。创建模板、整理条目或添加入口不等于建立自动执行钩子；定时任务、外部 Issue 与全局配置仍需对应授权。

## 从证据形成教训

按本轮范围读取实际变更、报告与执行结果，优先找修后返工、过早完成和验证不足。记录起止版本、过滤条件及未读部分；连续审查标记只能推进到完整覆盖的位置，稀疏审查单列范围。

事件材料只有口头或任务描述时，不虚构文件名、错误行号、工具版本和运行日志；先以该描述作为来源，保留字段、版本、原始错误和原始包未提供的边界。除非用户明确要求在当前回复维护文档，交付可粘贴的教训建议和位置；用户授权编辑时才写入权威位置。

先区分观察、原因假设、已支持机制和未知，再写“在什么条件下应怎样行动，在哪里检查”。原因不明也可以记录止损与取证动作；重试通过、补丁合并或文档新增不能替代相应验证。成功纠正案例可作为“正确做法”保留直接证据。

按失败机制和适用范围匹配旧条目：同一事件的多次补丁、转述和重复审查合并证据，不机械增加发生次数；相似现象但原因不同保持分开或关联待查。统计独立事件与被审查日期时分别标明口径，后续能从记录重新算出次数。

## 提炼并维护规则

需要模板、晋升判据或整理已有账本时，读取 [维护指南](references/maintenance-guide.md)。判断候选规则是否有稳定范围、当前依据和能捕获原错误的检查动作，同时检查相邻正常行为是否被误限制。

按失败机制先选择环境改进方向：

- **机械错误：** 能由命令输出或文件结构确定的错误，优先提出或落地最小确定性检查、钩子、CI 或测试；无法落地时保留可运行建议和未实施状态。
- **判断错误：** 因标准、取舍或专业判断失误造成的问题，进入项目规则或标准，并写清适用条件和人工检查方式。
- **导航／信息缺口：** 因入口难找、权威位置不清或证据不可达造成的问题，补入口指针、权威位置或取证动作，不重复堆行为提醒。
- **无修改授权：** 需要 CI、钩子或全局配置的改进超出本轮授权时，交付具体修改建议、预期检查效果和未实施状态，不越权修改。

优先采用项目已有晋升标准。未定义时，可将“在三个不同日期发现独立复发”作为明确标注的候选标准，不默认三份记录等于三次错误。已确认的高后果约束可由单次事件形成规则，不等待事故重演；低价值、偶发环境错误或原因未明的发现可继续留作教训。

与旧规范冲突时先查主体、条件、时点与依据，能依据现有材料消解的直接修正；需要新的产品决定才留待选择。将规则放到已有权威规范，教训保留证据、晋升日期和目标指针，入口写明何时读取。失效规则注明替代依据与位置，去重时保留历史引用。既有规则后再次犯错，更新原条目并查入口、表达、测试或执行机制，不靠再加一句同义规则结束。

## 核对与交付

复读条目、规则及入口，检查证据能定位、次数可重算、范围未扩大、链接有效、旧引用有去向。每条规则能回答“何时适用、做什么、怎样发现违背”；拟议检查标为未运行，实际验证注明版本、环境、结果与限制。

交付新增／合并／晋升／失效的条目、实际文件或建议位置、仍未修复的问题与下一取证动作。项目规则写好了，只支持规则维护完成；防止复发的效果需要后续行为证据。

**完成条件：** 本轮覆盖范围与缺口可见；每条教训有证据、边界、行动和真实状态；每条规则有权威位置与检查方法；关联入口及旧引用已核对，声明不超过实际修改和验证。

方法来源及本包适配区别见 [来源说明](references/sources.md)，需要追溯方法时读取；日常执行无需联网。
