# 运行测试闭环

Test Loop 是编排层，不是新的测试方法。它把已有测试专项接成一个有界、可暂停、可恢复的轮次；方法、用例格式、执行证据和信心判定仍由对应专项维护。Loop **不复制**专项方法，也**不修改被测产品代码**。

## 何时使用

用户明确要求“从分析到执行再到报告”“完整测试闭环”或直接调用本 Skill 时使用。只要求一次接口检查、单条用例、单层自动化、单次执行或报告汇总时，不进入完整 Loop。

## 启动契约

在推进产品执行前，先从用户请求、项目规则和可选 `.test-privateer/project.md` 固定：

- 测试对象、目标版本或快照、目标和范围；
- 允许的环境、账号、数据和测试资产修改；
- 禁止动作；
- 时间、费用、运行次数或其他预算；
- 可观察的退出条件；
- 当前或新建的 Run ID。

跨多个阶段、会话、分支、人工检查点或审计时，使用 `testing/runs/<run-id>/run.md`。已有可恢复轮次先恢复原 Run ID；不能为同一工作创建第二套状态。**项目配置不是授权**，只是事实和来源索引；没有配置时继续调查，**缺少配置不阻塞**。

如果缺口只影响部分阶段，先继续不依赖它的工作，并标明受阻范围。只有会改变测试对象、执行安全或判定依据的缺口才暂停并询问。新增环境、凭据、费用、共享数据破坏或生产访问必须重新确认。

## 阶段状态

按当前资产和风险推进，不机械执行全套阶段：

```text
恢复轮次
→ 固定契约
→ 项目与变化认识
→ 风险、模型与用例
→ 测试资产自校
→ 建立盲测任务包并启动冷启动子代理
→ 盲测发现并封存结果
→ 选择并执行知情回归
→ 调查 Finding
→ 选择并执行回归
→ 评估测试信心
→ 完成／暂停／受阻／取消
```

每次只处理当前缺口。进入一个阶段前，先从当前 `run.md`、权威资产和实际项目状态固定本阶段的：

- 输入指针；
- 要关闭的具体缺口；
- 预期产生或更新的权威产物；
- 能证明阶段完成的证据；
- 证据成立后的下一动作。

`run.md` 只保存这些状态和指针，不复制产物正文。只有权威产物实际存在、仍适用于当前版本，且完成证据支持本阶段目标时才能推进。读取过 Skill、写过计划、出现“已完成”标题或模型自述都不是推进证据。

专项 Skill 按当前阶段即时加载。先读取当前阶段需要的入口；只有其 handoff 或新证据把下一阶段变成当前动作时，才读取下一专项。不得为了预演完整流程一次性读取所有候选方法、框架或参考；已复用或跳过的阶段不加载其专项，最终信心评估也等到执行与调查边界稳定后再加载。

阶段交接用 `handoff` 传递：当前阶段、已完成、未完成、证据与产物、阻塞、下一动作、执行许可。已有适用产物时先核对后复用；与当前目标无关或已被充分覆盖的阶段跳过，并记录理由。多个分支只返回隔离证据，由 **单一合成者** 更新共享轮次和资产。

继续或恢复时先读取 `run.md` 指向的实际资产并核对当前状态，不用旧聊天、上次总结或阶段自述代替。记录与实际文件冲突时，以可核验状态定位缺口，保留冲突，不直接推进。

只有新证据改变范围、风险、模型、用例、执行路径或结论时才回边。回到拥有该问题的最近责任阶段：分析问题回分析，用例问题回设计，驱动问题回测试资产，执行证据问题回执行，报告归纳问题回信心评估。保留未受影响的完成产物、证据和 Run ID；将受影响资产标为需要复核，修正后只重验受影响路径。每次回边说明触发证据、责任阶段、受影响对象和下一次检查；重复重跑必须有新的区分目的。

## 冷启动盲测子代理

完整 Loop 进入测试发现或执行前，必须启动至少一个新的冷启动盲测子代理。普通单层请求继续直达对应专项，不受此门槛约束。

盲测子代理使用独立会话和自包含任务包，从当前项目重新形成质量判断。可以让它独立读取项目规则、用户可观察契约、项目测试配置、当前版本和获准测试入口；不得把开发聊天、实现理由、修复假设、实现 diff、开发自测结论、既有 Finding 结果、预期缺陷或评审 rubric 传入。为避免重复，可以提供不含结果的覆盖排除项和本轮分配的质量视角，但不能披露上一轮结论、原因解释或推理正文。

冷启动隔离的是本次开发叙事和既有结果，不是测试 Agent 的正常能力。子代理应按任务需要使用稳定操作基线，包括宿主固定规则、全局 RTK、全局／项目级 Skill、项目 `AGENTS.md`／`CLAUDE.md`、`.test-privateer/project.md` 和获准 CLI；这些能力不因全局安装、自动注入或父级继承而构成污染。

审计候选实际收到的任务特定输入、读取的 Skill 和项目规则、工具轨迹及可用记忆。发现未预先列出的稳定操作基线时，补记其名称、来源和可取得的版本或哈希后继续；不要求复制不可取得的完整系统提示词。只有它包含开发聊天、实现理由、修复假设、diff、开发自测、既有 Finding 结果、预期缺陷、rubric 或携带这些内容的记忆时，才先隔离；无法隔离或审计时，该 wave 无效并受阻或在干净会话重跑。

每个盲测 wave 在当前 Run 中记录 wave ID、子代理会话／任务 ID、模型与宿主、目标版本、质量视角、稳定操作基线与项目输入、明确未披露的开发材料、任务包哈希、覆盖指纹、隔离输出和证据指针。实际调度和候选输入是冷启动证据；主 Agent 或子代理声称“已独立测试”不算。

子代理只返回隔离 handoff，状态使用 `PASS`、`ISSUES` 或 `BLOCKED`，并附实际动作／命令、原始输出或产品状态、证据路径、已覆盖和未执行范围。没有实际执行证据的 Finding 只能保留为待验证假设，不能进入已证实问题。子代理不得更新共享 `run.md`、权威测试资产、公共报告或产品代码；仍由单一合成者复核、去重和更新当前 Run。

盲测结果和输入边界封存后，才进入知情回归。知情回归 handoff 必须显式携带当前 Run ID、封存 wave ID、目标版本和封存证据哈希／指针；开始前核对它们一致。新子代理会话不产生新的 Run ID，也不得创建第二套 `run.md`。不一致时先标记受阻，不执行或写入共享资产。

知情回归可以使用实现 diff、开发自测、已有用例和历史 Finding 补齐变更影响，但不得把这些材料追加给原盲测 Agent，也不得复用同一子代理上下文冒充第二个独立视角。由新子代理执行时仍只写隔离 handoff，沿用单一合成者更新共享 Run 的规则；需要新的独立判断时启动新的子代理。

普通完整 Loop 至少一个盲测子代理。高影响、未知面大或发布关键时，在预算允许范围内把业务、权限、安全、异常恢复、数据或交互等互不重叠视角分给 2～4 个子代理；每个 brief 自包含、输出隔离。子代理缺席或无有效证据形成覆盖缺口，不计为通过。

宿主不能创建新的子代理会话、不能排除开发会话或任务特定开发材料，或只能在当前上下文中扮演测试角色时，完整 Loop 停在盲测门槛并标记受阻。无法导出完整宿主基线，或新会话正常使用全局／项目规则、Skill 和 CLI，本身不是受阻理由。只有用户明确接受降级后才能继续；Run 记录降级授权和原因，最终报告必须写明“独立盲测未完成”，不能声称完整 Loop 已满足盲测要求。

### 防止重复 wave

每项执行使用以下覆盖指纹：

```text
测试表面 + 身份／数据／初始状态 + 动作／路径 + Oracle + 故障或质量视角
```

新 wave 至少改变一个维度，或者明确属于修复回归、稳定性调查、环境恢复或新版本对照。完全相同且没有复验目的的执行直接跳过；选择新的风险切片，或在没有新增证据价值时停止。允许的相同复验必须说明要区分什么，并保留前后两次证据，不能冒充新增覆盖。

## 路由与执行边界

按风险和观察位置选择最小充分的专项，不为“完整”强制运行所有测试层级：

- 纯接口行为 → `writing-api-tests`；
- 跨页面或服务旅程 → `writing-e2e-tests`；
- 视觉、交互、无障碍或任务可用性 → `reviewing-ui-ux`，取得真实渲染和操作证据；
- 自动化组合、项目验证器或形式／性质检查 → `designing-test-automation`；
- Agent 评测 → 通用 `agent-eval` 加项目已选入口；只有项目明确选择对应框架时才加载框架专项；
- 失败原因 → `investigating-findings`；
- 回归保护 → `selecting-regression-tests`；
- 当前轮次信心 → `assessing-test-confidence`；
- 获准的实际运行 → `running-test-sessions`。

Loop 不安装、替换或擅自选择测试框架，不因某个专项 Skill 存在而改变项目约定。项目使用自有框架时沿用项目入口。项目明确选择的框架专项不可用时，报告具体缺口或继续使用通用能力，不静默换框架。

Loop 只修改获准的测试代码、夹具、驱动、验证器、测试分析、用例、执行记录和报告；被测产品代码保持只读。真实产品行为违反已确认规则时，保留复现证据并交给调查和交接，不顺手修产品。验证器或测试资产过时，可以在授权范围内修正并复验。

每次失败先归类为产品行为、测试资产、环境／身份、工具、依据不足或未知。工具失败不能写成产品通过；首次失败后重试通过也必须保留稳定性风险和两次证据。

## 人工检查点、暂停与恢复

人工检查点、冷启动恢复点和决策日志沿用 `running-test-sessions`，并共享当前 Run ID。只有审批、凭据、第三方后台、环境操作或人工观察会阻塞下一步时才建立检查点；结果未回填前不推进依赖它的结论。

达到预算、退出条件、安全边界、人工检查点或无法改变结论时停止。状态使用轮次契约中的“已暂停”“受阻”或“已完成”，不能用“通过”代替轮次状态。暂停时完成当前原子步骤，交付恢复动作；恢复时继承已验证工作，不重做已完成测试。已完成或已取消的轮次不改回执行中，后续新版本、新环境或新的产品执行创建新的 Run ID。

## 交付信心报告

结束时调用 `assessing-test-confidence`，只汇总当前 Run ID、目标版本、环境和当前有效证据。报告至少说明：

- 实际执行范围和未执行范围；
- 直接、间接、矛盾证据与未知；
- 测试资产发生的变化；
- 产品缺陷、测试资产问题和环境阻塞的区分；
- 残余风险、证据限制和下一项补证。

Loop 完成、退出码为零、用例通过率或报告生成成功，都不能单独支持“产品质量良好”“可以发布”或风险已接受。发布和风险接受由有权负责人决定。

**完成条件：** 当前 Run ID 与授权边界清楚；阶段交接和回边有依据；实际动作、证据和未执行范围可追溯；轮次状态、测试判定和测试信心没有混用；最终交付没有把局部通过扩大成整体结论。
