# Design

## Context

参见 [proposal.md](proposal.md) 的问题说明。当前 Loop 已有稳定 Run ID、阶段产物门禁、单一合成者、定向返工和“重复重跑必须有新区分目的”，但没有规定测试必须由独立冷启动 Agent 执行，也没有留下证明上下文隔离的输入清单。

pstack 的可复用模式是：worker brief 自包含、候选不见评审 rubric、各 worker 使用隔离输出、adversarial Finding 必须由真实运行证明、聚合者丢弃无证据结果。这里适配为 Test Privateer 的测试域约束，不复制 pstack 的模型配置、云工作树或固定四代理编排。

## Goals / Non-Goals

**Goals:**

- 让完整 Loop 的第一轮测试发现不受开发叙事和既有结论锚定。
- 证明实际创建了新的子代理，并能审计它看到了什么。
- 让重复检查有新颖性或明确复验目的。
- 保持测试资产、证据、Run ID 和单一合成者规则不变。

**Non-Goals:**

- 不要求普通单层测试请求启动子代理。
- 不固定子代理模型或要求不同模型家族。
- 不默认每轮启动四个 Agent。
- 不让子代理修改产品代码或共享轮次资产。
- 不把“盲测”解释为完全不能读取项目；子代理可以从项目入口独立调查，但初始盲测任务包不提供开发过程和既有结论。

## Decisions

### 1. 使用“盲测发现 → 知情回归”两阶段

完整 Loop 在开发变更之后进入执行时，先启动一个新子代理完成盲测发现。该子代理收到独立任务包，可以读取当前项目规则、用户可观察契约、项目测试配置和获准入口，但不收到：

- 开发聊天、实现理由或修复假设；
- 实现 diff、提交说明和开发者自测结论；
- 既有 Finding 的结果、预期缺陷清单；
- 评审 rubric、目标答案或其他候选结果。

盲测结果和证据封存后，主 Agent 才进入知情回归，使用 diff、已有用例和历史 Finding 补齐变更影响。知情阶段使用新的子代理或由合成者按现有专项执行，不把开发上下文追加给原盲测子代理。handoff 显式携带原 Run ID、封存 wave、目标版本和证据哈希／指针；新子代理会话不创建新 Run ID，且仍只写隔离输出。

替代方案是把所有材料交给一个“测试角色”子代理。角色名称不能消除上下文锚定，因此不采用。

### 2. 盲测任务包以可审计输入清单为边界

每个盲测 wave 记录：

- wave ID、Run ID、目标版本和分配的质量视角；
- 子代理会话／任务 ID、模型和宿主；
- 允许读取的规则、契约、配置、入口和测试资产指针；
- 环境、账号、数据、预算和禁止动作；
- 中性的覆盖排除项；
- 明确未披露的开发材料；
- 任务包哈希和结果／证据路径。

“中性覆盖排除项”只描述已经执行的表面、状态、动作和 Oracle 组合，不包含通过／失败结果、原因解释或开发假设。这样既减少重复，又不把结论泄漏给盲测 Agent。

候选输入审计不能只保存显式 prompt。系统／开发者输入、宿主自动注入规则、父目录 `AGENTS.md` 和可用记忆同样属于候选输入。冷启动工作区不得放在会继承开发仓库父级规则的目录树中；出现未声明额外输入时，该 wave 无效并在干净工作区重跑。

部分宿主不公开完整系统基线。此时记录宿主／版本、全新会话机制、是否 fork、记忆策略和父级规则隔离保证；能排除开发上下文继承即可继续判读，保证不成立时才受阻，避免把“看不到宿主固定基线”误判为所有 Loop 都不可运行。

不新增第二套轮次文件。字段进入 `testing/runs/<run-id>/run.md` 的盲测 wave 索引；详细 prompt、输出和证据留在对应隔离路径。

### 3. 子代理只取证，单一合成者复核

子代理不得更新共享 `run.md`、权威用例、公共报告或产品代码。它只返回 `PASS`、`ISSUES` 或 `BLOCKED`，并为每项提供：

- 实际执行的动作或命令；
- 原始输出或产品状态证据；
- 证据路径；
- 覆盖范围和未执行范围。

合成者检查实际调度记录、输入清单、工具轨迹和证据。无运行证据的 Finding 被丢弃或保留为待验证假设，不能进入已证实问题。

### 4. 用覆盖指纹控制重复

每项执行生成覆盖指纹：

```text
测试表面 + 身份／数据／初始状态 + 动作／路径 + Oracle + 故障或质量视角
```

新 wave 至少改变一个维度，或者声明允许的复验目的：

- 修复后的回归确认；
- 首次失败后的稳定性调查；
- 环境恢复后的有效性确认；
- 新版本或新配置的对照。

完全相同且没有复验目的的执行被跳过。连续 wave 只收到覆盖指纹和当前分配视角，不继承上一 Agent 的推理和结果正文。

### 5. 风险分级，不固定过度 fan-out

- 普通完整 Loop：至少一个盲测子代理。
- 高影响、未知面大或发布关键：在预算允许时分配 2～4 个独立子代理，按业务、权限、安全、异常恢复、数据或交互等互不重叠视角切片。
- 每个 brief 自包含，每个子代理有独立输出路径；缺席子代理形成覆盖缺口，不计为通过。

这保留 pstack 的独立 worker 和 adversarial coverage，但不把每次测试都升级为固定四代理成本。

### 6. 无子代理能力时严格受阻

宿主不能创建新会话、不能证明输入隔离，或只能让同一 Agent 伪装角色时，完整 Loop 在盲测门槛标记 `blocked`。用户明确接受降级后可以继续同上下文测试，但：

- Run 记录降级授权和原因；
- 最终报告列出“独立盲测未完成”；
- 不把降级结果表述为完整 Test Loop 已满足盲测要求。

普通单层请求仍可沿原专项运行，不受该门槛影响。

### 7. 评测必须观察真实调度和输入

静态契约测试检查规则、模板和场景存在。行为评测至少覆盖：

- 开发上下文中启动新的盲测子代理；
- 子代理输入不包含开发叙事、diff、既有 Finding 结果或 rubric；
- 子代理独立读取项目并返回真实执行证据；
- 主 Agent 在结果封存后才做知情回归；
- 重复覆盖指纹被跳过，新风险切片可以推进；
- 子代理不可用时受阻，显式降级不会冒充盲测；
- 高风险 fan-out 使用隔离输出，单一合成者更新共享资产。

判读依据是调度事件、prompt／输入清单、Skill 加载、工具轨迹、文件差异和证据，不是主 Agent 或子代理自述。

## Risks / Trade-offs

- [子代理增加模型成本和时间] → 普通 Loop 只要求一个；高风险时才扩展。
- [排除既有结果导致重复] → 提供不含结果的覆盖指纹和分配视角。
- [项目调查本身暴露实现信息] → 初始 brief 不提供 diff 或开发叙事；子代理从项目入口独立调查，知情回归另开阶段。
- [宿主无法证明冷启动] → 严格标记受阻或显式降级，不伪造。
- [隔离目录继承父级规则] → 审计实际加载输入；未声明输入使 wave 无效，并改用干净工作区重跑。
- [新会话被误当成新轮次] → 知情 handoff 固定原 Run ID 和封存 wave；子代理禁止创建第二套 `run.md`。
- [并行 Agent 污染共享状态] → 隔离输出，单一合成者写共享资产。

## Migration Plan

1. 先增加失败契约测试和行为场景，证明当前 Loop 没有强制子代理和输入隔离。
2. 更新 Loop Skill 和轮次模板。
3. 运行目标场景和相邻正常场景，按真实失败最小修正。
4. 全量验证后保留活动 change，等待用户确认。

回滚时删除盲测 wave 规则和模板字段；原有阶段状态、Run ID、执行、调查和报告能力继续可用。
