# Design

## Context

Test Privateer 已有测试分析、风险、建模、用例、自动化、执行、调查、回归和信心评估专项。主入口当前按阶段停止，适合精确调用，但用户需要多次发送“继续”才能完成完整测试闭环。

本 change 只增加编排层。它依赖：

- `establish-test-run-asset-lifecycle` 提供 Run ID、轮次状态、证据和失效契约。
- `add-test-privateer-project-setup` 提供可选项目配置、环境边界和质量门槛。

Loop 不重新定义这两个 change 的产物，也不复制专项方法。

## Goals / Non-Goals

**Goals:**

- 在一个明确授权内连续推进完整测试链。
- 根据已有资产跳过不需要的阶段。
- 根据风险选择最小充分测试方法。
- 沿用项目选定的测试框架，只在匹配时加载框架专项 Skill。
- 让新证据改变后续测试，而不是机械执行预设清单。
- 在预算、检查点、安全边界或退出条件处可靠停止。
- 输出有范围的测试信心报告。

**Non-Goals:**

- 不修改产品代码或自动修复产品缺陷。
- 不自动批准发布或接受残余风险。
- 不要求每轮执行所有测试层级。
- 不创建新的测试方法、编号体系或证据格式。
- 不自动创建、更新或关闭外部缺陷。

## Decisions

### 1. 新增一个薄编排 Skill

新增 `skills/running-test-loop/SKILL.md`。它只维护：

- 启动契约。
- 阶段状态。
- 路由决定。
- handoff 合成。
- 退出判断。

分析、用例、API、E2E、UI、执行、调查、回归和报告继续由现有专项 Skill 负责。

真实模型评测显示，正确路由仍可能在开始时预读大量未来阶段专项，增加上下文和耗时。Loop 因此要求按当前阶段即时加载：handoff 或新证据把下一阶段变成当前动作后才读取下一专项；复用或跳过的阶段不预读对应方法。

替代方案是扩展 `test-privateer` 主入口。该方案会让每个请求都加载完整循环规则，并让路由表承担执行状态，因此不采用。

### 2. 使用有回边的阶段状态机

Loop 使用以下阶段：

```text
恢复项目与轮次
→ 固定任务、授权和退出条件
→ 建立或复核项目与变化认识
→ 风险、模型和用例
→ 交付前自校
→ 选择方法并执行
→ 调查 Finding
→ 选择和执行回归
→ 评估测试信心
→ 停止、暂停或完成
```

只有新证据改变规则、风险、模型、用例、执行路径或结论时，才回到前一阶段。回边必须追加决策记录，并只更新受影响范围。

参考公司 dev skills 的推进方式，Loop 不把阶段名称当作进度。每个当前阶段需要明确输入指针、当前缺口、预期权威产物、完成证据和下一动作；只有产物实际存在、适用于当前版本且证据支持阶段目标时才能推进。Skill 加载、计划、标题或模型自述不构成完成证据。

恢复时从 `run.md`、资产指针和实际项目状态重建当前视图，不依赖旧聊天总结。后期发现问题时回到拥有问题的最近责任阶段，保留未受影响的完成产物、证据和 Run ID，只重验受影响路径。这里借鉴“真实状态恢复、产物门禁、定向返工”，不引入 Harness 的 ticket、提交或回执协议。

### 3. 启动契约一次授权正常执行

Loop 开始时从用户请求和项目配置固定：

- 测试对象和版本。
- 目标和范围。
- 允许的环境、账号和数据动作。
- 允许创建或修改的测试资产。
- 禁止动作。
- 时间、费用或运行次数预算。
- 退出条件。

用户明确要求“运行完整 Test Loop”时，视为授权在已声明边界内执行测试。新增环境、凭据、费用、生产访问或共享数据破坏仍需要新的决定。

项目配置中的质量门槛是项目默认要求。当前 Run SHALL 将本轮适用的门槛、用户新增限制和退出条件保存为快照。后续项目配置变化不改写进行中或已完成轮次；需要采用新门槛时创建新轮次，或在未执行前由用户确认更新当前轮次。

同时修正 `analyzing-change-for-testing`。没有执行授权时，它只核对已有测试和历史证据；Loop 已记录授权时，执行由后续专项承担。

### 4. 选择方法，不追求层级齐全

Loop 读取 `designing-test-automation` 和对应实施专项：

- 纯接口目标进入 `writing-api-tests`。
- 跨页面或服务旅程进入 `writing-e2e-tests`。
- 视觉、交互、无障碍和任务可用性读取 `reviewing-ui-ux`，并通过真实渲染执行取得证据。
- 单元、组件、集成、性质或形式检查继续按现有风险选择。
- Agent 评测先读取项目框架约定；只有项目选择 DeepEval 等受支持框架时才加载对应专项，否则使用通用 `agent-eval` 和项目自身入口。

一个检查只有能发现独特错误时才加入组合。局部模拟和真实链路分别报告。

Loop 不负责替项目选择或安装测试框架。项目尚未决定且选择会改变资产或执行方式时，Loop 交回 `setup-test-privateer` 确认；项目使用自有框架时不得为了复用专项 Skill 而改用其他框架。

### 5. Loop 只修改测试资产

Loop 可以在授权范围内修改：

- 测试代码。
- 测试夹具和数据生成器。
- 项目验证器和驱动。
- 测试分析、用例、执行记录和报告。

Loop 不修改产品代码。产品缺陷进入 Finding、调查和交接。验证器漂移可以在测试资产范围内修正并复验。

### 6. 失败先分类，再决定下一步

每次失败先分类为：

- 产品行为不符。
- 测试资产或驱动失效。
- 环境或身份问题。
- 工具失败。
- 规则或判定依据不足。
- 原因未知。

分类决定调查、修正测试资产、建立人工检查点或停止。相同重试必须有新的区分目的；无界重试不属于 Loop。

### 7. 单一合成者维护轮次，分支只取证

Loop 是轮次合成者。可以并行分派互不共享状态的 API、E2E 或 UI 检查，但分支只返回 handoff 和隔离证据。Loop 更新权威分析、用例、轮次记录和报告。

该规则直接复用测试轮次 change，不在 Loop Skill 中复制完整字段。

### 8. 真实模型评测验证路由和边界

行为评测至少覆盖：

- API-only 任务不启动浏览器。
- 项目使用自有 Agent 评测框架时不加载 DeepEval 专项。
- 项目明确选择 DeepEval 但专项 Skill 不可用时报告能力缺口，不静默安装或替换框架。
- UI 任务取得真实渲染和操作证据。
- 已有适用用例时跳过重复分析。
- 缺凭据时建立人工检查点。
- 工具失败后不声称产品通过。
- 首次失败、重试通过时保留稳定性风险。
- 预算耗尽时停止。
- 暂停后恢复原 Run ID。
- 产品缺陷不会触发产品代码修改。
- 普通单层请求不进入完整 Loop。
- 阶段自述完成但权威产物缺失时不得直接推进执行。
- 后期发现测试驱动问题时只回到测试资产责任阶段，不重做有效分析和用例。

候选会话只能看到自然任务。评审依据单独保存，并核对实际 Skill 加载和工具轨迹。

## Risks / Trade-offs

- [Loop 变成大而全的复制入口] → 只保留状态、路由和退出规则；方法仍由专项维护。
- [自动执行越过权限] → 启动时固定授权；新增高影响动作触发检查点或停止。
- [Loop 把框架专项变成默认框架] → 以 Setup 和项目权威来源为准；专项 Skill 只在明确匹配时加载。
- [循环无法停止] → 每个回边必须有新证据和预算；退出条件是启动契约的一部分。
- [并行结果互相覆盖] → Loop 是唯一合成者；分支只写隔离证据。
- [测试失败诱导修改产品] → 产品代码只读；缺陷只调查和交接。
- [有限评测被解释为稳定自治] → 报告模型、宿主、场景和失败边界，不声称跨模型普遍稳定。

## Migration Plan

1. 先完成并验证测试轮次资产 change。
2. 完成并验证项目 Setup change。
3. 新增 Loop Skill 和主入口路由。
4. 修正变化分析的授权表达。
5. 对普通专项请求保持原路由，不自动迁移到 Loop。
6. 按测试轮次、项目 Setup、Test Loop 的顺序同步规格和归档，避免后置 change 在当前规格中引用尚不存在的能力。
7. 若回滚，删除 Loop 路由和 Skill；底层专项、项目配置和轮次资产继续独立可用。
