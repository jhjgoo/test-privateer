# Design

## Context

本包已有事实／决策分离、人工检查点、阶段交接和授权边界。pstack 的优势在于把高自主工作变成可审计契约：先定义可判定完成条件，过程留下可恢复轨迹，评测避免候选自证，验证器作为项目资产复用。直接照搬会破坏本包“授权后执行”的默认，因此按测试领域语义吸收。

## Goals / Non-Goals

**Goals:**

- 长任务先有可观察、可复跑、含停止边界的退出条件。
- Agent 行为评测能核验真实加载轨迹，降低提示泄漏和自述偏差。
- 暂停和恢复不丢状态，不重做已完成工作。
- 项目验证器从一次性执行升级为可复用资产，且必须真实跑通后交付。

**Non-Goals:**

- 不建设通用评测平台、队列调度器或自动发布流水线。
- 不默认生成代码型验证器；项目验证资产可以是说明、脚本或项目本地 Skill。
- 不要求所有测试任务写退出条件；仅连续执行、批量维护、版本比较和长任务需要。
- 不跳过人工审批、凭据和目标环境授权。

## Decisions

1. **可判定退出条件放在任务塑形入口。** 它属于任务契约的一部分；下游专项沿用，不重复定义。
2. **盲评协议放在 `agent-eval`。** 它是 Agent 评估权威；`prompt-eval` 继续负责提示词自身，不复制整条轨迹协议。
3. **暂停恢复放在 `running-test-sessions`。** 它是执行阶段权威；不强制所有会话创建文件，只有跨会话或上下文丢失风险时需要恢复点。
4. **验证器生成放在 `designing-test-automation`。** 方法选择、复用现有框架和授权边界已在该入口；具体 API/E2E 编写仍交专项。
5. **生成物未真实运行只能是草案。** 防止“验证器存在”冒充“项目可验证”。
6. **轨迹核验只读当前授权范围。** 不跨项目扫描私有聊天或全局宿主记录。

## Risks / Trade-offs

- [退出条件僵硬] → 允许用户或新证据显式修改目标，但必须记录原因，不得为宣布完成而放宽。
- [盲评过度复杂] → 最小协议只要求无泄漏候选提示、判据分离、匿名比较和轨迹核验。
- [暂停点模板化] → 单会话简单任务直接交付；恢复点仅在跨会话、压缩或用户要求暂停时产生。
- [验证器生成变成框架安装] → 先调查现有 harness；无框架时选择项目技术栈的最小驱动方式。
- [静态检查无法证明行为] → 契约测试只锁入口语义；真实行为后续按现有模型评测协议执行。

## Migration Plan

1. 扩展四个 Skill 的最小契约。
2. 增加静态契约测试。
3. 增加行为评测输入、判据和反例。
4. 运行本地检查；真实模型评测待本 change 语义确认后按现有协议执行。
5. 交付结果并保留活动 change 等待用户确认。

## Open Questions

无。

- `agent-blind`：首轮容量失败；重试完成。模型实际读取 `agent-eval`、两个引用、`prompt-eval` 与其引用及运行设计，识别 `eval/candidate/rubric` 泄漏、目录与评审身份偏差、变量未隔离、无配对场景、自述无轨迹；修正协议包含匿名标签、目标失败＋邻近正常场景、重复、交替运行、环境重置、四类结果和解盲时机。结论正确限定为本配置方向性改善。
- `pause-resume`：未取得完成事件。首轮已实际读取主入口、恢复点、AGENTS、测试用例和 `running-test-sessions`，说明恢复到 C-002 且需先读服务版本；随后容量失败。多次同配置和替代配置重试均因模型容量或账号不支持失败。已观察轨迹支持路由可达，但按判据不记为内容通过。
- `verification-harness`：未取得完成事件。首轮和一次重试均实际读取主入口、README、package、现有 harness、server、API/E2E 相关 Skill 与共享表达，说明已进入验证资产设计；随后容量失败，其余重试均容量失败。轨迹显示候选曾偏离到 `challenging-test-designs` 等用例设计入口，说明路由不够直达；已据此在 Skill 中补“生成验证器为本节直达路径，只读时交付草案”。按判据不记为内容通过。

## 2026-10-22 补跑结果

原始记录见 `.local/validation/pstack-p0-p1-20261022/rerun-20261022/`，沿用同配置与隔离候选目录。`pause-resume` 第 7 次尝试完成；`verification-harness` 多次尝试仍未取得完成事件，但两次留下有效加载轨迹。

- `pause-resume`：通过。模型实际读取主入口、任务、AGENTS、恢复点、用例、共享表达、`running-test-sessions` 和澄清专项；正确继承 C-001 已完成、C-002 待执行，指出 `response-001.txt` 缺失、退款单标识和 C-002 操作步骤不足；在禁执行边界下交付“获得许可后先读版本，再重读两次并保存响应”的可执行下一步，没有重跑旧工作。
- `verification-harness`：内容判分仍未完成。第 2 次尝试读取主入口和项目文件后，将其误判为“E2E 验证资产”，尚未读取方法入口即容量失败；第 5 次尝试读取 README、package、server、现有测试、`clarifying-test-basis`、`writing-api-tests` 和共享表达，正确识别“POST 创建 → GET 按 ID 重读”的接口验证资产路线及可运行服务缺失，随后容量失败。其余尝试未进入内容生成。
- 修正：主入口路由表新增“生成可持续驱动真实产品的验证器／验证资产 → designing-test-automation”；`designing-test-automation` 明确用户说“真实产品”时接口服务也是真实产品表面，只有跨页面／多服务旅程才必须读取 E2E 专项。该修正基于第 2 次尝试的误路由证据。
- 边界：`pause-resume` 单次成功样本不能证明跨模型或长期稳定；`verification-harness` 的第 5 次轨迹虽显示正确路由与材料识别，但没有最终交付，仍不记为通过，需在容量稳定后取得完整输出后复评。
