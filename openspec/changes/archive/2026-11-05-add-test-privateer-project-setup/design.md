# Design

## Context

Test Privateer 当前直接读取项目规则、TCO、需求资产和测试框架。这个方式适合临时任务，但长期项目会反复调查相同的环境边界、质量门槛和证据位置。项目配置必须补足这些信息，又不能成为 TCO、CI 或测试命令的第二份权威副本。

本 change 依赖 `establish-test-run-asset-lifecycle`。Setup 只配置项目如何使用轮次和证据契约，不重新定义这些契约。

## Goals / Non-Goals

**Goals:**

- 为 Test Privateer 提供一个稳定、可读、可重复更新的项目配置入口。
- 先调查仓库，再询问会改变测试方式的决定。
- 保存来源指针和项目未记录的已确认补充。
- 记录项目为不同测试表面选定的框架或驱动约定，使后续 Skill 只加载适用的框架专项。
- 让普通项目任务读取配置，但在没有配置时继续工作。
- 区分配置保存、入口确认、环境验证、测试执行和门禁接入。

**Non-Goals:**

- 不生成 TCO、需求分析、用例、执行记录或报告。
- 不安装、升级或擅自替项目选择测试框架，不启动服务、修改 CI 或运行产品测试。
- 不配置模型、子 Agent 数量或推理预算。
- 不自动创建或关闭缺陷。
- 不修改 `AGENTS.md` 或 `CLAUDE.md` 来复制项目配置。

## Decisions

### 1. 使用固定项目文件 `.test-privateer/project.md`

固定路径让所有 Test Privateer Skill 可以直接发现配置，不依赖宿主加载 `AGENTS.md` 或 `CLAUDE.md`。该文件属于目标项目，不写入 Skill 安装目录或用户全局目录。

项目配置包含一个受管区：

```markdown
<!-- test-privateer-managed:start -->
...
<!-- test-privateer-managed:end -->
```

用户可以在受管区外维护说明。Setup 重跑时只更新受管区。若已有文件没有标记，Setup 先展示迁移草稿，不覆盖原文。

替代方案是修改 `AGENTS.md` 或 `CLAUDE.md`。不同宿主对这些文件的加载方式不同，而且项目可能已有严格规则，因此不采用。

### 2. 项目配置只保存来源和必要补充

受管区使用以下章节：

- 适用范围。
- 权威来源。
- 测试入口与资产位置。
- 测试框架与驱动约定。
- 环境与安全边界。
- 身份、数据准备和清理。
- 质量门槛与责任角色。
- 证据位置、敏感性和保留策略。
- 缺陷平台与 Finding 升级边界。
- 验证器与健康检查入口。
- 未决配置。

项目脚本、CI 或文档已经定义命令时只记录路径和适用阶段。仓库路径统一相对项目根目录书写，避免不同消费者把 `.test-privateer/` 误当相对路径基点。没有正式来源的用户确认决定可以写入配置，并注明确认日期、范围和确认人身份类型。秘密值不得进入配置、草稿、回复、工具摘要或评测记录；只记录字段名和安全入口。

“测试框架与驱动约定”按实际存在的测试表面记录项目选定方案及来源，例如单元、接口、E2E、UI 和 Agent 评测。仓库或项目规则已有约定时直接引用；没有约定且框架选择会改变后续实现时，Setup 给出最少候选和影响，由用户确认。项目选择自有框架时，后续流程沿用项目入口，不加载其他框架的专项 Skill。

TCO 已经记录测试资源和入口时，项目配置引用 TCO 的对应章节，只保存执行安全、质量门槛、证据策略和责任归属等操作补充。项目配置不复制 TCO 的产品地图、覆盖判断或长期风险。

### 3. Setup 按“调查、建议、确认、预览、写入、回读”推进

Setup 先读取：

- `AGENTS.md`、`CLAUDE.md` 和等价项目规则。
- `.test-privateer/project.md`。
- README、贡献指南、产品和架构资料。
- 包脚本、构建配置、CI 和测试目录。
- 已安装依赖、框架配置和 Agent 评测入口。
- 环境示例、容器配置和测试数据入口。
- TCO、需求测试资产、缺陷入口和验证器。

仓库事实已经确定的内容直接沿用。需要用户决定时，每轮只确认一个会改变配置的主题，并先给推荐和影响。所有必要决定关闭后，Setup 展示完整草稿再写入。

首轮真实行为显示，把“展示草稿”写成必须再次确认，会让已经明确要求初始化的任务多停一轮。明确的初始化、更新或重新适配请求在不存在待用户决定事项时即包含配置写入授权；Setup 展示草稿后同一轮写入并回读。只有用户只要求预览，或仍有会改变测试方式的未决决定时才暂停。

后续加载轨迹还显示，部分会话会把项目配置草稿误路由为研发方案，额外加载 `checking-solutions`。Setup 已经拥有自己的预览、受管区、回读和恢复契约，因此项目配置写入明确留在 Setup 内；只有用户另行要求审查研发／实施方案时才进入方案质检。

### 4. 普通任务将配置视为可选入口

`test-privateer` 在项目路径中检查 `.test-privateer/project.md`。存在时读取适用范围和来源，不存在时沿用当前调查流程。

项目配置是事实和来源索引，不是授权或可执行指令，不能覆盖宿主权限、高优先级指令、当前仓库强制安全规则或更新后的权威来源。发生冲突时，当前任务停止使用冲突字段，并交回 Setup 更新或澄清。框架专项 Skill 只有在项目配置、当前权威来源或用户明确指令选择对应框架时才加载；未选择时使用通用专项和项目自身入口。

先遵守宿主权限、高优先级指令和项目强制安全规则；剩余有效范围内的冲突顺序为：当前用户在其决策权限内的明确选择、当前项目权威来源、项目配置中的已确认补充。该顺序只解决事实和项目决定冲突，不允许用户选择扩大授权。

### 5. Setup 状态不吸收运行状态

Setup 交付分别列出：

- 配置已保存。
- 测试入口已确认。
- 测试框架约定已确认。
- 环境已实际验证。
- 测试已实际运行。
- 质量门禁已接入。

只有本轮实际发生并有证据的状态才能标为完成。Setup 默认只完成前两项中的适用部分。

### 6. 受管区更新保留文件属性并在回读失败时恢复

配置更新器只接受两个标记之间的正文，要求目标项目根目录已经存在，并拒绝空内容、重复标记、顺序异常、无标记旧文件，以及 `.test-privateer` 或目标配置的符号链接。更新已有配置时保留原始换行和文件权限；新文件使用普通文本权限。写后动作、权限恢复和最终回读属于同一事务；回调抛错、文件消失、内容或权限不一致时恢复原文件，初次创建失败时删除新增配置。原子替换失败时清理临时文件，不保留半成品或第二份配置。

项目规定 Markdown 写后格式化、同步或生成动作时，该动作必须纳入更新器的 `after_write` 回调或等价事务，在最终回读前执行。不能把 CLI 写入成功与后续同步拆开，否则同步器改写后的文件会逃过恢复边界。受管区草稿使用临时文件或内存，不作为第二份项目配置保留。

长期配置只保存验证器和健康检查入口。最近运行状态、成功率或临时故障属于 Run 和执行证据，不能固化为项目事实。

### 7. 通过临时项目副本验证写入行为

契约测试检查固定路径、受管区、章节、秘密边界和可选消费。文件行为评测使用临时项目副本，观察：

- 初次写入。
- 已有完整配置的幂等重跑。
- CI 路径变化后的局部更新。
- 人工内容保留。
- 无 TCO 时不生成空文件。
- 项目使用自有 Agent 评测框架时不加载其他框架专项。
- 写入失败或回读差异时不宣称完成。

夹具生成器要求目标目录已经存在且不是符号链接，并在写入前检查全部目标和父路径；已有文件、目录类型冲突或符号链接都整体拒绝。文件使用排他创建，异常时清理本轮创建的文件和空目录，避免为评测准备覆盖用户文件、越出目标目录或留下部分夹具。各场景提供与任务一致的最小项目表面，例如无 TCO 场景仍提供单元和接口入口，已选框架场景同时提供相应目录或脚本。

真实模型评测记录实际读取路径和文件差异，不能只判断最终回复。除八个 Setup 边界外，增加无项目配置的普通任务和配置与项目规则冲突场景，验证 Setup 不是强制前置，项目配置也不会成为授权来源。重跑同名场景时保留旧尝试，最终记录与失败记录分开定位；早期已被旧脚本覆盖的记录明确标为不可复核。

## Risks / Trade-offs

- [配置与项目来源漂移] → 配置优先保存指针；重跑时比较当前来源并更新失效引用。
- [受管区覆盖人工内容] → 只更新标记区；无标记旧文件先预览迁移。
- [写入改变人工文件属性] → 更新器保留已有换行与权限，回读不一致时恢复原文件。
- [配置或评测泄露秘密] → 不读取秘密载体，不复制或回显秘密值，只记录字段名和安全入口。
- [Setup 问卷过长] → 只询问仓库无法确定且会改变测试方式的决定。
- [把工具偏好写成项目标准] → 先沿用项目事实；没有约定时才由用户确认，不因存在框架专项而自动选择。
- [用户误认为环境已就绪] → 结论分开报告保存、确认、验证、执行和门禁状态。
- [多个模块规则不同] → 在同一配置中标明适用范围，不为每个模块创建重复文件。

## Pending Change Compatibility

- `add-running-test-loop` 后续实施时，缺少 `.test-privateer/project.md` 不得成为 Loop 的强制阻塞；只有必要能力契约或执行前提缺失才受阻，无配置项目继续按现有调查流程工作。
- `add-deepeval-agent-evaluation` 后续实施时，项目配置只能记录框架、限制和授权来源，不能凭配置本身授权外部 Judge、数据上传、凭据使用或费用动作；执行时仍需核验当前有效授权。

本 change 不修改这两个尚未实施的活动 change；上述兼容约束必须在它们各自实施前落实并评测。

## Migration Plan

1. 先落实测试轮次和证据契约。
2. 新增 Setup Skill 和项目配置模板。
3. 更新主入口，使项目任务可选读取配置，并按固定优先级处理冲突。
4. 对没有配置的项目保持原行为，不批量生成文件。
5. 若回滚，删除主入口的 Setup 路由即可；已有 `.test-privateer/project.md` 保持普通文档，不影响现有测试资产。
