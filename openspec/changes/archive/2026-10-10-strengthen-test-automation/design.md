# Design

## 当前阶段与目标

本轮是 `strengthen-test-automation` 的第二阶段设计，已获用户确认并进入实施。第一阶段实现和证据仍保留，但不能证明第二阶段的独立入口已生效。行为要求见 [spec delta](specs/test-automation/spec.md)，执行状态见 [tasks](tasks.md)。

用户指出接口、集成及 E2E 参考偏概括，要求借鉴 `writing-unit-tests`。本轮借鉴它的任务契约：输入事实、观察边界、独立预期、首个用例、执行分支和证据交付；不机械复制单元测试的一个 Act 或强制 RED。

**目标：** 执行者能从专项 Skill 直接判断先查什么、写什么、怎么运行、如何处理失败，以及何时交付。只设计的任务仍止于设计。

**非目标：** 不新增通用执行平台、安装器或每个框架一个 Skill。不修改单元测试职责，不扩展性能、完整安全、移动端专项，不全量迁移使用方测试。不将模型输出一致性作为硬门槛。

## 1. 职责划分

比较三种方案：

- 只扩写四份参考：入口少，但接口和 E2E 的执行契约仍藏在方法入口后面。
- 每份参考各建 Skill：可直接调用，但集成、契约、接口和旅程之间容易重复承担任务。
- **采用：方法入口＋两个实施专项＋必要参考。** 接口与 E2E 有独立交付，集成／契约保留跨专项方法。

| 位置 | 职责及输出 |
| --- | --- |
| designing-test-automation | 选择目标错误、真实边界、互补测试和投入；路由到实施专项。已选合理范围时不再生成策略报告 |
| writing-unit-tests | 保持现有实现与单元 TDD 规则，文件不改 |
| writing-api-tests（新增） | 直接接收接口任务，交付测试设计或获准的代码、运行与判错证据 |
| writing-e2e-tests（新增） | 直接接收跨层旅程，交付设计或获准的旅程测试、运行与判错证据；已有框架优先 |
| 集成／契约参考 | 从目标协作错误选择真实依赖与观察，说明消费者／提供者两侧证据 |
| 组件参考 | 组件事件、反馈、状态恢复和模拟边界；不假装完整 E2E |
| 官方 e2e Skill | 选中 tester-army 框架后使用，负责匹配版本的配置与 API 操作，不决定产品预期 |

```text
test-privateer 或直接调用
├─ 方法／组合不清 → designing-test-automation
├─ 单元测试 → writing-unit-tests
├─ 接口测试 → writing-api-tests
└─ 系统旅程 → writing-e2e-tests
                 ├─ 已有框架：沿用
                 └─ 选中官方 e2e：接入参考 → 配套官方 Skill
```

接口也可能贯穿系统。按当前交付目标选择主专项：以 HTTP 合同为主交给接口专项，以跨层业务旅程为主交给 E2E 专项；必要时读取另一方法，不重复跑同一检查。纯组件请求继续由方法入口的组件参考承接，不强制升级成 E2E。

这次新增两个 Skill 替代第一阶段“不增加 Skill 数量”的决定。Skill 数量预计由 23 变为 25，实施时核对实际目录，不只改文档数字。

## 2. writing-api-tests：接口实施契约

### 定位任务

读取相关需求／TCON／缺陷、API 合同、真实调用方式和现有测试。核实测试服务、身份取得方式、数据控制入口、框架、文件位置及目标命令。

区分只设计、编写不运行、编写并运行三种授权；再区分新行为／缺陷保护与既有行为补保护。缺少源码但接口与环境已具备时仍可做黑盒接口测试，不把源码设为普遍前提。

**完成条件：** 明确目标行为、执行许可、已知调用合同和影响实施的缺口。未知只阻塞依赖它的动作。

### 固定请求、状态与独立预期

每个用例明确调用身份、资源归属、请求方法／路径／字段，以及预期来源。把响应合同和业务结果分开：状态码、字段形状不能替代写入、状态变化或下游动作。

选取独立观察入口，说明从哪里确认业务结果。数据库是目标依赖时不能用返回正确结果的 mock 证明它；按需读集成／契约参考。

权限用例只引入目标拒绝条件，其余前置保持有效。依据权限合同确认拒绝响应，再观察应受保护的状态，避免其他错误提前拒绝而假通过。没有合法观察或准备入口时明确缺口。

**完成条件：** 请求、初始状态、结果观察和每个精确预期均有依据。内部变量不冒充外部操作，未知状态码／幂等语义不编码。

### 选择首个有区分力的用例

从选定风险中挑最能区别正确与错误实现的一例。成功写入、对象越权、边界、重复或异步行为按任务需要展开，不每次全做。

写操作可形成“准备 → 请求 → 响应断言 → 独立重读”的结构。拒绝行为增加受保护状态的前后对照。读接口只断言其承诺的结果，不为了套结构虚构副作用。

并发需有可控交错或竞争条件；异步需有相关标识、完成信号和有依据的等待预算。它们不是串行重复调用或固定睡眠。幂等只有在产品承诺明确时才写重复请求断言。

**完成条件：** 能指出一个本例应当识别的错误，而不是只列风险名。

### 编写与独立准备

沿用现有框架、目录、HTTP 客户端和命令；没有工具时选项目内最小方案，不引入浏览器。准备、被测请求、观察断言、清理在代码中可辨认；多次观察请求可以共同证明一个业务行为。

数据标识按本次运行隔离，账号和环境引用获准配置。helper 只隐藏无关重复，关键身份、输入和结果留在用例附近。清理仅作用于本轮拥有的数据；失败证据先保留，清理失败单独报告。

**完成条件：** 用例不依赖前一例残留，真实字段与请求协议准确，无凭证硬编码。

### 执行、归因与交付

只运行目标测试，再按改动影响选相关回归：
- 符合预期：记录实际结果；既有行为首次通过正常，不伪称 TDD。
- 业务断言不符：保留请求、响应和状态差异，核对前置及预期来源，不能自动改 expected 迎合实现。
- 启动、认证准备、数据准备或工具错误：说明本次哪些断言未到达，修可修的测试基础；不能算目标缺陷的有效 RED。
- 首次失败后通过：保留首次结果，区分产品重试、轮询等待与套件重跑。

缺陷保护在未修复版本能复现目标失败时留存该证据；已有实现可在安全夹具用已知失败变体验证探错能力，恢复后复跑。无法探查则写清限制，不破坏生产实现。

交付测试文件、命令、版本／运行标识、实际边界、预期来源、首次及重跑结果、未覆盖项和下一动作。只生成代码时明确未执行。

## 3. writing-e2e-tests：旅程实施契约

### 定位旅程与真实范围

读取用户目标、成功／失败规则、起点、终点、身份及现有自动化。列明旅程穿过的页面、服务和数据边界，以及哪些依赖被替换。已有合理范围直接使用。

一个用例围绕一条可说明结果的旅程，可包含多个必要操作；不照搬单元测试“一个 Act”。不把所有输入组合搬到浏览器，也不把后端全部模拟的组件测试称为完整 E2E。

**完成条件：** 起止状态、真实链路、预期来源和当前权限清楚。

### 准备可重复的开始状态

沿用现有登录／数据夹具。用接口或其他获准手段加速非目标准备可以成立，但被验证的关键动作必须实际经过选定旅程。

隔离身份与后端可变数据，确认初始状态。新的浏览器 context 不能独自证明数据隔离。每次使用本轮标识，清理范围可定位；未知登录、删除或重置入口先查证。

**完成条件：** 单独运行不依赖其他用例；前置可核实，失败后能保留证据并恢复本次资源。

### 实现操作与业务断言

按用户可见名称、角色或稳定测试标识定位；不猜选择器。等待具体状态或本次请求结果，不用任意睡眠。

关键业务动作之后断言承诺结果。若合同要求重开后保留，就重新读取；并非所有操作都机械增加页面重开。对错误恢复，按当前规则验证输入保留、修正重试与最终结果，不把旧错误提示当第二次失败的证据。

同一层出现多个结果时，确认它们对应同一对象／业务标识。参数、路径和字段保留项目真实名称；模型自然语言总结不是业务断言。

**完成条件：** 断言能指出哪个业务承诺未成立；成功提示或点击结束不能单独替代结果。

### 复用框架，按需使用 AI

已有框架直接编写测试。只有没有合适框架且已选官方 e2e，才读取接入参考并获取匹配版本的官方 Skill。普通 E2E 任务不要求模型凭证。

选择 AI 操作时给出一个清楚目标，参数独立传递。操作后由明确断言检查业务结果。首次验证禁用回放并记录实际模型调用；回放与冷运行分别报告。调用记录缺失时不凭“执行了 agent.act”声称已经冷运行。

**完成条件：** 工具选择服从测试目标，配套版本可核实，模型只负责所需操作，不自产预期。

### 证明能发现错误并交付

单独运行首条旅程。失败时定位最后一个已确认的状态，区分准备失败、定位／同步失败、模型故障、业务断言失败和清理遗留。避免用重跑全套或增大等待掩盖原因。

优先复用已知缺陷版本或受控失败变体，检查业务结果被破坏时核心断言确实失败。故障恢复后用同一断言重跑；不以改错 expected 作为发现业务缺陷的充分证据。

交付目标命令、测试文件、框架及应用版本、真实范围、数据准备和清理、首次与重跑结果、必要截图／轨迹以及未验证项。没有运行权限时只交付代码或设计，并说明已完成的检查。

## 4. 参考文件也要可执行

- **集成／契约：** 明确要证明的协作错误 → 选真实依赖及版本 → 准备两侧数据／契约 → 从真实入口刺激并观察 → 区分兼容与业务副作用 → 交付缺失一侧的证据。数据库约束、消费者通过但提供者未验证分别给一个简短反例。
- **组件：** 明确事件与可见结果 → 找实际组件和依赖替换边界 → 按真实协议配置替身 → 操作并观察反馈／恢复 → 判错及未覆盖真实服务边界。具体按钮或状态只来自任务，不固定套便签示例。
- **框架接入：** 保留官方来源、版本核对、初始化文件影响、运行与证据读取。增加“配置成功、测试启动、断言到达”三个实际状态的核对，不复制完整 API 手册。

保留第一阶段原始来源：Google、Vocke、Dodds、Pact、OWASP、AWS、Playwright、Hypothesis 和 Beck。来源支撑方法及适用边界，不用名称代替操作要求，不把研究笔记变成必读资产。

## 6. 验证与证据继承

第一阶段记录作为旧结构基线保留。旧脚本通过只证明旧脚本，不证明新 Skill 的路由或生成行为。

实施前冻结当前 Skill 快照、输入和判据；小规模验证，发生实质错误再定向复测：
1. 接口和 E2E 各选一个非便签业务输入，对比旧入口与新专项输出。检查缺失事实处理、动作、独立观察、预期和完成状态；不按字数或关键词评分。
2. 复用 A01、A04、A05、A06、A08、A10 检查单元精度、契约两侧、组件边界、已有框架、只设计和历史报告。只读样本不宣称实际运行。
3. 经新接口专项在原本地夹具的独立副本生成并运行接口保护；正常、已知丢写故障、恢复三态。经新 E2E 专项在已有 Playwright 副本新增保护，保留原套件。
4. 新 E2E 专项经迁移后的接入参考定位原已安装官方 Skill，完成一条 e2e 业务用例和获准模型冷运行。复用版本和下载资产，不重新演示安装；断言检查实际结果及模型调用，故障验证一次即可。
5. 重跑受影响静态契约、夹具自检、XMind、OpenSpec及引用／空白检查；请用户看一份接口和一份旅程产物，评估能否接手。

框架、凭证、数据或服务失效仅阻塞相关动作，不临时缩减承诺或冒用旧结果。无精确目标模型证据时，skill-eval不以“旧模型提示词过时”为由删领域约束。本次内容调整的依据是用户要求与任务契约缺口，不是模型迁移。

## 7. 实施、发布与回退

复用当前 worktree `codex/strengthen-test-automation` 和本 change，保留 main 及未提交工作。本设计与执行任务一并审阅；未获本阶段设计确认前不改运行时 Skill。

按“静态契约先失败 → 专项与引用迁移 → 受影响行为及实际路径 → 用户文档与审查”推进。具体实施清单在tasks的第二阶段中维护；不另建重复计划。

只有新阶段验收完成且获准后，才同步本地安装副本、提交／推送或归档。回退恢复旧结构及引用，不卸载使用方框架、不删除其数据。
