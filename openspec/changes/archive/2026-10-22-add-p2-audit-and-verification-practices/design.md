# Design

## Context

当前主入口已经把可判定退出条件、恢复点、人工检查点和验证器生成分开：任务塑形负责目标，执行会话负责轨迹，错题本负责教训，自动化入口负责方法与验证资产。P2 若简单叠加模板，会重复这些对象。因此本次只补各权威入口缺失的判定与维护路径。

## Goals / Non-Goals

**Goals:**

- 长执行的测试决策能按时间追溯，后续证据变化不覆盖当时决策。
- 教训晋升能区分账本记录、规则提醒和确定性检查，避免同义提示膨胀。
- 既有项目验证器可以在安全边界内维护，发现被分类而不是全部当作验证器 bug 修复。
- 性质／形式方法有明确风险触发、依据来源、可失败验证和覆盖边界。

**Non-Goals:**

- 不要求短任务、单轮问答或普通执行写审计表。
- 不自动安装 formal verifier、property testing 框架或模型检查器。
- 不修改被测产品代码，不承担产品缺陷修复。
- 不把 pstack 的通用工程流程复制进测试包。

## Decisions

1. **决策日志放执行入口。** 它是执行轨迹的一部分，与恢复点互读但不重复：恢复点回答“从哪里继续”，决策日志回答“当时为什么这样走”。
2. **决策必须追加。** 新证据推翻旧决策时新增行，不重写旧行；证据字段只接受路径、ID、版本、时间戳或等价稳定指针。
3. **教训晋升优先结构化。** 只有独立复发、可观察判定、可接受误报、权威位置和既有体系接入都满足时，才落地测试／检查器；无法自动检查的判断才写规则。
4. **验证器维护限定验证资产。** 先确认目标已存在；按功能做源理解和真实驱动对账；发现分成文档漂移、验证器缺口、产品缺陷，只有前两类属于维护动作。
5. **doctor 是安全门。** 首次驱动、冷启动恢复和异常后先运行只读 doctor；证据必须在清理后仍存在，失败才清理本次残留。
6. **性质／形式验证按风险进入。** 并发、状态、约束输入、独立规则和安全边界才触发；普通确定性用例仍是首选。

## Risks / Trade-offs

- [审计表模板化] → 仅连续执行、多轮证据变化、无人值守或明确审计要求触发。
- [结构化检查造成孤立资产] → 必须接入既有测试、脚本、CI 或入口检查，不新建无人运行的规则岛。
- [验证器维护越界] → 目标不存在则停止；产品缺陷只记录和交接，不在验证器维护轮修复产品。
- [形式化过度] → 无真实代码映射或已确认规则时不选模型检查／属性测试；通过结论只覆盖模型和边界。

## Migration Plan

1. 建立本 change 与三个 spec delta。
2. 扩展三个 Skill 的最小行为契约。
3. 增加静态契约测试与评测输入／判据。
4. 运行包检查、单元测试和 OpenSpec 严格校验。
5. 保留活动 change 等用户确认；真实模型评测待用户要求时按现有协议执行。
