# Design

## Context

当前 Setup 的测试表面矩阵已经区分框架、入口和项目级状态，但仍不足以表达“能否准备、启动、驱动、观察、留证和恢复”。`designing-test-automation` 已有项目验证器生成与维护路径，`running-test-loop` 已有 Run、盲测、阶段交接和证据边界；本 change 只补一个共享判定层，不重做这些能力。

## Goals / Non-Goals

**Goals:**

- 用一个短参考文件定义六段能力、六个长期状态和证据边界。
- 让 Setup、自动化设计和 Loop 使用相同词义，避免框架存在被误判为 Harness 可用。
- 让 API、UI/E2E、Agent 和单元等表面按实际边界裁剪六段能力。
- 让本轮首次真实执行尽量同时产生 Harness 证据，避免为贴标签重复运行。
- 保留旧配置、现有 Runner、盲测和验证器交接的兼容边界。

**Non-Goals:**

- 不新增 Harness 服务、注册中心、运行时依赖或每项目专用 Harness 文件。
- 不为所有测试表面强制引入六个脚本、浏览器、服务或统一框架。
- 不在 Setup 自动运行产品、安装框架、生成验证器、修改 CI 或创建测试数据。
- 不替代现有 `designing-test-automation` 的验证器生成／维护结果，也不完成 `add-setup-project-verifier-handoff`。

## Decisions

### 1. 用共享参考文件作为唯一词义来源

新增 `skills/designing-test-automation/references/harness-readiness.md`，只放六段定义、状态、证据门槛、按表面裁剪示例和迁移规则。三个消费者只引用它并补充自身阶段边界，避免在每个 Skill 复制一套长规则。

备选方案是新增独立 `harness-readiness` Skill；它会增加路由和加载成本，且用户只要求轻量通用约定，因此不采用。

### 2. 替换测试表面“项目级就绪”语义，而不是再加一套状态列

项目配置契约升级为 `test-privateer-project-profile/v2`。测试表面状态改为六个 Harness 状态；Setup 顶层状态、完整 Loop 架构状态和单项测试判定继续保留，各自不混用。

旧 v1 的 `ready` 只表示项目入口可定位，不能直接迁移为 Harness `verified`；没有六段证据时迁移为 `declared_unverified`。历史配置不覆盖，重跑 Setup 时只更新受管区。

备选方案是保留旧状态并新增 Harness 状态列；这会让“ready”同时有两个含义，增加误读和配置负担，因此不采用。

### 3. Harness 状态与生成结果分开

长期配置只使用六个 Harness 状态；自动化设计的 `verified`、`draft`、`blocked` 是一次构造／维护交接结果。`draft` 不写成长期状态，`blocked` 需要具体恢复入口。

这样可以表达“资产已经写出但未实测”和“当前测试表面不可安全继续”，又不引入第七个 `stale` 状态。旧证据失效时回到 `declared_unverified`、`partial` 或 `blocked`。

### 4. Loop 只检查本轮选中表面

全局 Setup、治理、Run 和盲测门禁保持优先；通过后，Loop 只对本轮实际选中的表面检查六段能力。首次合适执行的证据直接复用，未选中的表面不会阻塞本轮。

这避免把轻量单层任务升级成全项目初始化，也避免用“完整性”要求运行 API、UI、E2E、Agent 和单元的全部组合。

### 5. 用行为证据而不是文字或退出码验证

`verified` 至少需要真实目标路径、独立观察、原始证据和清理后证据可读性。健康检查、页面打开、文件存在、零退出码或 Agent 自述只能证明对应局部事实，不能替代六段行为证据。

### 6. 分析阶段先侦察选中表面，再扩展资产

完整 Loop 先用项目地图、变化和规则形成足以选择测试表面的最小认识，不先展开完整风险模型和用例。选中表面缺少当前 Run 仍适用的真实执行证据，且结论依赖执行时，先建立最小 Run 合同和盲测任务包，由冷启动子代理验证真实 `Start`、`Drive`、`Observe` 是否可达。长期 Harness 为 `verified` 也不能覆盖目标版本、入口、环境或失效条件变化。

可执行性成立后再按探针证据补风险、模型、用例和后续阶段；当前边界内不可达时，只封存探针证据、受阻范围、恢复入口和有界信心报告。没有执行授权时只做静态侦察，不能把入口存在写成运行时已验证；获得授权后仍需实际探针。

这避免模型在 API、UI、Agent 或其他真实目标根本不可用时先生成完整 TCO、用例、调查和回归资产。既有且适用的资产仍复用；实际探针已经构成有效冷启动盲测时直接复用，不为门槛重复相同覆盖。

## Risks / Trade-offs

- [旧项目配置字段被改变] → 使用 v2 标记；保留人工内容和历史证据；无六段证据的 v1 `ready` 安全迁移为 `declared_unverified`。
- [六段模型被误解成六个脚本] → 参考文件明确“能力而非脚本”，并提供 API、UI/E2E、Agent 和单元的复用示例。
- [Loop 变重] → 只检查本轮选中表面，并复用首次真实执行；单层请求绕过完整 Loop。
- [侦察探针后仍继续空转] → 探针失败且没有获准替代入口时立即停止；最小受阻交付不加载 Finding、回归或无关方法包。
- [侦察变成未授权执行] → 无执行授权或涉及新增环境、凭据、费用、共享破坏、生产访问时只做静态侦察，保留运行时未验证。
- [历史 verified 被误当成当前证据] → 目标版本、入口、环境或失效条件变化时必须重新侦察；当前 Run 的适用证据优先。
- [测试表面被错误标为 verified] → 要求实际驱动、独立观察、证据保留和清理后回读；静态契约测试只检查接入，行为评测检查真实路由和边界。
- [与验证器交接 change 冲突] → 本 change 只定义共享契约和消费方式；验证器生成确认、交接和回写继续由 `add-setup-project-verifier-handoff` 负责。

## Migration Plan

1. 先新增共享参考和当前 change 的 Skill／模板／Run 消费规则。
2. Setup 重跑既有配置时，将 v1 的测试表面 `ready` 映射为 Harness `declared_unverified`，并记录需要校准的六段。
3. 已有真实证据能覆盖六段的项目可在复核后标为 `verified`；否则保持 `partial` 或 `declared_unverified`。
4. 不修改历史 Run、旧测试结果或产品代码；新 Run 使用六段证据指针。
5. 若验证器生成交接后续落地，沿用本参考的 Harness 词义，不再创建第二套状态。

## Open Questions

无。验证器如何生成、何时询问用户和如何回写项目配置属于现有活动 change 的边界，不影响本 change 的契约。
