# Design

## Context

当前规格已有“项目初始化的缺陷入口、测试责任、风险接受或 CI 门禁若影响交接或判定，必须确认”，但 Skill 把 TCO、责任、缺陷和 CI 列在“判断是否配置完整 Test Loop”下，容易被模型按范围二分误读。

## Goals / Non-Goals

**Goals:** 普通 Setup 能决定适用测试类型、复用已有框架、识别治理缺口，建立可供后续工作复用的项目测试全景基线，并让后续任务判断配置是否仍然有效。

**Non-Goals:** 不在 Setup 中复制项目建图方法，不生成需求测试资产、测试代码、验证器、空目录或 CI；不代替项目负责人选择框架和治理责任。项目验证器的生成交接由独立 change 处理。

## Decisions

- TCO 是普通项目初始化的核心资产，不是 Loop 专属资产。Setup 调用现有 `mapping-project-test-space` 建立或校准唯一 TCO，不在自身重复建图方法。
- 初始 TCO 可以是有来源的草案：保留未知、影响和取证动作，但不能只有空标题或模板占位。这样既避免伪造完整度，也避免后续项目任务从零调查。
- 用户明确排除写入或只要预览时保持授权边界，但 Setup 只能报告 `partial: tco_not_initialized`，不能把配置文件保存等同完整初始化。
- 缺陷入口、测试责任、风险接受、CI 门禁是项目治理决定。普通 Setup 发现它们会影响交接或判定时必须确认。
- 完整 Loop 的额外要求是：关键架构决定全部关闭；盲测隔离输出、唯一合成者、共享资源并行策略和真实验证器可定位。
- 用户选择普通配置表示本轮不评估 Loop `ready`，不表示忽略治理缺口。
- 测试类型与框架在普通 Setup 中核对。已有入口只证明该表面存在约定，不代表其他表面不需要；适用范围未明确时先确认范围，再逐项确定缺失的框架，不在同一问题里要求所有决定。
- 复用现有 Skill 和项目配置模板，不增加第二套 Loop 配置。两个独立普通 Setup 夹具分别观察框架缺口和治理缺口，避免一个问题掩盖另一个问题。
- 新增一个默认初始化场景观察 TCO 的真实创建；保留原“用户明确不要生成地图”场景，验证显式边界优先于默认行为。
- 顶层 Setup 状态、测试表面就绪状态和完整 Loop 状态分别维护。三者回答不同问题，不能用一个 `ready` 互相替代；当前环境和宿主能力仍只在当轮报告。
- Setup 状态与新鲜度、测试表面矩阵和资产索引都放入唯一 `.test-privateer/project.md`，不新增第三份初始化产物。配置契约版本只在字段语义不兼容时升级。
- 资产索引替代分散的资产位置和证据保留段落，统一记录权威位置、责任、访问、保留／失效和恢复入口；缺失资产只记录状态，不创建空目录或占位文件。
- 测试表面状态描述项目级约定和驱动是否可定位，不缓存当前机器、账号、网络或服务的短期可用性。

## Risks / Trade-offs

- [问询过多] → 只确认会影响范围、安全、证据、门槛或责任归属的决定；每轮一个问题。
- [配置膨胀] → 不新增文件；新增字段集中在 Setup 状态、测试表面矩阵和资产索引三处，并删除重复的证据位置段落。
- [状态名称过多] → 顶层、测试表面和 Loop 状态在模板中分区，并明确各自回答的问题。
- [长期状态快速过期] → 保存来源快照和具体失效条件；重跑 Setup 时按变更来源重新校准。
- [TCO 内容不足] → 允许标记草案和取证任务，但要求实际来源、项目关系、覆盖与风险内容，禁止空模板。
- [Setup 过重] → 复用专项方法并只建立足以支撑后续影响判断的基线，不要求一次写完项目百科。

## Migration Plan

现有配置通过重跑 Setup 更新受管区；未确认字段留为未决项，不覆盖人工内容。新规则只影响以后执行的 Setup，不迁移或猜测旧项目决定。
