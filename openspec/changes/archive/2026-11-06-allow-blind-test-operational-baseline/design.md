# Design

## Context

参见 [proposal.md](proposal.md)。当前实现已经允许“稳定且不含开发材料的已声明宿主基线”，但仍将未声明的父级规则和全局能力默认判为污染，评测也因此把读取全局 RTK 的首轮 worker 归为环境错误。

## Goals / Non-Goals

**Goals:**

- 以内容和来源作用判断污染，而不是以全局、项目级、自动注入或父级继承判断。
- 保留新会话、开发材料隔离、真实调度和证据审计要求。
- 让测试子代理正常使用项目规则、测试 Skill 和本地 CLI。

**Non-Goals:**

- 不允许盲测子代理继承开发聊天、实现理由、diff、开发自测或既有 Finding 结果。
- 不要求把全局规则和 Skill 复制进任务包。
- 不把所有宿主记忆视为安全；携带本次开发材料的记忆仍是污染。

## Decisions

### 1. 区分稳定操作基线与任务特定开发上下文

稳定操作基线包括宿主固定规则、全局 RTK、全局／项目级 Skill、项目 `AGENTS.md`／`CLAUDE.md`、`.test-privateer/project.md` 和获准 CLI。它们定义 Agent 如何工作和如何访问项目，不因自动注入或继承而失去盲测资格。

任务特定开发上下文包括开发会话、实现理由、修复假设、diff、开发自测、既有 Finding 结果、预期缺陷和 rubric。它们可能锚定测试判断，必须从盲测会话排除。

### 2. 未声明基线采用补记而不是作废

发现未预先列出的稳定操作基线时，合成者补记名称、来源及可取得的版本或哈希，并检查其是否包含任务特定开发材料。内容安全时继续判读；包含开发材料且无法剥离时，该 wave 才无效或受阻。

替代方案是要求每个任务包完整枚举所有系统规则、Skill 和 CLI。宿主通常无法完整导出这些内容，也会让盲测成本高于其证据价值，因此不采用。

### 3. 用现有首轮记录纠正评测判读

首轮 worker 读取全局 RTK 和项目 `AGENTS.md`，但没有读取开发聊天、diff 或既有 Finding。该行为应作为“允许使用稳定操作基线”的正例，不需要为了改变分类重新消耗模型运行。

## Risks / Trade-offs

- [项目规则可能夹带本次开发结论] → 按内容审计；携带任务特定结果时仍隔离或使 wave 无效。
- [不完整记录降低可复核性] → 至少记录可观察到的基线名称、来源、版本或哈希和 Skill 加载轨迹。
- [规则放宽被误解为允许共享历史会话] → Skill、模板、规格和评测判据都显式保留开发会话与结果隔离清单。

## Migration Plan

1. 修改契约测试和行为评测材料，固定允许基线与禁止开发材料的边界。
2. 更新 Loop Skill 和轮次模板。
3. 用现有完整轨迹重新判读首轮 worker，并运行静态与 OpenSpec 验证。
4. 保留活动 change，等待用户确认后再同步规格、归档和本地 Skill。
