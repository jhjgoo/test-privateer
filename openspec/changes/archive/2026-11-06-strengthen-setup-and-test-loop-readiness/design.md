# Design

## Context

`setup-test-privateer` 已覆盖项目事实、测试入口、框架、安全、责任和证据位置，但缺少完整 Loop 专用完成门禁；`running-test-loop` 已有轮次、盲测、阶段证据和单一合成者规则，但默认“缺少配置不阻塞”，使完整闭环可能在执行中才补问架构。外部参考的共同经验是：Setup 先固定后续 Skills 依赖的权威入口、状态存储、验证器、隔离和责任模型；普通任务不强制接入。

## Goals / Non-Goals

**Goals:**

- 完整 Loop 前固定项目级资产、验证器、隔离、责任和风险边界。
- 普通 Setup 对影响交接与判定的治理未知也要确认，但不强制配置完整 Loop 架构。
- 将 Setup 完成状态与完整 Loop 就绪、当前宿主能力、环境验证和测试执行分开。
- 保留普通单层任务的短路径。

**Non-Goals:**

- 不在 Setup 中生成 TCO、验证器、测试用例、CI 或任何产品/测试代码。
- 不把具体模型名、当前宿主临时状态或每轮预算写成长期项目配置。
- 不要求所有项目先完成 Setup 才能执行普通测试。

## Decisions

1. **用项目配置内的 Loop 就绪状态连接 Setup 和 Loop。**
   - `ready` 只表示项目级架构决定可定位。
   - `awaiting_user_confirmation` 表示还有必须由用户确认的架构项。
   - `blocked` 表示用户已确认缺少某项架构（常见为验证器）且记录了恢复入口。
   - 备选方案是让 Loop 每次自行调查，但这会重复提问并造成晚阻塞，故不采用。

2. **Setup 只确认架构，不创建执行设施。**
   - 验证器缺失时记录后续补建入口，完整 Loop 执行保持受阻。
   - 这避免 Setup 越权生成验证器或用空文档冒充可用资产。

3. **完整 Loop 预检先于 Run 创建和产品执行。**
   - 配置未就绪时进入最小 Setup，不先创建一套临时 Run 状态。
   - 普通单层请求不经过该门禁。

4. **当前宿主子代理能力仍由 Loop 运行时检查。**
   - 项目配置不保存“本机是否有子代理”这类临时事实。

5. **已确认的阻塞与旧 Run 恢复不重新决策。**
   - `blocked` 沿恢复入口停下，不重复问已经确认的延期决定。
   - 旧 Run 先只读核对原 ID 和有效证据；缺少项目级架构时先补最小 Setup，就绪后沿原 Run 继续。

## Risks / Trade-offs

- [问询过多] → Setup 沿用“每轮只确认一个主题”；仓库事实和已有权威来源直接引用，不重复问。
- [配置字段膨胀] → 模板只新增 Loop 必需架构字段，复用现有责任、证据和验证器章节。
- [完整 Loop 被误判未就绪] → `ready` 不要求 TCO 已存在或环境已运行，只要求资产入口和架构决定可定位。

## Migration Plan

1. 更新项目配置模板和 Setup 规则。
2. 更新 Loop 启动契约和预检顺序。
3. 扩展静态契约测试与最小行为评测场景。
4. 现有无配置普通测试行为保持不变；已有完整 Loop 场景在真实模型评测中按新预检补测。
