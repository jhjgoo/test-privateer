# Design

## Context

当前 `prompt-eval` 已要求固定模型宿主、盘点 Prompt 表面、基于真实失败给最小修正并做前后对照。缺口不在整体流程，而在企业多层 Prompt 中容易漏掉协议权限、输入裁剪、程序校验和运行可观测性。

## Goals / Non-Goals

**Goals:**

- 让审查维度覆盖消息角色、指令来源、上下文充分性、结构化输出和运行成本证据。
- 保持新增规则可判定，避免把某个厂商行为或缓存阈值写成跨平台定律。

**Non-Goals:**

- 不搭建 Prompt 平台、不引入模型路由、不规定统一消息顺序或缓存阈值。
- 不把 Prompt 评测扩展成完整 Agent 评测；工具与环境归因仍交给 `agent-eval`。

## Decisions

1. 新增维度写入现有参考文件，主 Skill 只加简短选择规则。这样保留当前流程，不把 Skill 变成清单执行器。
2. 角色与层级按“实际 API 元数据”审查，不按 Markdown 标题或 XML 标签推断权限。
3. 上下文审查采用“最小充分”而非“越短越好”；删除材料必须证明不承担判断条件。
4. 缓存、质量、成本、延迟分别取证。缓存命中只作为运行效率证据，不作为正确性证据。
5. 用 SkillEvaluator Tier 1 做静态门禁；Tier 3 用同条件旧版／新版双臂比较，覆盖目标失败和邻近正常场景。默认 Codex 矩阵为 GPT-5.6-SOL 与 GLM-5.3。
6. 用户进一步明确盲测与可选框架需求，继续同一 change。执行会话只见本组指令，独立评审只见匿名产物和判据；版本映射在锁分后揭盲。无法遮蔽的指令特征或轨迹泄漏单独披露，不保证天然双盲。
7. 在 `prompt-eval` 加按需读取的接入参考，沿用 e2e 的“领域 Skill 管判据、官方 Skill 管工具”模式。客户选用后读取官方 `skillevaluator`；不新增产品 Skill、复制上游命令手册或自动安装。仓库验证协议保持维护专用，客户自选的引用不继承其模型／策略。
8. SkillEvaluator 的带／不带 Skill 比较与旧版／新版比较分别回答贡献和优化问题。普通 Prompt 若需改变消息角色、工具或加载方式才能运行，则沿用原宿主的框架无关配对设计，不能用包装后系统代替原对象。
9. 本次追加行为使用追加前的完整工作区快照作为增量基线，新增四个来源明确的代表案例并保留原四例。独立审阅修正了 Skill 对象也需核对运行等价性、未选框架不阻断已授权原入口对照，并补仅选择框架的授权反例；中止初轮七例运行并保留。最终两版、两个默认模型各八例一次，共 32 次实际尝试，另计 Judge；本轮不主张 Skill 贡献，因此用官方 `--skip-baseline` 省去无 Skill 组。历史 HEAD 比较保留原范围与失败，不拼接本轮证据。

## Risks / Trade-offs

- 新增维度可能诱导逐项套清单；主 Skill 保留“按现象选择”的要求。
- 缓存与成本数据常缺失；只能形成待验证风险，不能升格为失败或改善结论。
- 单次 Tier 3 不能证明普遍提升；两版都通过时必须保留“未观察到提升”的结论。

## 行为反证后的最小修正

最终八例首轮发现 GPT 新版在 `schema-cache-overclaim` 中正确拒绝成本和业务提升，却将仅有新版 Schema 达标数据改写为“结构通过率提高”。在第 3 节审查主张处明确每个指标都需要自身同口径前后基线，不能借其他指标的基线或在替代结论中补改善。原始失败保留。

对该修正使用修正前候选与修正后候选做独立双模型配对：冻结 `schema-cache-overclaim` 和邻近 `minimal-sufficient-context` 两例，其他配置不变，共 8 次尝试。该运行只验证新增的比较证据规则，不与前一矩阵拼成一次运行，也不重新解释前一矩阵为全部通过。
