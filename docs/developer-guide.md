# 黑帆测试官：研发使用教程

从接需求到提测，按当前工作选择入口。无需每次走完整流程，也不用记住全部 Skill 名称。

## 它能帮研发什么

> 黑帆测试官是研发的质量搭档：动手前，帮你发现需求歧义、规则遗漏和方案风险，减少返工；开发中，梳理改动影响，设计关键场景并编写有效单测；出问题时，用复现和对照证据缩小原因范围；提测前，选择重点回归，说明已验证内容与剩余风险。让你更清楚“为什么这样实现、怎样证明做对了、改动可能影响哪里”。保障来自可追溯的规则与实际验证，不承诺零缺陷。

## 开始使用

在支持 Agent Skills 的客户端中安装全集：

```bash
npx skills add jhjgoo/test-privateer --skill '*'
```

安装范围与更新方式见 [README](../README.md)。随后显式调用 `test-privateer`，说明当前阶段、相关材料和希望得到什么。下方提示词中的材料描述需替换成实际文件、链接或粘贴内容。

Workbuddy 用户可在已安装的“黑帆测试官”中使用下面的话术；其中的专项 Skill 名表示包内能力，由主入口读取对应参考模块。

准备好需求或 Spec、代码位置、目标版本；需要运行测试时，再提供测试命令、环境和允许操作的范围。能从项目自行调查的事实，无需重复整理。

| 开发阶段 | 什么时候用 | 你能拿到什么 |
| --- | --- | --- |
| 接需求 | 规则不完整，不确定怎么实现 | 待确认问题、业务边界、可验证的预期 |
| 评方案 | 担心方案只修 badcase，或设计、任务和需求对不上 | 样例耦合、作用点错位、契约链断点和验证缺口 |
| 写代码 | 不知道先测什么、如何写有效单测 | 关键行为切片、测试代码和实际运行结果 |
| 改代码 | 担心影响旧功能 | 影响范围、重点回归项及选择理由 |
| 改界面 | 样式、交互和使用体验需要自查 | 任务中的体验问题、判定依据与补证动作 |
| 查问题 | 有异常，但原因不确定 | 复现条件、原因假设、支持与反对证据 |
| 提测 | 需要说明完成程度 | 已验证行为、未执行项、剩余风险和证据 |
| 复盘 | 返工后希望下次改变做法，或错题本已堆积 | 去重后的教训、晋升依据和项目规则更新 |

## 1. 接需求：先把容易返工的地方问清楚

```text
使用 test-privateer，按项目任务结合当前代码库分析这份需求。
先找会影响实现的规则歧义、上下游影响和关键边界，说明哪些需要产品确认，
以及答案会改变什么。本轮只做分析。
```

例如“新增订单取消功能”，需要先弄清：哪些状态能取消？支付和取消同时发生怎么办？库存何时释放？规则未定的部分会保留为问题，已明确的部分可以继续。

读结果时，优先处理会改变接口、数据和状态设计的问题。项目任务会读取或补齐项目测试上下文；仅需分析所给材料时，可明确说“独立分析，仅基于这些材料，在对话交付”。

## 2. 评方案：检查是否已经足够指导开发

```text
使用 checking-solutions，质检这份已经形成的解决方案。
结合原问题、已确认规则和现有证据，检查是否存在只针对当前 badcase 的判断、
作用点错位、影响范围遗漏或无法证明方案有效的验证设计。
只报告具体位置、直接证据和最小补证／修正方向，不重新生成整套方案。
如果这是 SDD 变更包，再加深检查规格、任务、实现证据和归档事实。
```

适用于普通研发、修复和实施方案，也适用于 Spec Kit、Kiro、OpenSpec、BMad 等 SDD 流程。拿到结果后，先处理会让实现走偏或验收无法判断的问题。质检结论需区分方案文本是否闭环与实现是否已经验证。

## 3. 开发中：让单测保护业务行为

以下示例假定“已支付订单不能直接取消”已由业务确认：

```text
使用 writing-unit-tests，为“已支付订单不能直接取消”编写单元测试，
沿用项目框架。在本地测试环境运行目标测试，确认断言依据和失败原因，
交付测试文件与结果。本轮不修改生产代码。
```

新行为尚未实现时，测试应当因为该行为缺失而失败；导入错误、环境故障不算有效验证。研发据此实现，再运行测试。为已有功能补测试时，第一次通过也正常，但仍要检查它能否识别错误行为。

该能力负责测试设计与验证，完整的实现、重构由研发或开发 Agent 承接。需要进一步验证接口协作或业务全流程时，应补充相应层级的测试。

## 4. 改动后：选出有依据的回归范围

```text
使用 test-privateer，基于这次 diff 和相关需求选择回归测试。
覆盖直接变化、受影响的上下游及关键旧行为，说明选择和排除理由。
允许在本地隔离测试环境执行已有测试，保留命令与实际结果。
```

看报告时关注“每条测试保护什么”，以及哪些重要行为仍没有证据。项目要求的全量检查仍需完成。执行发现新的影响范围时，再调整回归集。

## 5. 出问题：从现象追到可验证的解释

```text
使用 test-privateer，调查“取消请求成功，但库存没有恢复”。
相关日志、版本和复现步骤如下。
请区分观察事实、原因假设和已验证结论，优先使用现有证据，
列出仍需取证的部分。本轮先调查原因。
```

尽量提供同一次请求的输入、输出、日志、时间和状态变化。若需要实验，明确允许使用的测试环境与操作范围。修复后，要回到原始场景验证，并补充能再次发现该问题的回归测试。

例如，补偿任务重试后库存恢复，能支持恢复措施有效；要确认最初为什么没有恢复，仍需检查原始事件、处理过程及其他可能解释。

## 6. 提测前：让完成声明有依据

```text
使用 test-privateer，根据需求、diff 和本次测试记录，评估是否足以支持提测。
列出已验证行为、失败或未执行项、未覆盖风险，以及需要补充的证据。
结论请附来源。本轮基于已有记录评估。
```

交接给测试同学时，保留需求版本、变更范围、测试结果和剩余问题；需要脑图评审时，可把定稿用例导出为 XMind，Markdown 用例继续作为权威来源。

## 7. 开发 Agent 或 Prompt：先明确测什么

审查 Prompt、Skill 或工具描述时使用 `prompt-eval`：

```text
使用 prompt-eval 审查这次 Prompt 修改。
目标模型和宿主如下，请定位实际生效的 Prompt 表面，
从真实失败提出最小修正，并设计目标失败、邻近正常和边界场景。
没有前后对照证据时，不要声称 Prompt 已优化。
```

评估完整 Agent 时使用 `agent-eval`：

```text
使用 agent-eval 质检这个 Agent 的现有评估方案。
请区分模型、Prompt、工具、权限、编排和环境影响，
检查任务结果、策略合规、轨迹、稳定性和成本的证据，
将 Agent 失败、环境错误和无效案例分开。
本轮只审查和补测试设计，不搭建评测平台。
```

`prompt-eval` 关注 Prompt 在当前模型、宿主和任务中的适配；`agent-eval` 关注完整系统。若 Agent 失败已定位到 Prompt，前者接收失败场景和直接证据继续纠偏；Prompt 修改后再回到系统级场景验证。

需要完整操作步骤、联动案例、可复制提示词和评测证据解读时，阅读[《Prompt 与 Agent 评测实战教程》](prompt-agent-eval-guide.md)。

## 8. 改界面后：评审任务中的体验

```text
使用 reviewing-ui-ux 评审这次界面改动。
目标用户与任务如下，已有设计约定、改动前后截图和操作记录。
请检查关键元素、视觉呈现及反馈恢复是否支持任务，
按问题选择走查、设计对照或其他合适方法，说明依据和证据缺口。
本轮先评审材料，不执行或修改产品。
```

也可以直接向 `test-privateer` 提出相同请求。截图能支持遮挡、裁切和层级判断；键盘路径、失败恢复和实际保存结果需要对应操作证据。只有截图时仍会完成可见部分评审，不要求先安装测试工具。

例如改了弹窗，除样式外，还应核对进入、关闭、出错后用户能否继续原任务。扫描零告警不能代替动态路径检查；自动操作成功也不能证明首次用户容易理解。若目标是持续自动反馈，转入 `designing-test-automation` 设计检查。获准实施时再沿用项目工具编写、运行测试。

## 9. 返工之后：维护错题本与项目规则

```text
使用 maintaining-project-lessons 整理这些修复和审查记录。
请沿用项目的错题本、规则位置和统计口径，区分同一事故的多个补丁与独立复发。
记录原始失败、纠正办法、验证状态和适用边界；有足够依据时更新规范与 Agent 入口。
本轮允许修改这些项目文档，不运行产品测试、不建立定时任务、不发外部 Issue。
```

这个入口可独立使用，也可由 `test-privateer` 路由。只有未解释现象时，先由 `investigating-findings` 取得必要证据；当前补丁是否对症则由 `checking-solutions` 判断。维护教训会保留这些工作的真实状态，不替代修复和验证。

已有规范后同类错误再次出现，会更新原教训，并查入口、规则表达与验证是否真正覆盖错误路径。晋升后保留证据与规范指针，避免两份规则分别修改。示例结构与来源见 [维护指南](../skills/maintaining-project-lessons/references/maintenance-guide.md) 和 [来源说明](../skills/maintaining-project-lessons/references/sources.md)。

没有特殊约定时，使用项目根目录 `LESSONS.md` 保存教训，长期规则直接写入根目录 `AGENTS.md`；已有规范位置继续沿用。AGENTS.md 中保留原有项目要求，规则只写适用条件、动作和检查方法，详细事故证据留在错题本。

## 产物在哪里，下一次如何继续

项目任务维护唯一的 `testing/TCO.md`，汇总业务与系统关系、覆盖情况和长期风险。每个需求的测试分析与用例分别保存，详细依据按需拆分；优先沿用已有需求目录，否则放在 `testing/requirements/<需求前缀>/`。

已有产物时，可以这样继续：

```text
使用 test-privateer，先读取上次的测试分析、用例和执行记录。
这次变化如下，请更新受影响的规则、测试项和回归建议，保留原始执行证据。
本轮先更新分析与设计。
```

## 能力边界

- 单元测试支持编写与验证；只请求测试代码时，生产代码不在修改范围内。
- 不确定在哪一层测试时，使用 `designing-test-automation` 选择方法；明确要写接口或端到端测试时，分别使用 `writing-api-tests`、`writing-e2e-tests`。
- 两个编写入口都覆盖准备、代码、运行、失败判断与交接。已有框架优先复用；纯接口不必装浏览器；合适的无框架 Web 项目可按需取得官方 e2e Skill。
- 只设计不执行。模型连接、依赖版本与环境可用性需要核实；不能把 Web 夹具实测扩展为移动端或所有框架已验证。实测范围见[自动化评测](../evals/test-automation/README.md)。
- 单测通过只支持相应行为，真实集成和业务全流程仍需对应验证。
- 环境不可用或未运行的测试会明确记录；提测、发布与风险接受由团队结合实际证据决定。

更多方法与完整案例见[通用使用教程](guide.md)。

### 任务升级

当请求只描述“测试一下”“帮我看看”或用户不知道如何提问时，先使用 `shaping-ai-tasks`。它会把局部动作升级为最终目标、交付物、原始材料、专业方法、验证方式和下一步；目标已经明确时直接进入测试专项。
