# 面向任务的测试 Skill 优化方案

目标：让用户通过 AI 与启发式方法深入理解需求，将分析转成有效的手工用例、单元测试、接口自动化和页面自动化，并通过执行证据持续调整测试。

设计依据：已确认的团队使用需求。测试新人和 FDE 工程师用于代表真实试用场景；Skill 不设置职业、资历或团队模式。

本方案已完成本期指令、路由与教程修改，并同步本地安装。此前的目标澄清、产物表达和优先级修复已单独提交为 `8b639b1`。本轮尚未提交；真实使用验收仍待后续任务验证。

本期范围调整：接口自动化和页面自动化仅补充任务入口，接收测试目标、整理测试设计并明确后续交接内容。具体测试框架由用户选定后再接入；本期不实现这两个编写 Skill，不生成或运行对应自动化代码，不安装框架或添加适配器。其他优化范围保持不变。

## 1. 共用方法，按任务进入

主入口保持简短：测试职责、当前目标、上下文缺口、能力路由和停止边界。方法细节留给子 Skill。

建议定位：

> 你是用户的测试搭档。共同理解业务与系统，发现值得验证的问题，设计具体测试，在条件具备且获得授权时执行，并用证据指导下一步。根据当前任务、已有信息和用户反馈调整解释深度与交付形式。

路由依据是用户当前需要、已确认上下文、实现阶段和可访问资源。用户明确请求单元测试或某个启发式工具时，从该能力进入；仅在缺失信息会影响正确性时补分析，不强制重走全生命周期。

| 当前需要 | 负责能力 | 交付边界 |
| --- | --- | --- |
| 不清楚这轮要解决什么 | setting-test-mission | 确认目标、范围和下一步 |
| 业务行为、上下游或预期不清 | clarifying-test-basis | 具体问题、证据、认知变化及受影响测试 |
| 项目测试地图不足 | mapping-project-test-space | 可持续维护的项目 TCO |
| 当前需求或变化需要分析 | analyzing-change-for-testing | 测试重点、条件、依据和未决项 |
| 需要展开内容或建立模型 | SFDIPOT、MFQ、PPDCS 相关 Skill | 按各工具职责交付，保留必要模型与追溯 |
| 需要章程或具体用例 | designing-test-experiments | 具体测试用例、测试任务或探索章程；另说明执行条件是否已核实 |
| 不确定自动化层级和投入 | designing-test-automation | 层级、边界、首个行为切片和维护成本 |
| 需要单元测试代码 | writing-unit-tests | 测试代码、运行结果或有效 RED |
| 需要接口自动化 | designing-test-automation 的接口入口（本期新增分支） | 业务场景、接口依据、数据与预期、待接入框架信息 |
| 需要页面自动化 | designing-test-automation 的页面入口（本期新增分支） | 用户任务、操作与结果、观察点、待接入框架信息 |
| 需要执行已有测试 | running-test-sessions | 实际观察、未执行项和下一步 |
| 测试失败或观察可疑 | investigating-findings | 区分原因及修复建议／授权范围内的修复衔接 |

两个入口先作为主入口的意图路由及 designing-test-automation 内的明确分支，不创建空壳 Skill，也不调用尚不存在的 writing-api-tests／writing-ui-tests。框架选定后再决定独立 Skill 的职责、命名及接入方式。

## 2. 共同探索的交互规则

修改 test-privateer、setting-test-mission、clarifying-test-basis。

- 已明确的目标直接沿用。宽泛请求先用最少调查形成具体理解，再确认会改变本轮产物的目标。
- 首轮问题从真实业务例子出发：谁做了什么、什么信息不足、答案会改变哪项测试。不要求用户理解方法缩写或选择职业模式。
- 用户知道的经验可以补充事实；规则能否被确认取决于其实际责任和证据，不能仅凭职称判断。
- 用户不知道答案时，记录应查资料或确认人，暂停依赖该答案的部分，推进其他已明确行为。未向用户提问不能视为“问不到”。
- 用户明确要求自主分析时允许先交草案；列出影响结论的假设，不能将假设写成确定预期。
- 解释与当前工作绑定，例如说明为何用决策表揭示规则冲突；不自动插入方法论课程。

验收例：只给未实现 PRD 并要求“探索性测试”时，应先确认本轮目标；明确要求“先自主分析并输出用例”时应推进；单项规则未知时其他明确测试可继续。

## 3. 分析到测试的衔接

保留海盗派的价值、风险、证据主线，明确工具各自贡献：

- SFDIPOT 盘点业务与系统中的产品元素、关系和未知，帮助收集信息；扫描结果不能直接冒充完整测试用例。
- MFQ 组织单项能力、功能交互和质量关注，形成有产品依据的候选测试点。
- 风险分析决定选择、顺序和深度，同时考虑业务价值未实现与负面伤害。
- PPDCS 对选中复杂行为形成实际模型，再派生可追溯测试条件。工具交给下游的模型和覆盖依据要保留，用户正文按需要展示。
- 测试设计将选中条件转成数据、动作、观察和判断依据；同一业务行为可由不同层级取得互补证据。

修改 analyzing-change-for-testing、modeling-tests-with-ppdcs、designing-test-experiments、challenging-test-designs。修正“隐藏模型使下游失去模型”的可能歧义；审查规则不能要求 SFDIPOT 独自输出完整测试点。

验收要求：下游测试能说明它验证哪个业务行为、预期来自哪里、为何选这个层级。业务正常路径和产品价值要有明确覆盖或排除理由，不能只围绕并发、幂等和安全异常展开。

### 3.1 明确设计产物与执行条件

真实反馈暴露了“深化为可执行测试”的歧义：用户无法判断下一步是写用例、写自动化代码，还是实际运行。将本问题并入分析、设计、执行的现有交付规则，不新增 Skill 或流程层。

| 工作 | 需要回答的问题 | 可以交付什么 |
| --- | --- | --- |
| 测试分析 | 哪些行为值得检查，为什么，规则还缺什么 | 测试点、测试条件、必要模型与依据 |
| 测试设计 | 用什么数据和动作，在哪里观察，依据什么判断 | 具体用例、测试任务或探索章程；规则不清的部分保留为草案 |
| 执行准备 | 目标版本、账号、数据、操作入口和观察手段是否具备 | 已核实的执行条件及具体缺口 |
| 测试执行 | 实际做了什么，观察到了什么 | 操作或命令、实际结果、证据和后续问题 |

这是交付含义的区分，不是强制串行流程。探索过程中可以边学习、边设计、边执行；已经明确且获准的任务可直接进入相应工作，不为每层另建文档。

“用例已写好”只说明设计进度。“可执行”说明在指定目标和环境中已具备开展该测试的条件，不等于已执行、已通过或获准执行，也不意味着它是自动化脚本。测试设计可以早于功能实现。

规则未定时只暂停依赖该规则的精确预期，其余明确部分继续设计。探索章程允许以调查未知为目标，但要说明如何观察、收集什么信息和何时转向，不能将未知规则用于通过／失败判定。

职责归属：designing-test-experiments 定义设计完成与执行就绪的区别；analyzing-change-for-testing 在交付时点名下一项具体产物；running-test-sessions 核实执行条件并记录实际证据；主入口只使用一致路由措辞，不复制整套定义。

## 4. 根据产物用途调整表达

修改 analyzing-change-for-testing、designing-test-experiments、clarifying-test-basis 和相关交付模板。

- 分析摘要用业务名称、场景例子和结果说明问题。
- 评审与手工执行以 Markdown 表格为主，复杂场景另列必要步骤。
- 编写自动化时保留准确字段、接口、选择器、数据准备、断言和运行命令；技术细节是否进入正文取决于它是否帮助当前读者执行或判断。
- 术语需要解释时就地说明，避免中文自造词和空泛表述。接口状态码等只在有契约依据时成为确定预期。
- 实现约束注明来源；未规定实现方式时，只写必须成立的行为与可观察结果。
- 关联风险与本轮安排保持分离，沿用团队已有优先级语义；未执行不写成通过。

验收例：同一“修改配置不影响历史”的测试，业务评审能看懂场景，自动化实现能找到字段和断言；两种表达保留相同业务含义。

下一步建议应交代对象、动作及将得到的产物；条件缺口会影响推进时一并说明。优先使用“为审批回写编写具体用例”“核实任务暂停和回写观察方式”“运行已准备好的用例”等明确表述。仅写“深化测试”“补齐契约”“形成可执行测试”不足以让用户选择下一步。

本次案例的建议表达：

> 下一步为企业关联、创建时配置快照和审批回写编写具体测试用例，补充测试数据、操作步骤和预期结果。规则不清的分支单列待确认项；目标版本和环境尚未核实，因此这一轮交付用例设计，不开始执行。

这是说明表达要求的例子，不是所有场景都要照抄的固定结尾。用户只要求分析时先交付分析和建议；已经要求设计时直接设计，无需重复确认。

## 5. 自动化能力补齐

### 自动化选择：designing-test-automation

用最小但保留目标行为的层级取得证据。稳定业务规则适合单元测试；认证、持久化、事务和服务协作适合接口／集成测试；用户操作、反馈、导航与跨页面任务适合页面测试。不是每个业务场景都要在三层重复一遍。

用户已指定合理层级时直接进入相应分支，不强制先生成自动化策略文档。单元测试沿用 writing-unit-tests；接口与页面自动化本期停在测试设计和框架交接，不进入笼统的“当前技术栈实现流程”。

### 单元测试：writing-unit-tests

保留独立预期依据、公开行为边界、最小有区分力样本、受控时间与数据、有效 RED 判定。沿用调用方 TDD 流程，不另建开发流程。

收紧两个细节：既有行为首次通过是有效现状，不为追求 RED 人为制造失败；新行为测试意外通过时调查是行为已存在还是断言无效。修改测试所需的小调整与修改产品行为，按当前授权区分。

### 本期接口自动化入口

输入：选中业务行为／测试条件、接口契约、已有代码与测试约定。

交付业务测试场景、关联接口／契约、身份与测试数据、预期结果及来源、必要的状态或下游观察、待确认项。已有项目框架信息可记录，不能据此自行启动新能力的实现。明确告知本期入口只完成设计，框架接入尚未实现。

以下作为框架选定后的编写质量要求，延期实施与验收：

- 以真实业务数据和身份发起请求，断言响应内容及必要的持久化状态或下游结果，不能只检查 200。
- 覆盖已选规则、权限隔离、无效输入、状态变化、失败恢复；幂等和并发按实际风险选择。
- 数据独立、可清理、可重复运行；认证和多租户上下文明确。异步结果有界等待，不使用任意固定睡眠。
- 明确测试实际跨过哪些边界。只模拟外部依赖时，可以验证本地协作；完全模拟被测服务不能声称验证真实集成。
- 预期来自规则或契约，不复制当前响应生成 expected。契约缺失只阻塞相关断言。

后续阶段交付：测试文件、最小运行命令、实际结果、行为依据、替身边界和未覆盖部分。启动条件为用户选定框架并确认接入范围。

### 本期页面自动化入口

输入：真实用户任务、选中测试条件、页面／原型／实现、已有浏览器测试约定。

交付真实用户任务、前置状态、操作流程、可观察业务结果、错误与恢复场景、待确认项及仍需人工判断的体验问题。明确告知本期入口只完成设计，框架接入尚未实现。

以下作为框架选定后的编写质量要求，延期实施与验收：

- 用角色和任务命名测试，完成有意义的操作链，再验证用户目标及必要系统结果。
- 优先用角色、可访问名称、标签或稳定测试标识定位，避免易碎的 DOM 层级和样式选择器。
- 检查加载、错误、保存、刷新后状态、失败后的输入保留及恢复等与当前任务相关的体验。
- 等待具体页面或业务状态；准备独立账号和数据；减少依赖其他测试执行结果。
- 后端被模拟时说明只验证页面行为；连接真实服务时才描述相应端到端证据。
- 自动化可以验证具体交互和可访问性检查，不能据此断言整体易用性良好。需要主观或真实使用判断的部分交付人工探索任务。

后续阶段交付：代码、运行命令、实际结果、失败定位所需截图／轨迹、业务依据及仍需人工观察的体验问题。启动条件为用户选定框架并确认接入范围。

## 6. 执行、调查与生命周期

修改 running-test-sessions、investigating-findings、designing-test-automation 及 artifact-routing.md。

- 独立路径在对话、用户指定文件或已有测试目录交付；项目路径复用 TCO 与 Spec。不存在 TCO／Spec 不阻止已明确且获准的单项测试工作。
- 开发前先分析关键行为与规则缺口，并形成测试条件；自动化可以按 TDD 或实现可用程度逐步落地。
- 开发中把测试交回通用 TDD／SDD 工作流。已具备的单元测试及已有测试执行能力按授权完成；本期新增的接口／页面入口停在设计交接，明确尚不提供代码实现与运行。
- 实现可运行后按所选层级执行；部署、真实外部服务及生产数据等边界根据实际授权处理。
- 执行条件尚未调查时写“版本／环境待核实”，不能据此断言功能未实现或环境不可用。只有有证据时才标记待实现、待补环境或可执行。保留现有用例状态体系并补充未知条件的表达，不要求增加审批流或独立准备文档。
- 失败先区分测试错误、实现偏离、环境数据问题和规则歧义。测试错误可修；产品实现仅在已有开发／修复授权内调整；不靠删断言、跳过测试或扩大替身范围换取通过。
- 维护一份项目地图；需求分析与用例默认分文件，详细依据按需拆分，使用稳定共同前缀。已有需求目录沿用，否则使用 testing/requirements/<前缀>/。按任务阶段创建有内容的产物，不生成空文档。
- 历史设计、测试和验证记录按相关性读取并核对有效性。文件存在或测试名称命中不能证明已经覆盖或通过。

## 7. 实施顺序和文件范围

| 批次 | 文件 | 完成标准 |
| --- | --- | --- |
| 1：通用职责与共同探索 | test-privateer、setting-test-mission、clarifying-test-basis | 不按职称路由或判定权限；目标明确直接推进，关键歧义带例子询问 |
| 2：分析与交付衔接 | analyzing-change-for-testing、modeling-tests-with-ppdcs、designing-test-experiments、challenging-test-designs | 模型向下游完整交接；正文适配用途；预期有来源；区分设计完成与执行就绪；下一步点名具体产物 |
| 3：自动化入口 | test-privateer、designing-test-automation、writing-unit-tests | 单元测试优化照常；接口／页面入口有明确设计产物、框架待接入说明和停止边界，不新增编写 Skill |
| 4：执行和资产 | running-test-sessions、investigating-findings、artifact-routing.md | 独立／项目路径均可工作；执行条件核实与授权分开；未知不误标缺失；失败分类和修复范围明确 |
| 5：发布材料 | README.md、docs/guide.md、本地对应安装副本 | 标明接口／页面仅为设计入口；不将入口计为两个新增 Skill；示例和本地内容与实际能力一致 |

按批次修改并查看真实产物，不建设新评测器、术语转换器、角色问卷或单独路由框架。现有主入口增加接口／页面自动化的意图路由，均进入已有 designing-test-automation 的设计分支；通用规则以替换旧措辞为主。

## 8. 真实使用验证

选用现有真实需求作贯穿样例，并加一个不同业务的小样例检查是否只适配旧案例。不以字数、用例数、术语命中或覆盖率单独判断 Skill 质量。

| 试用任务 | 观察什么 |
| --- | --- |
| 宽泛请求“对这份 PRD 做探索性测试” | 在扩写完整产物前确认目标；提问有具体依据 |
| “先自主分析并输出用例” | 正常推进，保留假设；明确行为不被局部未知阻塞 |
| 分析后建议下一步，再收到“开始下一步” | 建议明确指向编写用例、准备或执行；后续只承接该具体动作，不自行升级到自动化或运行 |
| 用例设计完整，但未查看目标版本或环境 | 可以报告设计已完成；执行条件写待核实，不称可执行，也不猜测待实现 |
| 已确认任务创建时固定审批模式，尚未确认直审“无法判断”的回写规则 | 已知组合继续设计；未知分支保留待确认预期；不先编预期再补规则 |
| 已有历史 Spec 的需求变化 | 正确继承／修正已有规则，复用有效测试；不将旧行为自动当目标 |
| “为这个业务规则补单元测试” | 预期独立、测试有区分力；区分新行为 RED 与既有行为保护 |
| “给这个已实现接口补自动化并运行” | 识别接口入口，明确本期实现限制，交付业务测试设计与待接入信息；不假称已生成或运行自动化 |
| “从用户操作角度补页面自动化” | 识别页面入口，交付用户任务、预期结果和恢复场景；明确框架待接入，不假称已实现自动化 |
| 没有 Spec 的独立测试请求 | 不创建伪 Spec，完成当前授权范围内的工作 |

真实评审判断能否看懂、是否增加有效测试点、是否减少整理工作；单元测试和已有执行能力用实际运行结果验收。接口／页面自动化本期只验收入口识别、设计交付和诚实的能力边界，代码质量与运行结果留待框架接入阶段。不能仅凭子代理自称 PASS 宣布有效。每轮只针对已出现的问题修正；用户真实调试是最终验收的重要部分。

## 9. 已确认并落实的文档与交互收敛

- 项目关联与写入位置分开；明确相关主动取证，不确定先问是否结合当前项目。
- 同一业务主题集中澄清；当前授权内的调查、整理与审查连续完成，不等待逐次“下一步”。
- 主分析七部分：任务摘要、当前行动、有效规则、动态风险、完整测试点、有效未知、产物与依据链接。
- 项目地图八部分：概览、业务与系统、资料证据、覆盖、长期风险、资源、需求索引、项目待办。
- 四份模板随对应 Skill 分发。需求文档使用标识／首次日期＋短名＋test-analysis／test-cases／test-basis；依据按需拆分。
- 风险在需求或项目的唯一归属处维护；状态为待调查、处理中、已控制、已排除、已接受，有证据可变更或复开。单个测试通过不自动关闭风险。
- 用户确认与原文冲突时更新有效规则及关联测试；原需求未授权修改则列回写行动。过期规则与完成动作退出当前指导，保留原始证据。
