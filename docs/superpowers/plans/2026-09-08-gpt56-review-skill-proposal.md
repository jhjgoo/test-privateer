## 3. Agent 自行完成的闭环

### 成稿与自校

负责组装最终产物的Agent固定当前稿和依据，检查当前范围内的引用及内容；中间模型由上层统一复核，不逐层重复检查。简短澄清、进度回复和无测试语义变化的文字修改不启动完整流程。

Markdown允许沿用项目表达。编号必须回到相应定义和业务含义核对；不能把“全文搜得到同一串字符”当作引用有效。缺号要区分写错引用与遗漏内容，分别修引用或补依据已经要求的内容，不为凑连续编号创造测试。

### Agent 裁决并修正

“成稿者/原作者”明确指Agent。它对意见负责核查、接受、驳回、修正，不是请用户审核审阅者的每一条意见。

- 错号、失效引用、旧内容残留和关联修改遗漏，直接查清并修正。
- 前后表述不同，先对齐对象、范围、阶段、历史版本和事实/目标规则性质。
- 一般规则与具体规则可兼容时，补清适用范围，不扩大规则变化。
- 已声明采用的有效Spec缺少本轮原始文件时，标明核实边界，不仅因未读到原始文件就撤销它。
- 真正无法确定的产品规则保留未知；不为了让报告“无问题”编造预期。

例如，连接记录已解绑后，唯一键可以被新记录占用；Agent应明确两种主体并同步模型和测试条件。这种表达纠错不需要用户批准。若实际业务要求“旧记录复活还是新建记录”尚无任何依据，则才是待确认的产品规则。

### 独立审阅辅助

涉及多份资产、状态/决策模型或重要规则变化时，能力允许则用独立上下文审阅；给原任务、有效规则、当前稿和必要依据。审阅者不拿作者预设的正确答案，也不继续委派子审阅者。

审阅者可以只读返回意见，但成稿Agent仍负责修好最终产物。没有独立审阅能力时继续自校，不要求用户配置工具，也不声称已经独立复核。

### 修后检查与停止

重新阅读每项修改影响到的定义、引用、模型和结论。仍能据现有材料解决的文档错误继续修正，不能留给用户逐项确认。

同一争议没有新证据时，Agent对齐范围后裁决并记录理由，不重新开展全量挑刺。范围外建议不阻塞交付。真正需要业务选择、风险接受或扩大授权时，才提出具体问题；其他内容继续完成。

工具失败或实际修复未完成时，诚实报告未完成状态；不伪装成业务待确认，也不声称复核通过。这个边界用于防止虚假完成，不是把常规纠错转成人工工作。

| 位置/现有指令 | 判断与依据 | 处理及置信度 |

| 前版“局部核对后未解决问题随草案交付” | 把可自行解决的文档缺陷一并退回用户，不满足最新要求 | 替换为按现有证据继续修正；只有真实业务缺口才询问 |

| State主体/身份 | 用户产物有主体混淆；身份判定属于业务模型的必要内容 | 针对性补充，修正效果需看实际产物 |

v3改为观察完整“自校→自行修改→检查修正”的行为：使用原5.6产物的临时副本，允许修改副本，不提供已知缺陷答案，不新增脚本、不执行产品测试、不询问用户批准纠错。已观察到Agent修正编号与状态主体，并在主会话Agent两项反馈后补回拆分时遗漏的共同观察和E2E限制。用户未介入文档纠错；这不是无反馈一次成功或5.6单模型稳定性证明。详见[自校修正试跑](../../research/2026-09-08-gpt56-self-revision-probe.md)。

后续仍需覆盖：
- 修正后的干净稿不产生无依据改动；
- 不同业务的状态主体与ID表达；
- 完整分析自动触发一次，中间模型不重复；
- 仅审查请求不修改已有文件；
- 真正缺少业务规则时问具体问题，其余内容继续完成；
- 独立审阅缺失/工具失败时不虚报已验证；
- 实质修改后复读关联内容，不用旧复核结论覆盖新稿；拆分、合并或改号后，原有观察点与保持要求完整保留。

单次自校成功也不代表稳定修复。部署前需要完成上述代表性验证，并通过skill-eval的行为验证要求。
