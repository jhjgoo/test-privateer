# Prompt 与 Agent 评测实战教程

这份教程面向编写 Prompt、开发 Agent、维护 Skill 或负责 AI 功能测试的研发与测试同学。目标不是搭建一套评测平台，而是用 `prompt-eval` 和 `agent-eval` 判断：当前改动解决了什么、证据是否可信、还可能伤害哪些正常行为。

## 1. 先选对 Skill

| 当前问题 | 使用 | 原因 |
| --- | --- | --- |
| Prompt、System Prompt、Skill、工具描述是否写对 | `prompt-eval` | 检查实际进入模型的指令、层级、冲突和模型适配 |
| 一次 Prompt 修改是否比旧版更好 | `prompt-eval` | 在相同模型、宿主和任务下做前后对照 |
| Agent 能否完成真实业务任务 | `agent-eval` | 结果还受工具、权限、记忆、编排和环境影响 |
| 现有案例、Judge、指标或报告是否可信 | `agent-eval` | 需要同时质检案例、环境、Oracle 和结论 |
| Agent 为什么失败，但还不知道失败在哪一层 | `agent-eval` | 先在完整系统中定位模型、Prompt、工具、编排或环境 |
| Agent 失败已经定位到某段 Prompt | `prompt-eval` | 只修已经定位到 Prompt 表面的部分 |

简单判断：**只改变文字和指令时先看 Prompt；用户结果依赖工具或环境时看完整 Agent。**

## 2. 开始前准备什么

材料不必一次齐全，但缺少的部分要保留为评测边界，不能靠猜补上。

### Prompt 评测材料

- 目标模型、推理设置和宿主，例如 Codex、Workbuddy 或自建 Agent；
- 实际生效的 System Prompt、Skill、工具描述、请求模板和示例；
- 一个真实失败或明确要保护的行为；
- 失败时的输入、实际输出和必要运行记录；
- 修改前版本，以及可以保持其他条件一致的运行方式。

### Agent 评测材料

- Agent 的模型、Prompt、工具 schema、权限、记忆和编排版本；
- 用户目标、初始环境状态和业务规则；
- trace、工具返回、最终产物和环境最终状态；
- 现有测试案例、Judge、指标或评测报告；
- 本次结果要支持的决定，例如继续开发、合并改动或允许灰度。

如果只有“这个回答看起来不好”，可以先收集失败；如果只有模型榜单，尚不足以判断产品里的 Agent 是否可用。

## 3. 使用 `prompt-eval` 评测 Prompt

### 第一步：固定评测对象

先写清楚四件事：

```text
目标模型与宿主：
目标任务：
期望行为：
本轮要保护或改善的问题：
```

同一段 Prompt 在不同模型、宿主、工具权限下可能表现不同。没有这些信息，可以检查内部冲突，但不能声称已经适配目标模型。

### 第二步：盘点完整 Prompt 表面

不要只检查用户贴出的那一段文字。实际行为可能同时受到以下内容影响：

- System Prompt；
- 项目规则与 Skill；
- 工具名称、描述和参数 schema；
- 请求模板和示例；
- 宿主注入的权限与完成条件；
- 模型、推理强度和其他运行配置。

例如，工具描述写“查询订单”，System Prompt 却要求“必须先获得用户确认才能查询”，问题可能来自规则冲突，而不是工具调用能力不足。

### 第三步：从真实行为找问题

重点检查：

- 目标和完成标准是否清楚；
- 同一规则是否在不同位置冲突；
- 应由模型判断的工作是否被写成固定步骤；
- 示例是否把模型锁定在一个表达或 badcase；
- “已经调用工具”是否被误写成“业务结果已经成立”；
- 为修一个案例增加的禁令是否伤害正常场景。

文字长、语气正式或没有使用某种模板，本身不是问题。只有会改变行为、正确性、权限或可验证性的写法才值得修改。

### 第四步：提出最小修改

每项修改都要回答：

1. 它解决哪个已经观察到的失败？
2. 修改发生在真正控制该行为的位置吗？
3. 哪些正常行为可能被误伤？
4. 用什么场景证明它有效？

优先删除冲突、失真和重复规则。不要只是在末尾继续增加“必须”“绝不允许”或一个针对当前关键词的新禁令。

### 第五步：做前后对照

至少准备：

- **目标失败场景**：旧 Prompt 会暴露原问题；
- **邻近正常场景**：不应触发同一限制；
- **必要边界场景**：容易击穿定向补丁或规则边界。

前后版本保持模型、宿主、材料、工具、权限和运行配置一致。开放式任务按风险决定是否重复运行。没有实际对照时，只能说“建议修改”或“等待验证”，不能说 Prompt 已优化。

### 示例：防止工具重复调用

失败现象：Agent 在工具已经成功后继续请求相同动作。

不可靠的修改：

```text
绝不允许连续两次调用同一个工具。
```

它可能误伤失败重试和参数变化后的合法调用，也没有说明 Agent 是否收到了成功结果。

更合理的评测方式是先验证：成功结果及状态变化是否进入下一轮模型输入；若问题确实定位到 Prompt，再修改“何时认为目标已经完成、何时允许重试”的决策依据，并用成功后停止、失败后重试、参数变化三个场景做对照。

## 4. 使用 `agent-eval` 评测 Agent

`agent-eval` 有四个常用入口，先选择当前真正要回答的问题。

### 4.1 设计 Agent 测试

适用于还没有可信测试方案。先定义质量主张，例如：

> 在有权限的测试环境中，退款 Agent 能为符合规则的订单完成退款，并拒绝越权退款。

再根据业务后果选择风险，不必把所有质量维度都平均覆盖。每个场景写清：

- 用户目标和初始状态；
- 业务与权限规则；
- 允许和禁止的动作；
- 期望环境最终状态；
- 必须保留的 trace 或产物；
- 哪个具体错误会导致该场景失败。

优先选择最小场景集，不默认搭建平台或生成大量评测代码。

### 4.2 质检现有评估

已有案例、Judge 或报告时，依次检查：

1. 任务是否可解，规则是否完整；
2. 环境是否可重置，依赖是否稳定；
3. Oracle 是否观察真实结果，并能让已知正确结果通过、已知错误失败、合理替代路径不被误拒；
4. 使用模型 Judge 时，是否用人工确认的正反样例完成校准，并检查重复评分稳定性；
5. 案例是否代表目标用户任务，是否泄漏答案；
6. Agent 能否修改测试、伪造产物或迎合评分器；
7. 当前证据只是可观察、可诊断，还是足以作为发布门禁。

有 trace 平台不等于评测可信；未经校准或表现不稳定的 Judge 只能作为调查线索，不能独立充当发布门禁。

### 4.3 比较两个版本

先声明基线、候选和本轮有意改变的组件。配对比较时，除待测变化外保持以下条件一致：

- 任务和初始状态；
- 环境、工具和权限中的非待测部分；
- 预算、超时和模型配置中的非待测部分；
- Oracle 与评分方法。

分别报告目标改善、邻近退化、高风险变化、环境异常、延迟和成本。多个组件同时变化时，结果可以用于比较完整系统版本，但不能把差异单独归因于某一个组件。不要只给一个平均总分；关键安全或权限场景不能被大量简单案例稀释。

### 4.4 分析 Agent 失败

沿真实执行链逐层定位：

```text
用户目标
→ 模型决策
→ Prompt 与上下文
→ 工具及参数
→ 编排、记忆与 handoff
→ 环境结果
→ 案例与 Oracle
```

优先取得能区分竞争解释的下一条证据。例如：工具调用返回成功，但环境状态没有变化，要先判断工具结果、环境写入和 Oracle，不能直接归因于“模型不聪明”。

结果状态应分开记录：

- `pass`：有效案例中，证据支持质量主张；
- `agent_failure`：Agent 的行为或结果不成立；
- `environment_error`：环境、依赖或工具使本次无法有效判断；
- `invalid_case`：案例、规则或 Oracle 本身不成立。

环境错误和无效案例不能算成 Agent 失败，也不能通过重跑后只保留成功结果来抹掉。

## 5. Prompt 与 Agent 如何联动

推荐使用以下闭环：

```text
Agent 系统失败
→ agent-eval 定位失败层
→ 已定位到 Prompt 时交给 prompt-eval
→ Prompt 做最小修改和前后对照
→ 回到 agent-eval 验证完整系统结果
```

仍以重复工具调用为例：

1. `agent-eval` 检查模型输入、工具结果、状态反馈、循环控制和环境状态；
2. 如果成功结果没有进入下一轮上下文，修编排或状态反馈，不应继续堆 Prompt 禁令；
3. 如果上下文完整，但 Prompt 的完成条件和重试规则冲突，再交给 `prompt-eval`；
4. Prompt 修改通过局部对照后，回到完整 Agent 场景，确认真实工具调用和环境状态正确；
5. 若由 AI 生成了修复方案，实施前可用 `checking-solutions` 检查是否只针对原 badcase。

Prompt 层通过不等于 Agent 层通过。Agent 最终还可能受工具、权限、编排、记忆和环境影响。

## 6. 可以直接复制的提示词

### 审查 Prompt

```text
使用 prompt-eval 审查这次 Prompt 修改。
目标模型、宿主和任务如下：<填写>。
真实失败及运行记录如下：<填写>。
请盘点实际生效的 Prompt 表面，只报告会影响行为、权限或可验证性的问题，
给出最小候选修改，并设计目标失败、邻近正常和必要边界场景。
本轮只审查，不修改文件，不把待执行验证写成优化已生效。
```

### 比较两个 Prompt 版本

```text
使用 prompt-eval 比较 Prompt A 与 Prompt B。
固定使用同一模型、宿主、工具、权限、材料和推理设置。
重点判断目标失败是否改善、正常场景是否退化，
并将环境或工具问题与 Prompt 问题分开。
样本不足时不要声称稳定提升。
```

### 设计 Agent 测试

```text
使用 agent-eval 为这个 Agent 设计最小测试方案。
用户任务、业务规则、系统版本、工具和权限如下：<填写>。
请按业务后果选择质量维度，为高风险失败配邻近正常场景，
明确环境初始状态、期望最终状态、Oracle、需要保存的 trace 和停止边界。
本轮不搭建评测平台。
```

### 质检现有 Agent 评估

```text
使用 agent-eval 质检这些案例、指标、Judge 和评测报告。
检查任务是否有效、环境能否重置，并用已知正反例验证 Oracle；
模型 Judge 需要用人工确认样例校准并检查重复评分稳定性。
同时检查是否存在答案泄漏、评分器迎合或 Agent 篡改测试的可能。
区分可观察、可诊断和足以作为门禁的证据。
```

### 分析 Agent 失败

```text
使用 agent-eval 分析这次 Agent 失败。
用户目标、系统版本、trace、工具返回和环境最终状态如下：<填写>。
请区分模型、Prompt、工具、权限、编排、记忆、环境、案例和 Oracle，
优先给出能区分竞争解释的下一项证据。
只有定位到 Prompt 表面后，才交给 prompt-eval 继续修正。
```

## 7. 怎样判断评测结论可信

| 看到的证据 | 可以说明 | 不能自动说明 |
| --- | --- | --- |
| 模型说“任务已完成” | 模型生成了完成声明 | 环境中的任务真的完成 |
| 工具调用返回成功 | 工具接口返回了成功结果 | 业务状态已正确落库且可被用户观察 |
| 单次 Judge 高分 | 该 Judge 在这一次给出高分 | Agent 稳定、Judge 正确或适合发布 |
| 原 badcase 通过 | 当前输入下原症状未出现 | 共同原因已修复、同类场景都改善 |
| 平均分提升 | 被统计样本的平均结果变化 | 高风险场景没有退化 |
| benchmark 排名更高 | 模型在该 benchmark 配置下表现较好 | 当前产品、工具和权限组合更可靠 |
| trace 完整 | 执行过程可观察 | 结果正确、策略合规或评测可作为门禁 |

可靠结论通常同时具备：明确质量主张、有效场景、可信 Oracle、可复核结果、正常对照和清楚的适用范围。

## 8. 常见误区

- **先选评测平台，再定义要判断什么。** 平台只能承载证据，不能替你定义产品质量。
- **用模型 Judge 代替真实状态。** 能从数据库、文件、接口或业务契约直接判断时，优先使用确定性证据。
- **只看最终回答，不看工具副作用。** Agent 可能写得很像成功，但实际没有完成操作。
- **只复测原 badcase。** 需要能击穿关键词、固定值和单一路径补丁的对照。
- **把环境异常算成 Agent 失败。** 这会误导根因和版本比较。
- **为提高总分忽略高风险失败。** 权限、安全和不可恢复操作需要单独报告。
- **修改 Prompt 后不回到系统测试。** Prompt 局部行为改善，仍需完整 Agent 结果验证。

## 9. 团队最小 SOP

日常开发可以只保留五步：

1. 保存真实失败、系统版本和运行证据；
2. 用 `agent-eval` 判断失败层，或在已定位时直接用 `prompt-eval`；
3. 只修改有证据的问题；
4. 运行目标失败、正常对照和必要边界场景；
5. 记录证据支持什么、不支持什么，再决定是否进入下一阶段。

评测的价值不是产出一个漂亮分数，而是让团队知道：**当前版本在哪些任务和条件下可信，哪里仍然没有证据。**
