## 当前结论

现有证据支持“部分输出要求未实现”，不支持“Skill 整体没有生效”。当前会话存在能解释这些现象的平台约束；历史失败任务的完整运行时配置尚未取得，不能把当前环境直接当作历史根因证明。用户观察到 Sol 表现不同，是重要比较线索，但不是已控制变量的模型对照。

- 标题缺失：真实失败已确认。当前环境存在平台级标题风格约束，与 Skill 指定三级标题存在冲突。
- 引用 Skill：当前 Skill 明确允许环境要求披露时引用。不能仅因回复引用了条文，就认定该 Skill 违规。
- 模型差异：尚未排除切换模型时平台提示、思考深度、上下文或加载方式也发生变化。

在线来源核验见[官方文档证据](gpt-6-skill-model-evidence-2026-09-08.md)。已抓取的 [OpenAI Model guidance](https://developers.openai.com/api/docs/guides/latest-model) 明确描述 Astra 对冲突技能更敏感，技能披露属于提示词示例，默认倾向列表、表格和 Markdown；[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) 说明通用的消息角色优先级。这些来源支持调查方向，仍不构成历史根因或两模型行为对照。

## 下一步：能区分原因的最小实验

先做模型与宿主配置的对照，再决定是否修改 Skill。直接在用户消息中重复标题只能改变指令显著性，不能排除更高层冲突。

1. 固定两份 Skill 的字节版本、输入需求、显式加载方式、工具结果与新会话条件。保留实际 model ID、有效 effort、平台版本以及可取得的请求配置；缺失项标为未知。
2. 在可控制指令角色的运行器中，分别测试 Astra 与 Sol。对每个模型，使用相同的基础指令和相同的模型间兼容配置；不要把“UI 里只切换模型”当成已证明请求完全相同。
3. 标题实验：基础环境先无标题冲突，再只加入一条开发者级标题限制。比较标题遵守情况。
4. 披露实验：基础环境先无披露要求，再只加入一条技能导致暂停时解释原因的开发者级要求。比较引用行为。
5. 两类实验独立进行。先配对运行，再交替重复并报告次数；一次成功不算兼容性修复。完整业务样例确认后，才用短输入定位敏感条件。
6. 分列评分：已加载、问题完整、格式、披露是否符合环境、任务边界、回答后是否实际推进。不要把几项揉成“Skill 是否有效”。

可证伪预测：

- 若冲突只在加入平台标题约束后出现，两模型均如此，支持宿主冲突机制。
- 若在相同无冲突输入下 Astra 持续失败、Sol 持续成功，才进一步支持模型执行差异。
- 若只直接调用澄清 Skill 正常、经入口失败，才调查路由或指令显著性。
- 若缺失只出现在长上下文而短上下文正常，再研究上下文影响。

当前工具能读取历史任务，但本轮未建立可控制系统／开发者消息的两模型运行器；没有执行上述生成对照。当前诊断仍处于证据调查阶段。
