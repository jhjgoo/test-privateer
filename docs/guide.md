# 海盗派启发式测试：方法与 Skill 使用教程

这不是一套“把需求丢给 AI，等它生成测试用例”的流水线。

它教你和 AI 一起认识产品、发现真正值得测试的问题、设计有效实验，并让证据决定下一步。

## 1. 先别急着写测试用例

拿到 PRD 就开始列正常、异常、边界，是测试中最常见的偷懒。它默认了三件往往不成立的事：PRD 描述了完整产品；规则已经明确；列出来的检查就是最重要的检查。

海盗派 Tester 先问：

- 用户想完成什么？产品承诺改变什么？
- 这个功能嵌在怎样的业务链和系统联动中？
- 哪些信息仍不足以判断好坏？
- 什么可能让价值落空，或给用户和业务造成伤害？
- 用什么实验、从哪里观察，才能取得可信证据？

所以，第一份产物通常不是用例，而是更准确的测试使命、待澄清问题、测试地图或测试模型。

## 2. 海盗派 Tester 的工作原则

### 为学习而测试

测试不是执行既定脚本，而是在有限时间内学习产品。每次测试都应回答一个问题、推翻一个假设，或者缩小一个未知。

### 测产品，不是抄需求

PRD 是信息源，不是产品全貌。真实产品还包括业务流程、角色利益、上下游系统、历史数据、运行环境、故障恢复和实际操作方式。

### 价值定方向，风险定焦点，证据定下一轮

- 价值告诉你为什么测、成功意味着什么。
- 风险告诉你这一轮先把时间花在哪里。
- 证据告诉你已经知道什么、仍不知道什么、下一轮该往哪里走。

风险不是 Bug 的同义词。功能没有报错但无人采用、没有减少人工、产生错误业务结果，同样是产品风险。

### 启发式是探照灯，不是检查表

SFDIPOT、MFQ、PPDCS 帮你看到容易遗漏的内容。它们不会替你判断，也不要求每次全部使用。工具没有带来新信息、新测试条件或新决策，就该停。

### 没有 oracle，就暴露缺口

Oracle 是判断观察结果是否可接受的依据。它可能来自业务规则、用户承诺、协议、账务守恒、历史基线或可比系统。依据不存在时，记录未知并找人确认；不要让 AI 编造预期结果。

### Tester 是探索搭档，不是越权审批人

Tester 帮团队暴露价值、规则、可测性和残余风险，但不替产品制定规则，不替业务接受损失，也不替发布负责人批准上线。

## 3. 测试生命周期是一轮学习

```mermaid
flowchart LR
    A[明确使命和价值] --> B[补齐业务与系统上下文]
    B --> C[扫描并组织测试空间]
    C --> D[选择当前产品风险]
    D --> E[必要时建立模型]
    E --> F[派生 TCON]
    F --> G[设计并执行测试]
    G --> H[调查 Finding]
    H --> I[更新认知与下一轮]
    I --> B
```

这张图表达依赖，不是强制顺序。你可以：

- 已经有明确 TCON，直接设计测试；
- 执行时发现规则不清，返回澄清；
- 一个简单改动无需 PPDCS，直接从候选测试点设计实验；
- 一次 Finding 改变风险排序，立即停止低价值测试；
- 只调用一个方法 Skill，解决眼前问题。

判断下一步只问一句：**当前最妨碍测试的认知缺口是什么？**

## 4. 五分钟开始

### 安装

这套工作流由 18 个 Skill 组成。主入口会调用其他 Skill，因此安装全集：

```bash
npx skills add jhjgoo/heuristic-testing-skills --skill '*'
```

Codex 全局安装：

```bash
npx skills add jhjgoo/heuristic-testing-skills --skill '*' --agent codex --global --yes
```

### 最小调用

```text
使用 heuristic-testing 和我一起测试这个需求。
先说明当前理解和最需要探索的问题，不要直接输出完整测试计划。
这是 PRD：……
```

一个合格的首轮回复应包含：

1. 测试对象与当前理解；
2. 已知事实、推断和未知；
3. 一个会改变测试范围、模型、oracle 或优先级的问题；
4. 用户回答后再决定下一项测试活动。

如果 Agent 立即输出几十条用例，让它停下：

```text
不要假设业务和系统上下文。先告诉我：你当前根据哪些证据理解产品，缺少的哪项信息最可能改变测试？一次只推进一个探索目标。
```

## 5. 两条使用路径

### 独立测试

适合一次性 PRD 分析、临时测试设计、非项目目录或单次测试执行。产物可以直接交付，不创建项目 TCO 或 Spec 文档。

```text
使用 heuristic-testing 走独立测试路径。
目标是为这份 PRD 编写具体用例。先共同补齐测试依据，再根据需要选择启发式工具；版本与环境未核实时不宣称可执行。
```

### 项目级测试

适合开发项目以及通用 TDD/SDD 流程：

```text
testing/TCO.md                                      # 项目长期测试地图
<需求目录>/<前缀>-test-analysis.md                    # 分析、风险与行动
<需求目录>/<前缀>-test-cases.md                       # 用例和执行记录
<需求目录>/<前缀>-test-basis.md                       # 详细依据与模型（按需）
```

项目只维护一份 TCO，汇总长期认知、风险和资产索引。需求分析与用例默认分文件，详细模型与证据按需拆分；缺少明确需求目录时使用 testing/requirements/<前缀>/。单个需求或任务不能新建一份 TCO。

测试分析应在开发实施前进入：先暴露规则冲突、系统依赖、数据边界、oracle 和可测性问题，再让实现建立在更可靠的认识上。

## 6. 贯穿案例：和 AI 一起测试票据助手

以下内容是教学示例，不是票据业务的真实规则。示例中的规则必须由实际业务确认。

### 6.1 别让 Agent 对着 PRD 闷头猜

用户只提供一句需求：

> 用户上传票据后，Agent 自动识别并匹配已有费用；没有匹配项时建议新建，确认后写入系统。

错误做法：立即围绕文件格式、接口超时和幂等输出一大堆测试点。它们可能有用，但还没有证据证明它们最重要。

正确的第一轮：

```text
当前理解：用户希望减少票据录入和费用匹配的人工操作。系统需要识别票据、寻找已有费用、在用户确认后写入。

已知事实：存在“匹配已有费用”和“建议新建”两条路径；写入前需要用户确认。
推断：匹配结果会影响账务数据，但 PRD 尚未说明影响对象和错误代价。
未知：真实用户、完整业务链、匹配规则、重复票据处理、写入目标和验收依据。

本轮问题：这个功能主要服务谁，他们现在怎样处理票据；一次错误匹配与一次漏匹配，哪种业务后果更严重？
```

用户补充：员工报销后由财务复核；系统把票据关联到费用记录。错误匹配可能把别人的票据挂到当前员工费用上，漏匹配只会增加一次人工操作。

认知变化：

- 价值从“识别成功”收紧为“减少人工且不破坏费用归属”；
- 错误匹配比漏匹配更值得优先测试；
- 身份、费用归属、复核与撤销进入测试范围；
- “匹配成功率”不能单独作为 oracle。

这就是澄清的价值：问题改变了测试，而不是让用户替 Tester 写方案。

### 6.2 用 SFDIPOT 扫描产品，不是抄 PRD

此时调用 `scanning-product-with-sfdipot`。先标明“当前主要是 PRD 与用户陈述视角”，再主动寻找系统资料、接口、数据字典、历史缺陷和实际操作者。

| 因子 | 票据助手中的具体内容 | 暴露的未知或候选测试点 |
| --- | --- | --- |
| Structure | 上传入口、识别服务、匹配服务、费用库、确认记录、写入适配器 | 哪个组件保存原票和识别版本？失败后由谁恢复？ |
| Function | 上传、识别、去重、匹配、建议新建、确认、写入、撤销 | 修改识别字段后是否重新匹配？确认前后允许哪些操作？ |
| Data | 图片/PDF、票号、税号、金额、日期、员工、费用 ID、置信度、状态 | 空值、模糊值、重复票号、跨员工同金额、历史脏数据 |
| Interfaces | 上传页面、候选列表、确认交互、识别 API、费用查询 API、写入 API | 页面显示与 API 返回是否一致？超时后用户看到什么？ |
| Platform | 浏览器、移动端、OCR 服务、存储、费用系统、权限环境 | 服务版本差异、资源限制、外部系统降级 |
| Operations | 员工提交、财务复核、纠错、撤销、批量处理、客服排障 | 财务如何发现错配？是否保留人工接管和审计线索？ |
| Time | OCR 耗时、查询超时、并发确认、重试、票据过期、跨账期 | 双击确认、超时后重试、写入成功但响应丢失、月末高峰 |

SFDIPOT 的直接产物是产品元素、关系、未知、取证动作和候选测试点。上表仍不是 Case，因为前置状态、具体数据、动作、观察位置和 oracle 尚不完整。

停止条件：扫描已经覆盖当前业务链和关键系统关系，新增条目开始重复，并且未知已有明确取证动作。不是七栏填满才停。

### 6.3 用 MFQ 组织有界测试空间

扫描很广，但无法直接安排工作。把“从识别完成到费用写入”设为本轮边界，用 `analyzing-test-space-with-mfq` 形成可导航的大纲。

| ID | 类型 | 内容 | 业务/系统关系 | 候选测试想法 | 证据状态 |
| --- | --- | --- | --- | --- | --- |
| M-01 | M | 生成费用匹配候选 | 消费识别数据，查询当前员工可关联费用 | 相同金额不同员工；字段修改后重算 | 匹配规则待确认 |
| M-02 | M | 用户确认匹配或新建 | 决定后续写入目标 | 候选切换；确认时目标已变化 | PRD 已说明需确认 |
| M-03 | M | 写入费用系统 | 创建或关联费用记录 | 部分成功；重试；撤销 | 接口契约待取得 |
| F-01 | F | 员工身份 × 候选过滤 × 费用归属 | 跨权限边界，决定错配伤害 | 他人同额费用不得成为可确认候选 | 业务后果已确认 |
| F-02 | F | 确认 × 并发修改 × 写入 | 页面状态可能落后于费用系统 | 确认前目标被关闭或改账期 | 并发规则未知 |
| Q-01 | Q | M-01 的正确性与可解释性 | 用户需判断候选是否可信 | 排名依据、关键信息、无候选解释 | UX 依据待观察 |
| Q-02 | Q | M-03 的可恢复性与可追溯性 | 响应丢失不能造成重复费用 | 重试结果、审计记录、人工恢复 | 运维资料待取得 |

M 是有职责边界和业务结果的单功能；F 是具体交互；Q 必须挂在某个功能、交互或产品结果上。不要把菜单项当 M，也不要列“安全性、性能、易用性”三个空词充当 Q。

### 6.4 风险决定这一轮先测什么

调用 `analyzing-product-risks`，同时检查价值未实现和产生伤害。没有可信概率数据时使用定性判断，不编风险分数。

| 风险 | 类型 | 现有依据 | 对测试的改变 | 分析与准备顺序 |
| --- | --- | --- | --- | --- |
| 错误候选被确认，票据关联到错误员工或费用 | 伤害 | 财务确认错配后果严重；F-01 涉及权限边界 | 提前测试身份隔离、候选解释、确认前复验和恢复 | 先分析并准备 |
| 自动化没有减少人工，财务仍需逐字段核对 | 价值未实现 | 核心价值是降低录入与匹配成本 | 增加真实工作流观察和人工步骤对比 | 先分析并准备 |
| 写入成功但响应丢失，重试生成重复记录 | 伤害 | Q-02 的外部写入与恢复机制未知 | 在真实集成环境测试超时、重试和审计证据 | 随后准备集成环境 |
| OCR 偶发识别错误 | 可能伤害价值 | 已知依赖识别服务，但错误分布未知 | 先收集生产样本分布，再决定边界深度 | 先补样本 |

本包默认用 P0–P3 表示当前可执行测试的轮次顺序。尚未实现、规则未定或环境不足的测试保留风险依据，单独安排澄清与准备。团队已有不同定义时保留团队语义，另列本轮执行顺序：

- P0：回答核心问题不可缺少的最小可执行集合；
- P1：可能改变本轮结论；
- P2：扩展结论边界；
- P3：当前增量价值低。

风险必须改变测试。只写“存在幂等风险、性能风险、安全风险”却不改变顺序、深度、环境、oracle 或恢复验证，等于没分析。

### 6.5 用 PPDCS 建模，再派生 TCON

“确认时费用目标可能已经变化”包含状态和事件，仅列测试点容易漏掉迁移。调用 `modeling-tests-with-ppdcs`，用 TEST 选主模型：

- Triggers：查询、用户确认、费用修改、写入响应；
- Essentials：不能跨员工关联，确认只能写入仍有效的目标；
- Spanning Differences：已有费用/新建、目标有效/失效、响应收到/丢失；
- Targets：费用关联状态与可恢复结果。

主模型选择 State。示例模型：

| 当前状态 | 事件 | 守卫条件 | 预期输出 | 下一状态 |
| --- | --- | --- | --- | --- |
| 已给出候选 | 用户确认 | 候选仍属于当前员工且可关联 | 发起一次关联写入 | 写入中 |
| 已给出候选 | 用户确认 | 候选已失效或归属改变 | 拒绝旧确认并刷新候选 | 待重新确认 |
| 写入中 | 返回成功 | 关联 ID 可查询 | 显示成功并保存审计信息 | 已完成 |
| 写入中 | 响应超时 | 最终结果未知 | 查询既有结果，不直接重复创建 | 待核实 |
| 待核实 | 查询到已写入 | 业务键一致 | 恢复为成功，不重复写入 | 已完成 |
| 待核实 | 确认未写入 | 仍满足写入条件 | 允许受控重试 | 写入中 |

从迁移派生 TCON：

| TCON | 派生来源 | 测试条件 | 关联风险 |
| --- | --- | --- | --- |
| TC-01 | 已给出候选 → 写入中 | 当前员工的有效候选被确认时，只发起一次正确关联 | 错配 |
| TC-02 | 失效守卫 | 候选在确认前失效时，旧确认不得写入并要求重新确认 | 错配 |
| TC-03 | 写入中 → 待核实 → 已完成 | 写入成功但响应丢失时，重试不得新增重复记录 | 重复费用 |
| TC-04 | 写入中 → 待核实 → 写入中 | 确认未写入后，只允许一次受控重试并保留审计链 | 重复费用、不可追溯 |

PPDCS 不是把 Process、Parameter、Data、Combination、State 全部画一遍。只选能解释主导机制的模型；第二模型不能产生新增 TCON，就删。

### 6.6 从 TCON 到可执行测试

TCON 表达“必须挑战的条件”，但还不能直接执行。调用 `designing-test-experiments`，补齐状态、角色、数据、环境、动作、观察位置和 oracle。

| Case | 本轮安排 | 状态与角色 | 数据与环境 | 动作 | 预期结果与判断依据 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| C-01 | P0 | 员工 A 已登录；候选属于 A 且可关联 | A 的票据与费用 E1；集成环境 | 选择 E1 并确认 | 页面、写入 API、费用库、审计记录一致；E1 只关联该票据一次 | 可执行 |
| C-02 | P0 | 员工 A 已看到 E1；财务随后关闭 E1 | 同上；可控制费用状态 | 关闭 E1 后使用旧页面确认 | 不写入 E1；说明失效；刷新候选；保留被拒绝记录 | 可执行 |
| C-03 | 补齐故障模拟环境 | A 确认新建；服务端完成写入 | 代理层丢弃成功响应 | 确认、制造响应超时、点击重试 | 按业务键只存在一条费用；客户端恢复成功；两次请求可追踪 | 待补环境 |
| C-04 | 先确认跨员工数据访问规则 | 员工 A 操作 | 与员工 B 同金额同日期的费用 | 上传 A 的票据并查看候选 | 待确认可见字段与关联权限；确认前不判定通过或失败 | 待确认规则 |

当前条件包括可执行、待核实、待实现、待补环境、待确认规则；同一用例可记录多个真实缺口。缺少判断依据时，明确阻塞原因和下一步。关联风险沿用上文结论，本轮安排不代替风险判断。

同一条 TCON 在以下任一项发生实质变化时应拆 Case：前置状态、角色、数据分区、刺激、观察位置、oracle、风险、测试层级或环境。

### 6.7 执行不是把 Case 改成“通过”

调用 `running-test-sessions` 保存真实环境、输入、操作、原始观察和证据位置。

示例执行记录：

```text
Session: S-20260904-01
Mission: 判断失效候选是否可能被旧页面确认并形成错误关联
Build/Env: staging 2026.09.04 / Chrome / expense-api v18
Executed: C-02
Evidence: request trace 7fd2…, database snapshot expense_E1_before/after, screen recording 02:14
Observed: 页面显示“关联成功”；写入 API 返回 409；费用库未变化
Finding: UI 与业务结果矛盾，用户可能误以为关联完成
```

“接口报 409”不自动等于缺陷。调用 `investigating-findings` 列竞争解释：

- 页面错误地把请求完成当业务成功；
- 409 在产品规则中被定义为已完成；
- 查询读到了旧状态；
- 测试数据被另一任务修改。

最低成本 probe：用关联 ID 查询最终状态，并核对前端成功提示的触发条件。如果证据支持第一种解释，再形成缺陷报告；否则更新模型和 oracle。

随后更新：

- 当前风险：用户错误判断完成状态，依据新增观察提高关注；条件具备后优先执行相关检查；
- 新 TCON：所有终态提示必须与可查询业务状态一致；
- 回归候选：失效候选、409、响应丢失三条恢复路径；
- TCO 或 Spec 文档：记录系统契约和证据，不只记录“发现一个 Bug”。

这才完成了一轮学习。

## 7. 方法与 Skill：什么时候用，拿到什么

### 明确使命：`setting-test-mission`

- **解决**：为什么测、测什么、时间花在哪里、何时停止不清楚。
- **输入**：业务目标、测试对象、利益相关者、时间资源、已有证据。
- **动作**：写出要回答的问题、价值、范围、约束、信息源和停止条件。
- **产物**：可检验的测试使命，而不是“保障质量”。
- **停止**：团队知道这轮测试要支持什么判断以及不测什么。
- **误用**：替团队决定是否研发、联调或上线。
- **下一步**：依据不足时澄清；范围很大时建立测试地图。

### 共同补齐依据：`clarifying-test-basis`

- **解决**：业务、系统、规则、约束或 oracle 的未知会改变测试。
- **输入**：需求、现有资料、代码或系统观察、当前未知。
- **动作**：先调查事实；每轮推进一个探索目标；用复盘、举例、反例、边界、差异、证据、后果和恢复来提问。
- **产物**：事实、推断、已确认规则、测试输入、暂定假设、未知和取证动作。
- **停止**：已经知道接下来要查什么，不再靠提问拖延实验。
- **误用**：问治理决策；一次抛出问卷；问题与测试变化无关。
- **下一步**：扫描产品、分析变化或直接设计验证未知的实验。

用三个追问过滤问题：`Huh?`——用户听得懂吗？`Really?`——依据可靠吗？`So?`——答案会改变什么？答不出最后一个就删。

### 建立项目地图：`mapping-project-test-space`

- **解决**：长期业务链、系统边界和覆盖地图不存在或失真。
- **输入**：业务流程、架构、接口、数据、角色、运维资料、历史缺陷和已有测试。
- **动作**：用引导词与 SFDIPOT 扫描项目全貌，建立元素、关系、证据和未知。
- **产物**：唯一的项目 `testing/TCO.md`。
- **停止**：地图足以判断变化影响和下一项取证，而不是追求百科全书。
- **误用**：每个需求新建 TCO；把 TCO 写成本次执行计划。
- **下一步**：对当前 Spec 使用 `analyzing-change-for-testing`。

### 分析当前变化：`analyzing-change-for-testing`

- **解决**：需求、设计或代码变化尚不能支持测试设计。
- **输入**：项目 TCO、Spec、diff、接口与数据变化、实施计划。
- **动作**：识别承诺变化、受影响业务链、系统边界、风险、可测性和需要提前澄清的规则。
- **产物**：Spec 级测试分析骨架。
- **停止**：变化已映射到具体测试空间、风险和后续方法。
- **误用**：重复整个项目地图；等开发完成后才分析。
- **下一步**：按缺口使用 SFDIPOT、MFQ、风险或 PPDCS。

### 扫描与组织测试空间

| Skill | 何时用 | 直接产物 | 停止条件 | 典型误用 |
| --- | --- | --- | --- | --- |
| `mapping-test-space` | 有界范围内的产品内容、交互和质量关注仍散乱 | 可导航的测试空间与候选测试点 | 足以选择下一轮分析或测试 | 把地图写成用例仓库 |
| `scanning-product-with-sfdipot` | 需要广泛盘点产品及系统关系 | 元素、关系、未知、取证动作、候选测试点 | 新扫描项重复，关键未知有去处 | 七栏填表；只摘抄 PRD |
| `analyzing-test-space-with-mfq` | 需要组织功能、交互和质量关注 | 带稳定 ID 的覆盖大纲 | 节点边界清楚，可继续排序或建模 | M 写菜单；F 写空泛“交互”；Q 写质量名词 |

### 选择焦点：`analyzing-product-risks`

- **解决**：测试范围已经可见，但重点、顺序、深度和投入不清楚。
- **输入**：产品价值、测试地图、候选测试点、历史证据和当前约束。
- **动作**：识别价值未实现与产品造成伤害；选择当前 1–5 个焦点；说明风险如何改变测试。
- **产物**：当前轮次优先风险及相应测试动作。
- **停止**：已经知道先测什么、为什么、需要什么证据。
- **误用**：把错误类型当风险；虚构概率；把所有风险列为高优先级。
- **下一步**：需要推导行为时建模，否则直接设计实验。

### 建模与派生：`modeling-tests-with-ppdcs`

| 模型 | 必须建出的内容 | TCON 从哪里来 |
| --- | --- | --- |
| Process | 参与者、步骤、分支、失败、恢复、结果 | 路径 |
| Parameter | 条件、取值、动作、完整规则、缺口冲突 | 决策规则 |
| Data | 数据域、分区、边界、约束、转换 | 分区与边界 |
| Combination | 因素、水平、约束、交互强度、可行组合 | 生成组合 |
| State | 主体、状态、事件、守卫、输出、合法/非法迁移 | 迁移与序列 |

- **使用**：有界功能的流程、规则、数据、组合或状态行为需要精确表达。
- **产物**：一个实际模型以及从它逐项派生的 TCON。
- **停止**：模型能解释关注行为；新增模型不再产生 TCON。
- **误用**：五类全部套用；画概念图但不派生 TCON；因素和约束不明就做组合压缩。
- **下一步**：用 `designing-test-experiments` 把选中的 TCON 具体化。

### 设计可执行测试：`designing-test-experiments`

- **解决**：候选测试点、风险或 TCON 仍不能执行。
- **输入**：选中对象、模型、环境、数据、oracle、可用工具。
- **动作**：选择 Case、charter、task 或自动检查；补齐七个执行要素；按本轮价值排序。
- **产物**：Markdown Case 表、探索章程或具体测试任务。
- **停止**：执行者无需猜测关键前置、动作、观察位置和判断依据。
- **误用**：把测试标题当测试；把所有条件组合展开；用例数量冒充覆盖。
- **下一步**：执行前审查，或直接运行测试会话。

### 单元测试：`writing-unit-tests`

- **解决**：行为需要用快速、稳定的代码级反馈锁定，或 TDD 的 RED 不够可靠。
- **动作**：选择最低有效 seam；测试可观察行为而非实现形状；确保 RED 因缺少目标行为而失败，再写最小 GREEN。
- **产物**：可读、确定、隔离且能解释失败原因的单元测试。
- **误用**：过度 mock；断言私有调用；只追求覆盖率；看到任何红灯都算正确 RED。
- **下一步**：运行目标测试，再决定是否补集成或系统层证据。

### 审查设计：`challenging-test-designs`

- **解决**：分析、模型、章程或用例准备执行，但可能存在会改变结论的断裂。
- **动作**：挑战价值、范围、证据、模型派生、oracle、环境和完成声明。
- **产物**：只保留会改变执行、覆盖或信心的问题。
- **误用**：报告措辞、格式和个人风格偏好；为了显得严格而无限加用例。
- **下一步**：修复关键断裂后执行。

### 执行与调查

| Skill | 核心动作 | 产物 | 不能做什么 |
| --- | --- | --- | --- |
| `running-test-sessions` | 执行、观察、记录、根据证据调整下一步 | 会话记录、原始证据、Finding、更新后的测试方向 | 把计划当结果；只记 Pass/Fail |
| `investigating-findings` | 复现、列竞争解释、设计最低成本 probe、评估影响 | 被解释的观察、缺陷证据或模型修正 | 把每个异常自动登记成 Bug |

### 回归、自动化与信心

| Skill | 解决的问题 | 核心原则 | 产物 |
| --- | --- | --- | --- |
| `selecting-regression-tests` | 变更或发布需要回归保护，但全量回归慢且嘈杂 | 选择最小可信回归集 | 选择依据、执行顺序、覆盖与残余风险 |
| `designing-test-automation` | 高价值检查重复出现或反馈过慢 | 自动化购买反馈，不购买覆盖率表演；选择保留行为与 oracle 的最低层级 | 候选、seam、层级、触发、oracle、维护决策 |
| `assessing-test-confidence` | 需要用证据支持继续、停止或残余风险说明 | 主张与证据匹配；通过率不是信心，测试结论不是上线批准 | 已支持主张、证据限制、残余风险、建议下一步 |

## 8. 候选测试点、TCON、Case 和证据别混用

| 层次 | 回答的问题 | 示例 |
| --- | --- | --- |
| 候选测试点 | 哪里可能值得查？ | 确认前费用目标发生变化 |
| 模型 | 产品机制如何运转？ | 候选、失效、写入中、待核实等状态迁移 |
| TCON | 哪个条件必须被挑战？ | 候选失效后旧确认不得写入 |
| Case/charter | 具体怎样测试？ | 建立 E1、让财务关闭、从旧页面确认、观察 UI/API/数据库 |
| 证据 | 实际发生了什么？ | trace、快照、录屏、最终业务状态 |

跳过层次不是绝对错误。简单行为可以从候选点直接写 Case；复杂规则若不建模就容易漏测。关键是不要给半成品贴上“可执行”的标签。

## 9. 常见误用：看似专业，实际没有测试

1. **Agent 首轮输出大报告。** 纠正：先输出当前理解与一个高价值探索问题。
2. **SFDIPOT 全是 PRD 原句。** 纠正：标明证据视角，主动寻找业务、系统、数据和运维事实。
3. **MFQ 只有名词。** 纠正：M 有业务结果，F 是具体关系，Q 有挂载对象和观察方向。
4. **风险全是异常技术词。** 纠正：先说明威胁什么价值或造成什么伤害，再说明如何改变测试。
5. **PPDCS 五图齐全，TCON 为空。** 纠正：只留主模型；每个模型元素都要能派生条件。
6. **把测试点直接叫用例。** 纠正：检查七个可执行要素。
7. **用 P0–P3 固化全部测试。** 纠正：优先级服务当前轮次，证据变化后重排。
8. **执行记录只有 Pass/Fail。** 纠正：保存环境、输入、动作、原始观察和证据位置。
9. **看到异常立即报 Bug。** 纠正：列竞争解释，用最低成本 probe 区分。
10. **通过率高就宣称可上线。** 纠正：只声明证据实际挑战过的主张，并暴露限制。
11. **每个需求创建 TCO。** 纠正：项目一份 TCO，变化一份 Spec 测试文档。
12. **每次强制跑完所有 Skill。** 纠正：按当前认知缺口路由。

## 11. 可复制的启动提示词

### 独立测试分析

```text
使用 heuristic-testing 与我共同完成这次测试分析，走独立路径。

目标：[这轮测试要回答的问题]
测试对象：[PRD、页面、API、程序或观察]
已有材料：[链接或文件]
已知约束：[时间、环境、人员]

先调查你能自行取得的事实，再输出当前理解、证据状态和本轮最有价值的一个问题。不要直接生成完整测试计划，不要机械执行全部启发式工具。后续根据认知缺口选择 Skill，并明确每一步的产物和下一步。
```

### 项目级测试

```text
使用 heuristic-testing 走项目路径。

先检查并更新项目唯一的 testing/TCO.md；不要为本次任务新建 TCO。结合 TCO 与当前 Spec，在开发实施前识别业务链、系统影响、规则、oracle、风险和可测性缺口。

与我共同澄清关键未知，再按需要使用 SFDIPOT、MFQ、风险分析或 PPDCS。把候选测试点、TCON、Case 和证据分开维护，并将本次产物写入当前 Spec 的测试文档。
```

### 从分析进入可执行测试

```text
使用 designing-test-experiments，把已选 TCON 和风险转为可执行测试。
每条测试明确状态、角色、数据、环境、动作、观察位置和 oracle；Case 默认用 Markdown 表格。无法执行的条目标记为“待补环境”或“待确认规则”，并写清下一步，不要猜预期。
```

## 12. 最小完成检查

结束一轮测试前，检查：

- [ ] 测试使命说明了要学习什么，而不是“保障质量”。
- [ ] 已区分事实、推断、规则、假设和未知。
- [ ] 测试没有被限制在 PRD 文本内，关键业务链和系统联动已进入视野。
- [ ] 风险同时考虑价值未实现与产生伤害，并实际改变了测试。
- [ ] 使用的启发式工具产生了新认知或新测试条件，而不是填表。
- [ ] 候选测试点、模型、TCON、Case 和证据没有混写。
- [ ] 可执行测试明确状态、角色、数据、环境、动作、观察位置和 oracle。
- [ ] 执行保留了原始观察与证据，不只有 Pass/Fail。
- [ ] Finding 已被调查，没有自动等同于 Bug。
- [ ] 测试结论只覆盖证据实际支持的主张。
- [ ] 新证据已更新风险、测试地图、Spec 文档或下一轮计划。

如果这些问题都有答案，你使用的就不只是几个 Skill，而是一套能够持续学习、调整和交付证据的测试方法。


## 当前能力与交付边界

这套 Skill 按任务和已有信息提供帮助，不设置测试新人或开发者模式。目标明确就推进，关键歧义用业务例子澄清；当前用户能否确认规则取决于实际责任和证据。规则未知只暂停相关预期，其他明确测试继续。

| 工作 | 产物及边界 |
| --- | --- |
| 测试分析 | 测试点、条件、必要模型、依据与未知 |
| 测试设计 | 具体用例、任务或探索章程，数据、动作和观察清楚 |
| 执行准备 | 核实版本、账号、数据、操作与观察入口；未调查写待核实 |
| 实际执行 | 在已有授权内操作，记录实际结果与证据 |

这些工作可在探索中往返，不要求四份文档。设计完成不代表可执行，可执行不代表已获授权或已通过。探索章程可调查未知，但不能用未知规则判定通过／失败。

例如下一步写“为企业关联和审批回写编写具体用例，补充数据、步骤和预期；版本与环境尚待核实”，比“深化为可执行测试”更明确。用户回复“开始下一步”只承接这项已说明的动作。

自动化入口按证据选择层级：单元测试使用 writing-unit-tests 编写并验证；接口、页面自动化通过 designing-test-automation 交付业务测试设计与框架接入信息，当前不提供对应脚本生成或运行。已有测试仍可按授权执行，框架选定后再扩展新编写能力。

业务摘要使用具体场景；实现或执行测试需要的准确接口、字段、断言和控制手段可直接展示。方法模型与追溯交给下游，不能为了简化报告而丢失依据。

## 文档导航与持续更新

项目关联不明确时先问是否结合当前项目。已明确相关时主动读取 Spec、代码和测试，是否落盘另按任务决定。

需求文档共用稳定前缀：有编号用需求标识与短名，无编号用首次建立日期与短名。已有需求目录直接沿用，无明确目录则使用 testing/requirements/<前缀>/。默认拆分测试分析与测试用例，长依据按需拆出；一个项目仍只维护 testing/TCO.md。

主分析从任务摘要、行动清单进入，随后是有效业务规则、风险、全部已识别测试点、仍有效未知和产物链接。测试点按业务分组，区分本轮先做、后续补充、暂不覆盖与理由。完整用例和实际执行记录在用例文件；依据文件保留详细源码事实和实际模型。

风险状态使用待调查、处理中、已控制、已排除、已接受；每次变化有证据和范围。已接受需要有权负责人确认，暂不覆盖不等于风险已排除。局部风险在需求分析维护，共享风险由 TCO 维护；用例通过不能自动关闭风险。

新规则更新原条目并同步关联模型与用例；已解决问题退出待办，旧预期不留在有效指导中。原始执行记录保留，历史过程只保留必要摘要。用户说“继续”时完成当前授权范围内的调查与整理，不要求逐行推进。

模板随负责 Skill 提供：项目地图、需求分析、测试用例、可选依据。按任务填有内容的章节，不制造空表或为每个工具新建文档。

## 呈现：概览看图，明细对照表

复杂业务范围和测试层级优先用 Mermaid mindmap。图保留简短业务名称及必要编号，详细测试条件按业务分组用精简表格呈现：测试点、场景／条件、检查重点、关联用例。共同方法、依据、安排及理由放在组头，个别差异留在对应行；避免每行重复相同文字。

具体 Case 始终有表格条目，复杂步骤在表后按 ID 展开。业务流程、系统调用顺序或状态迁移难以解释时，可用相应 Mermaid 图辅助；条件与结果组合用决策表。图不维护第二份风险状态或执行结果，也不代替具体断言。

使用普通 Markdown 标题与表格，不使用 HTML 折叠标签。阅读器不能渲染脑图时，概览用短表，明细仍为分组表格，不降级为重复长列表。图与表的内容、编号和证据关联一同核对，呈现方式的变更先评审样稿再部署到 Skill。
