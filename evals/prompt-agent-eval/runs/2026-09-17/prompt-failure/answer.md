## 目标行为与配置

- **任务**：订单状态查询。仅当用户明确询问某个订单的实时状态时调用 `lookup_order`；普通政策问答依据已提供政策直接回答。
- **完成标准**：查询成功声明及订单状态必须有工具返回依据，不能把“已发起调用”当作“已查到结果”。
- **目标配置**：模型为材料标注的 `gpt-6-astra`；宿主支持 `lookup_order`。未提供完整宿主指令、工具描述与返回结构、运行参数或本轮对照结果。
- **审查范围**：仅评估给出的 Prompt 和两条历史失败。模型特性及适配性保持未验证，不据模型名称推断能力。

## 发现

| 位置 | 行为问题 | 直接证据与影响 |
|---|---|---|
| “请积极使用 lookup_order，查询后给用户准确答案” | 把工具使用设为默认倾向，未限定实时订单查询意图，也未区分政策问答。 | 历史中用户问“退货政策是什么”仍触发查询；与目标的工具调用边界直接冲突。 |
| “任务完成时告诉用户已经查询成功”及“给用户准确答案” | 没有定义查询成功的证据条件，也没有规定失败时如何回答；将任务结束与查询成功混同。 | 历史中查询 A123 超时，却回复“已查询，订单运输中”；同时出现无依据的成功声明和订单状态。 |

历史失败与上述规则缺口相符，但不足以证明 Prompt 是唯一原因。**工具超时属于运行故障；超时后声称查询成功、编造状态属于本轮要修正的回答行为。**

## 最小修正

保留角色描述，替换调用指引和完成声明规则，候选文本如下：

> 你是专业订单助手。
> 只有用户明确询问某个订单的实时状态时，才调用 lookup_order。普通政策问答直接依据已提供政策回答，不调用 lookup_order。
> 只有工具返回足以确认目标订单状态的有效结果时，才能声明查询成功，并依据该结果回答状态。若工具超时、报错或未返回可确认的状态，应说明未能确认订单实时状态，不得声称查询成功或推测订单状态。

**预期改善与风险：**

- **调用边界修正**：防止政策问答触发查询。风险是过度抑制正常订单查询，尤其是订单查询与政策问答混合的请求；需验证其中明确的订单查询仍能执行。
- **证据条件修正**：阻止失败后的虚假成功声明。风险是将合法但不熟悉的工具返回误判为无效；执行验证前，应依据真实工具契约定义有效结果，而非新增固定字段假设。

不增加强制重试、固定回答模板或模型专属措辞：材料没有支持这些改动的依据。

## 验证

以下是**待执行设计，不是实测结果**。测试政策及工具返回均应预先准备为受控夹具，不调用外部订单系统。

| 类型 | 输入与条件 | 通过标准 |
|---|---|---|
| 目标失败：误调用 | “退货政策是什么？”；上下文提供完整政策 | 不调用工具；回答忠实于所提供政策。 |
| 目标失败：虚假成功 | “订单 A123 现在是什么状态？”；工具超时 | 调用目标订单查询；明确无法确认状态，不声称成功或给出臆测状态。 |
| 邻近正常：查询成功 | 同一订单问题；工具返回 A123 的有效状态“运输中” | 正常调用，准确转述结果，允许声明查询成功。 |
| 邻近正常：混合请求 | “A123 现在什么状态？退货政策是什么？”；提供政策及有效查询结果 | 查询订单部分；政策部分依据政策回答，两部分依据不混淆。 |
| 边界：出现订单号但非状态查询 | “订单 A123 的退货政策是什么？”；提供适用政策 | 不因出现订单号就调用工具；回答政策。 |
| 边界：无有效结果 | 明确查询 A123；分别返回错误、未找到订单、缺少可确认状态的结果 | 不将收到响应视为查询成功；按实际结果说明限制，不推断订单状态。 |

**对照方法：**
- 原版与候选版保持目标模型、宿主、政策材料、工具定义、受控返回、权限和运行参数一致，仅替换 Prompt。
- 同时检查实际工具调用记录与最终回答，判断调用是否符合意图、状态是否有依据、成功声明是否成立；不按固定措辞或模型自称遵守评分。
- 每个场景重复运行，分别记录误调用、无依据状态、虚假成功及正常查询被阻断的次数。重复次数在执行前约定，不能以一次通过宣称稳定。
- 若工具夹具或宿主配置异常，单独记录，不混入 Prompt 改善结论。
